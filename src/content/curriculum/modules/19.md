# Module 19: Infrastructure and application security

## Introduction

Add security boundaries to the same systems you already understand instead of memorizing
security products.

## Prerequisites

Linux, networking, API runtime and CI basics.

## Learning question

If an attacker gains control of one service account or port, what could they reach next, and which observable control would limit that path?

## Learning objectives

- [Assets, trust boundaries, and threats](#module-19-assets-trust-boundaries-and-threats)
- [Reduce exposure and privilege](#module-19-reduce-exposure-and-privilege)
- [Verify a control](#module-19-verify-a-control)

## Lesson

Security begins with knowing which identities, services and interfaces exist and what each can access. A
least-privilege account cannot necessarily prevent all compromise, but it reduces the damage of a stolen credential
or buggy process. Define trust boundaries across browser, reverse proxy, API, database and deployment runner.
Keep test systems separated from personal or organization production environments; apply patches and remove
unused services. For a demo exposed to the internet, a simple architecture with minimal listening ports is preferable
to a complicated stack full of unmaintained dependencies.
Threat modeling need not be elaborate: identify valuable assets, likely failure/abuse paths and feasible mitigations.
Validate that auth and network controls behave as intended rather than relying on labels such as "secure" or a
successful vulnerability scan alone.

### Assets, trust boundaries, and threats

Start with what needs protection: credentials, user data, service availability, deployment authority and backups.
Draw the request path and mark where trust changes: browser to proxy, proxy to API, API to database, and CI runner
to deployment target. For each boundary ask what could be spoofed, exposed, changed or made unavailable. A useful
threat model describes a plausible path and a testable mitigation, not just a list of products.

```diagram
browser → proxy → API → database
              │      │       │
          public edge auth   stored data
          TLS/filter least privilege backup access
```

### Reduce exposure and privilege

Inventory listening services, accounts, firewall rules, package versions and data stores. Disable or restrict
interfaces that are not needed, patch supported packages and avoid root for network-facing services. An SSH rule,
application login and database credential protect different paths; verify each one. Backups are security-sensitive
because they may contain the same data and credentials as the primary system.

### Verify a control

Choose a single control and test both expected access and denied access in a disposable environment. Save the
configuration and sanitized result, then identify residual risk. A scanner can find known patterns within its
coverage, but a clean report does not prove that authorization, network boundaries, recovery or operator access are
correct.

## Guided practice

List exposed ports, identities and data stores for the Status API lab. In a disposable copy, close one unnecessary
path, confirm the intended request still works and the unwanted request is denied, then document evidence and
residual risks.

## Common mistakes

Assuming Docker isolation replaces OS security, publishing a database to the internet, or treating
a green security scanner as a security guarantee.

## Mini-lab

Write a one-page threat model and a hardened configuration checklist for the Status API lab.

## Readiness check

Justify each privileged identity, listener and data store. Demonstrate one control with an allowed and denied test,
and identify at least one unresolved risk without claiming a scan certifies the system.

## Recall question

Why should a threat model connect an asset to a trust boundary and a plausible attack path instead of only listing security tools?

## Recall explanation

The asset explains what harm matters, the boundary shows where trust or authority changes, and the attack path
explains how harm could occur. A mitigation can then be chosen and tested at that boundary. Tools are useful only
when they reduce a stated risk and produce evidence.
