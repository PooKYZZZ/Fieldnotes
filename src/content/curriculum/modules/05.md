# Module 05: HTTP, TLS, APIs and reverse proxies

## Introduction

Learn the application request path behind many backend and infrastructure tasks, without needing
to master frontend development.

## Prerequisites

Module 04 networking.

## Learning question

When the browser displays an error, how can you locate the exact boundary that failed between name lookup and the application response?

## Learning objectives

- [HTTP requests and responses](#module-05-http-requests-and-responses)
- [TLS and authenticated connections](#module-05-tls-and-authenticated-connections)
- [Reverse proxies and upstreams](#module-05-reverse-proxies-and-upstreams)

## Lesson

### HTTP requests and responses

HTTP is a request/response protocol. A request names a method and target and can include headers and a body; the
response includes a status code, headers and optional content. Methods communicate intent, so a retry is not always
safe for an operation that changes state. Status codes describe the result at the HTTP layer, not the complete
health of all services behind it.

| Evidence | Likely layer to inspect next |
| --- | --- |
| No connection or timeout | Route, listener, firewall, or overloaded upstream |
| TLS certificate/handshake error | Certificate name, trust chain, expiry, and TLS configuration |
| HTTP 404 | The contacted HTTP server did not find that target at the selected route |
| HTTP 502 from a proxy | Proxy-to-upstream connection or response; inspect both logs |

These are starting hypotheses, not diagnoses. A proxy can return a status on behalf of another component, so compare
direct and proxied requests when the environment allows it.

### TLS and authenticated connections

TLS protects a connection's confidentiality and integrity and authenticates the server when the client validates its
certificate for the intended name and trust chain. Encryption alone does not decide whether the caller is allowed to
use an application feature. A browser lock icon is not proof of correct authorization, safe data handling or secure
backend services.

```diagram
name lookup → TCP connection → TLS certificate/handshake → HTTP request
     │               │                    │                       │
     └─ DNS answer   └─ socket path       └─ secure channel       └─ app behavior
```

### Reverse proxies and upstreams

NGINX can accept client traffic, terminate TLS, choose an upstream, add or forward headers, and enforce timeouts.
The API still owns application behavior and authorization. The proxy should trust forwarding headers only from
known proxy hops; otherwise a caller may spoof client or scheme metadata. Test the API directly and through NGINX
to separate binding, routing, proxy and application failures.

For a reproducible check, use `curl -i http://127.0.0.1:8000/health` against the API and compare it with the
configured proxy route. Record the exact status and response body; do not infer a network response from a log entry.

## Guided practice

Use `curl -i` against a working local endpoint and a deliberately incorrect path. Then stop only the disposable
upstream and request it through NGINX to observe the proxy error. Compare the API and proxy logs; restore the
upstream and confirm the health endpoint before Activity A05.

## Common mistakes

Mistaking localhost inside a container for the host, passing untrusted forwarded headers blindly,
and treating HTTPS as a substitute for authorization.

## Mini-lab

Put a tiny /health FastAPI endpoint behind NGINX in a local VM; document exactly how
requests reach it.

## Readiness check

Trace the request through name resolution, connection, TLS, proxy and API. Diagnose a broken upstream mapping
using response and log evidence, and explain why HTTPS alone does not establish authorization.

## Recall question

Why does an HTTP 502 from a reverse proxy not prove the API itself generated that response?

## Recall explanation

The proxy is an HTTP server and can construct a 502 when it cannot reach its configured upstream or receives an
invalid upstream response. Compare the proxy's error log, upstream address and direct API request to identify where
the failure occurs. A status code is evidence about the responding hop, not a complete path trace.
