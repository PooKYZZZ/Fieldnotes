# Module 23: Incidents, backups, recovery and disaster scenarios

## Introduction

Practice restoring service and data after common failures instead of relying on luck and rebooting.

## Prerequisites

Linux operations, cloud basics, and monitoring.

## Learning question

If a deployment corrupts data and the service is unavailable, how do you stabilize the incident and prove that recovery actually works?

## Learning objectives

- [Triage and incident timeline](#module-23-triage-and-incident-timeline)
- [Backups, RPO, and RTO](#module-23-backups-rpo-and-rto)
- [Restore and recovery verification](#module-23-restore-and-recovery-verification)

## Lesson

An incident response begins with establishing user impact, the recent changes and current symptoms. Stabilize the
service before making speculative changes, preserve useful logs and record a timeline. The nearest visible error may
be a downstream symptom, not the initiating cause.
A backup that has never been restored is an unverified assumption. Recovery point objective (RPO) describes
acceptable data loss, while recovery time objective (RTO) describes an acceptable recovery duration. Define them
for the lab without claiming the system actually meets them until a drill proves it.
Rollback, restart, restore and failover are different responses. A new application version may roll back quickly, but
incompatible data migration can make rollback dangerous. Keep repeatable restoration instructions and practice the
complete workflow on isolated disposable infrastructure.

### Triage and incident timeline

Start by identifying user impact, affected service and the time symptoms began. Check the most recent change, logs,
monitoring and dependencies; preserve useful evidence and record timestamps with time zone. Stabilize the system
using a bounded action before attempting speculative repairs. The first visible error may be a downstream symptom,
so state what is confirmed and what is still a hypothesis.

### Backups, RPO, and RTO

A backup is a recoverable copy, not simply a successful job message. Recovery Point Objective (RPO) describes the
maximum acceptable data loss measured in time; Recovery Time Objective (RTO) describes the target time to restore
service. They are requirements to test, not performance claims. For example, a lab might choose an illustrative
RPO of one day and RTO of four hours, then discover through a drill that its actual recovery takes longer.

Protect backup access, retain copies separately from the source, and consider whether encryption keys and runbooks
are available during an incident. A backup exposed to the same compromised credentials as production may not
protect against deletion or ransomware.

### Restore and recovery verification

Restore into a clean, isolated target using a copy of the backup. Verify record counts or checksums, application
behavior, credentials/configuration and required access. Record the actual lost-data window and elapsed time. A
restart brings a process back; rollback changes a release; restore recovers data; failover redirects service. These
actions solve different problems and may need to be combined.

```diagram
detect → assess impact → stabilize → restore/rollback → verify user path → review
  │                         │                              │
timeline                 preserve data                  actual RPO/RTO
```

## Guided practice

Stop the API, corrupt a noncritical config in a copied lab, restore a test database snapshot and record the
timeline.

## Common mistakes

Deleting evidence, assuming a backup succeeded because the job ran, and testing restoration
against valuable live data.

## Mini-lab

Complete a controlled incident drill with detection, mitigation, data restoration and short
postmortem.

## Readiness check

Prove a working restore and explain what data or service availability would be at risk
in a real outage.

## Recall question

How are RPO and RTO different, and what evidence is needed before claiming that a system meets either target?

## Recall explanation

RPO is about acceptable data loss; RTO is about time to restore service. A stated target alone is not evidence.
Measure the data point restored and elapsed recovery time during a complete drill, including dependencies and
verification, then compare the observed result with the targets.
