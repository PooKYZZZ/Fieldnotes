# Module 11: Continuous delivery, releases and rollback

## Introduction

Learn what changes between an artifact that passed tests and a version safely running for users.

## Prerequisites

Module 10 CI and basic service operations.

## Learning question

If the new version fails after deployment, what evidence and compatibility choices determine whether a rollback is safe?

## Learning objectives

- [Promoting a tested artifact](#module-11-promoting-a-tested-artifact)
- [Safe release and compatibility](#module-11-safe-release-and-compatibility)
- [Smoke tests and rollback](#module-11-smoke-tests-and-rollback)

## Lesson

Continuous integration produces evidence about a particular source revision; continuous delivery keeps a
deployable artifact ready for promotion. Continuous deployment automatically releases it, which is not necessary
for a personal learning lab. Separate build and release so the image tested is the image deployed.
A release is more than replacing a process. Configuration, database schema and external dependencies can make
rollback unsafe even if the old container image is available. Prefer backward-compatible database changes and
validate migrations independently; include backup/restore steps when the data matters.
A smoke test should exercise a narrow but meaningful path after deployment, not only confirm that a TCP port
accepts connections. Record which version was released, whether checks passed and which clear action restores
the previous known-good version.

### Promoting a tested artifact

CI tests a particular source revision and produces evidence about it. A release pipeline should promote the same
artifact through environments rather than rebuild different bytes for each environment. Record the commit and
artifact identifier (ideally a digest for a container image) with the deployment. Configuration can vary by
environment, but it must be explicit and validated.

### Safe release and compatibility

Before changing a service, check health, persistent data, configuration and external dependencies. A code rollback
may not undo a database schema migration or a message already sent to another system. Backward-compatible
expand/contract changes allow old and new code to coexist during a rollout: add a compatible field, deploy code that
supports both shapes, migrate usage, then remove the old field in a later release. This is a pattern, not a guarantee;
test it against the application's real data operations.

### Smoke tests and rollback

A smoke test exercises one narrow but meaningful user path after release. A TCP connection or `/health` response
can confirm process availability, while a request through the actual proxy may confirm routing and application
behavior. Keep the known-good artifact and a documented restore procedure available. Define who decides to roll
back and how to verify recovery; a restart is not a rollback.

```diagram
commit → test/build once → identify artifact → deploy → smoke check
                                      │                     │
                                      └──────── failure ◀──┘
                                               ↓
                                  restore known-good version → verify
```

## Guided practice

Deploy two numbered versions in a disposable environment. Verify the new version label and a meaningful request,
introduce a controlled failure, return to the prior artifact and repeat the smoke check. Keep the test data and
schema compatible with both versions.

## Common mistakes

Using latest tags without traceability, testing one image but deploying another, or relying on blind
restarts after a bad release.

## Mini-lab

Create a deployment checklist and a script or documented procedure for versioned release plus
manual rollback.

## Readiness check

Release an identifiable artifact, reproduce a failure, roll back without losing test data, and verify both service
health and one user-facing request. Explain why the database change, if any, remains safe across that rollback.

## Recall question

Why can changing the container image back to the previous version fail to restore the whole service?

## Recall explanation

The deployment also depends on configuration, data schema and external side effects. The prior code may not read a
new incompatible schema, and restarting cannot undo messages or data already changed. Plan backward-compatible
migrations and verify the full user path after restoring the known-good artifact.
