# Module 12: Cloud concepts and Azure foundations

## Introduction

Learn one provider deeply enough to understand shared responsibility rather than memorizing
service names.

## Prerequisites

Linux, networks and basic service deployment.

## Learning question

When you create one small cloud VM, what else is created, which responsibilities remain yours, and what may still cost money after shutdown?

## Learning objectives

- [Cloud service models and responsibility](#module-12-cloud-service-models-and-responsibility)
- [Azure resource dependencies](#module-12-azure-resource-dependencies)
- [Cost-aware experiments](#module-12-cost-aware-experiments)

## Lesson

### Cloud service models and responsibility

Cloud providers expose virtual infrastructure through APIs and consoles. Infrastructure as a Service delegates
physical hardware management to the provider but leaves you responsible for guest OS patching, configuration and
many security choices. Managed PaaS shifts more operations to the provider, but the shared responsibility boundary
depends on the service.

### Azure resource dependencies

Azure groups resources for lifecycle and governance. A VM depends on network interfaces, disks, network security
rules and sometimes public addresses; deleting only the VM may leave billable resources. Learn the dependency
graph before creating anything.

### Cost-aware experiments

Before a lab, list its resources, region, size, expected runtime and cleanup procedure. Check the current calculator,
offer conditions and account billing status. Stopping or deallocating a VM can stop some compute charges, but disks,
public IPs, storage and other resources may still incur charges. Budgets and alerts provide visibility; they are not
universal hard spending caps. For early practice, use a local VM or container when that teaches the same concept.
Student offers, eligibility, credits, and service pricing can change. Check the current official offer and the
subscription's billing state before planning a cloud lab. A budget or alert helps you notice spend, but may not stop
every charge. You can learn the resource-dependency and ownership concepts with a diagram and local VM first; do not
create a paid resource unless you have deliberately reviewed the current price and accepted the possible cost.

## Guided practice

Draw resource ownership for one test VM; list every resource and investigate which could incur a charge
after a stop/deallocation.

## Common mistakes

Assuming the cloud provider secures your application, equating region with availability zone, or
leaving disks/IPs after deleting the VM.

## Mini-lab

Create a resource diagram and cleanup plan first. Provision one tiny Azure Linux lab only after reviewing current
terms and accepting the potential cost; otherwise verify the dependency model with a local VM or documented example.
If you do provision it, inventory and remove every lab resource.

## Readiness check

Explain each VM dependency, the shared-responsibility model and your cost-safe
cleanup method.

## Recall question

Why can stopping a VM reduce compute charges while the whole resource group can still incur cost?

## Recall explanation

Stopping or deallocating a VM changes its compute state, but attached disks, public IP addresses, storage, snapshots,
and other services have their own lifecycles and pricing. Inventory dependencies, check the current provider pricing,
and verify cleanup rather than assuming that stopping or deleting one resource removes everything.
