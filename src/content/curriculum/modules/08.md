# Module 08: Container fundamentals with Docker

## Introduction

Package applications reproducibly and understand what Docker isolates - and what it does not.

## Prerequisites

Linux processes, networking and HTTP (01-05).

## Learning question

What does a container actually isolate, and where must you put data that needs to survive replacing it?

## Learning objectives

- [Images and build context](#module-08-images-and-build-context)
- [Containers and process lifecycle](#module-08-containers-and-process-lifecycle)
- [Persistence, networking, and exposure](#module-08-persistence-networking-and-exposure)

## Lesson

An image is an immutable package definition; a container is a running instance with a writable layer. Files written
into that layer can disappear when the container is replaced, so persistent application state should use explicit
volumes or external services. An image tag is mutable; pinning a digest is more precise when reproducibility matters.
Docker port publishing connects host-side traffic to a container port. Inside a container, localhost points at that
container, not the host or a neighbor. Container networking is not a replacement for learning ordinary TCP/IP,
routing and service binding.
Build lean images with pinned base versions where appropriate, non-root execution where feasible and a
.dockerignore to avoid copying secrets and unnecessary files. A container is not automatically secure simply because
it runs inside Docker.

### Images and build context

An image contains a filesystem and metadata used to start a container. Dockerfile instructions create reusable
layers, and the build context is the set of files available to the build. A broad context can accidentally copy
credentials, local databases or generated folders into an image layer. A `.dockerignore` narrows that input; build
logs and the resulting image should still be reviewed for unintended content.

A tag such as `status-api:dev` is a human-friendly name that may later refer to a different image. For a release,
record the immutable image digest or another verifiable artifact identifier. Reproducibility also depends on pinned
dependencies, base-image updates and the build process.

### Containers and process lifecycle

A container is a configured runtime instance, not a lightweight virtual machine: it normally shares the host kernel.
The container's main process is PID 1 in its process namespace. It must handle termination signals and child
processes correctly; otherwise `docker stop` can be delayed until forced termination. Prefer a small, non-root
process and grant only the capabilities it needs.

### Persistence, networking, and exposure

The writable container layer is tied to that container and is lost when the container is removed. A named volume or
bind mount puts state outside that layer, so you must also back up and restore it deliberately. Container
`localhost` is the container's own loopback interface. Other services should use the intended container network,
while `-p host:container` publishes a port to the host. `EXPOSE` is image metadata; it does not publish a host port
or open a firewall.

```diagram
Dockerfile + build context ──build──▶ image:tag/digest ──run──▶ container process
                                                              ├── writable layer (replaceable)
                                                              └── mounted volume (separate lifecycle)
```

## Guided practice

Build an image for your status API; inspect its logs, user, health, network, port mapping and mounts. Store one test
value in the container layer and one in a mounted volume, then replace the container and compare which value
remains. Never use production or personal data for this experiment.

## Common mistakes

Baking secrets into layers, treating EXPOSE as opening a firewall, running everything privileged,
and confusing restart with rebuilding an image.

## Mini-lab

Package the Status API in a Dockerfile and document its build/run and shutdown commands.

## Readiness check

Explain the image/container distinction, identify the process running as PID 1, show the state location and diagnose
a service binding to the wrong interface or port. Demonstrate which traffic is host-published and which is internal.

## Recall question

After a container is removed, why can a mounted-volume file remain while a file written only to the container layer disappears?

## Recall explanation

The container layer belongs to that container's writable filesystem, so removing the instance removes that layer.
A volume has a separate lifecycle and can survive replacement, but survival is not the same as a backup: verify that
you can restore a copy.
