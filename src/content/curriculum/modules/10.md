# Module 10: Continuous integration with GitHub Actions

## Introduction

Automate reproducible checks so a pull request provides stronger evidence than “it runs on my
laptop.”

## Prerequisites

Git, Python tests and Docker basics.

## Learning question

How can a pull request give trustworthy evidence about a specific change while limiting what untrusted code can access?

## Learning objectives

- [Workflow events and jobs](#module-10-workflow-events-and-jobs)
- [Checks and artifacts](#module-10-checks-and-artifacts)
- [Permissions and trust boundaries](#module-10-permissions-and-trust-boundaries)

## Lesson

CI validates a change repeatedly in a controlled environment. The runner checks out a known commit, installs
dependencies, executes tests and reports results; passing CI does not guarantee successful deployment or security.
Distinguish unit tests, integration tests, lint checks and build checks because they cover different failure classes.
Each job runs in a defined environment and may not share filesystem state with other jobs unless artifacts or explicit
services are used. Triggers such as pull_request and push have different trust boundaries. Workflows should not run
untrusted contributions with write access and long-lived secrets.
Start with a small pipeline: dependency install, test, static checks, container build. Add reports and clear logs before
adding advanced orchestration. When a job fails, first find the earliest causally relevant error rather than rerunning
blindly.

### Workflow events and jobs

A workflow file declares events, jobs and steps. An event such as a pull request schedules a runner; steps execute
commands or actions in that job's environment. Separate jobs can use different runners and do not automatically
share files. Use artifacts when one job needs a specific output from another. Cache dependencies to reduce install
time, but do not confuse a cache with a verified build artifact.

```diagram
pull request event → isolated runner → install locked dependencies → tests/lint/build
                                                         │
                                                         └── result + logs/artifact
```

### Checks and artifacts

Tests, lint, type checks, integration tests and container builds catch different failures. A green status applies to
the revision and workflow that ran; it does not prove a later commit or deployed environment is correct. When a run
fails, locate the first causal error and compare the exact commit, event and environment before rerunning.

An artifact should have a clear name, retention policy and relationship to the source revision. Preserve useful
reports while avoiding credentials, personal data and debug dumps that reveal secrets.

### Permissions and trust boundaries

Treat code from external pull requests as untrusted input. Give the workflow token only the permissions needed for
that event and job; a test job rarely needs repository write access. Do not expose deployment secrets to unreviewed
code. Avoid privileged triggers that check out and execute pull-request content under the base repository's
authority. Review action versions and protect workflow files like application code.

## Guided practice

Break one test in a throwaway branch; inspect the earliest relevant failure and the commit SHA. Compare the event
and token permissions for a branch push and a pull request. Restore the test, then explain which checks establish
correctness evidence and which security boundaries Activity A10 still needs to enforce.

## Common mistakes

Granting broad repository write permissions to all jobs, copying secrets to logs, and confusing a
green build with an operational health check.

## Mini-lab

Implement PR checks for your API, including tests and a container build; require passing status
before merge where available.

## Readiness check

Explain every workflow event, job and step; show that an intentionally failing test blocks the required check, and
identify what the workflow token and secrets can access. State what a green CI run does not prove.

## Recall question

Why should a test workflow triggered by an outside pull request normally have read-only repository permissions and no deployment secret?

## Recall explanation

The pull request can contain code an untrusted contributor controls, and workflow steps may execute that code. If
the runner has write permissions or secrets, the code could use them. Grant only the permissions the check needs and
keep deployment authority in a separate, appropriately trusted workflow.
