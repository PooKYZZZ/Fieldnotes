# Module 13: Cloud networking, IAM and cost controls

## Introduction

Operate a small cloud environment without accidentally exposing services or losing control of
costs.

## Prerequisites

Modules 04 and 12.

## Learning question

If a cloud host is reachable from one network but not another, which separate identity, network, guest-OS, and cost controls should you inspect?

## Learning objectives

- [Network paths and exposure](#module-13-network-paths-and-exposure)
- [Identity and authorization](#module-13-identity-and-authorization)
- [Cost limits and cleanup](#module-13-cost-limits-and-cleanup)

## Lesson

A virtual network and subnet organize address space, but access is also governed by security rules, route tables and
host firewalls. Do not assume that being on the same network automatically grants permission or that an
internet-facing public IP implies a service is running.
Identity answers who may perform a control-plane action; network controls decide which traffic can reach an
endpoint. A role that can create VMs is not the same permission as an SSH account inside the guest. Apply the
narrowest practical privileges and avoid credentials committed to code.
Budgets and alerts improve visibility but are not universal hard spending caps. Price depends on VM size, region,
runtime, disk, outbound transfer and other resources. Always check active resources, cost estimates, and the
subscription billing status. Never use a credit card solely because a lab seems free without checking the exact offer.

### Network paths and exposure

A virtual network defines address space and subnets; a route table and security rules affect how packets travel.
Network Security Groups filter traffic at Azure network interfaces or subnets. The guest operating system can also
filter traffic, and the application must listen on the intended address and port. A public IP makes an address
routable; it does not guarantee a listener or permit traffic through every filter.

```diagram
client → public/private endpoint → NSG rule → guest firewall → listening service
  │             │                    │              │                 │
source IP   address path         allow/deny      local policy       bind/port
```

Test one layer at a time. For administrative access, restrict the allowed source range where feasible and avoid
opening SSH to all internet addresses. Do not publish a database just because the application needs to reach it.

### Identity and authorization

Azure RBAC governs actions on cloud resources; a Linux account governs actions inside the guest; application roles
govern what a user can do through the service. These are different identities and trust boundaries. Use the smallest
role and scope that completes the task, require MFA where supported, and avoid using an Owner account for ordinary
deployment. A network allow rule is not user authentication.

### Cost limits and cleanup

Budgets, alerts and quotas answer different questions. A budget can notify you about spend, while a quota may limit
resource usage; neither should be assumed to stop all charges automatically. Review actual resources after each lab,
including disks, addresses, logs and snapshots, and verify billing terms before relying on student credits.

## Guided practice

In a disposable cloud lab, allow a test connection only from your current approved address. Demonstrate a denied
connection from a disallowed source where practical, inspect the NSG and host firewall rules, and remove the rule
after verifying the allowed path. If you cannot safely create cloud resources, complete the same review on a diagram.

## Common mistakes

Opening 0.0.0.0/0 on administrative ports, using subscription owner credentials in CI, and relying
on alerts as an automatic shutoff.

Build a resource inventory and short security review for a single-VM Azure application.

## Readiness check

List allowed inbound connections and the identity that owns each. Explain which control denied a test request,
justify each remaining permission, and show that unused cloud resources were removed.

## Recall question

Does granting a user Azure's VM management role automatically give that user a Linux shell account or permission to call the web API?

## Recall explanation

No. Cloud RBAC controls operations on Azure resources. Guest OS authentication and application authorization are
separate systems with separate identities and policies. Trace each access path to its enforcing control instead of
assuming one role grants access everywhere.
