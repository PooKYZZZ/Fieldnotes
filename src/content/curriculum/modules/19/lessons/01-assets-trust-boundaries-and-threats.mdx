<ConceptSection layout="split">
  <div className="learning-concept-copy">
    <p>Start with what needs protection: credentials, user data, service availability, deployment authority and backups. Draw the request path and mark where trust changes: browser to proxy, proxy to API, API to database, and CI runner to deployment target. For each boundary ask what could be spoofed, exposed, changed or made unavailable. A useful threat model describes a plausible path and a testable mitigation, not just a list of products.</p>
    <p>Example: a deployment credential is the asset; an unreviewed workflow change is a plausible path to misuse it; the CI-to-cloud identity boundary is where trust changes. A mitigation could restrict deployment to a protected environment and a narrowly scoped identity. Verify the boundary by checking that an untrusted test workflow cannot obtain deployment credentials and that the approved workflow can perform only its intended action. Record remaining risk if that check is out of scope.</p>
