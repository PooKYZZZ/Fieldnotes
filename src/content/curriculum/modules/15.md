# Module 15: Ansible and configuration management

## Introduction

Configure software repeatably after provisioning a machine, including the ability to audit changes.

## Prerequisites

Linux administration, YAML reading and SSH.

## Learning question

How can the same playbook safely bring a fresh machine into the desired state and avoid unnecessary changes when run again?

## Learning objectives

- [Inventory and desired state](#module-15-inventory-and-desired-state)
- [Modules, handlers, and idempotency](#module-15-modules-handlers-and-idempotency)
- [Check mode and privilege](#module-15-check-mode-and-privilege)

## Lesson

Ansible connects to managed hosts, typically through SSH, and applies tasks describing their desired configuration.
A package module knows how to determine whether a package is already installed; a blind shell install command
may run unnecessarily on every execution.
Idempotency means repeating the same desired-state operation does not keep changing the system; it does not
imply every playbook or custom shell task is safe to repeat. Test repeated executions and inspect changed and failed
counts. Handlers should run when a relevant configuration actually changes.
Separate environment-specific variables from reusable roles and templates, keep secret values in a proper protected
mechanism, and review privilege escalation per task. Prefer a disposable VM for testing a new playbook before
letting it touch valuable systems.

### Inventory and desired state

An inventory names managed hosts and groups, and a playbook maps tasks to those hosts. Variables select values such
as package versions or service ports. A module describes an operation in a way Ansible can usually inspect; for
example, a package module can compare installed state before acting. A raw shell command may succeed but leave
Ansible without enough information to know whether anything changed.

```diagram
inventory + variables → play targets → modules compare state → changed task → handler
                                                        │
                                                        └── already correct → no change
```

### Modules, handlers, and idempotency

Idempotency means that repeating the same operation against the same inputs converges without continually changing
the host. It is not a promise that every task is harmless to repeat; custom shell commands can still append duplicate
data or restart a service on every run. Handlers run when notified by a changed task, which is useful for a service
restart after its configuration changes.

### Check mode and privilege

`ansible-playbook --check --diff` can preview changes for modules that support check mode, but it cannot perfectly
simulate every custom operation. Review privilege escalation (`become`) only where required, validate SSH host
identity, and protect credentials. Compare the first and second normal run: the second should have few or no
unexpected changes. Record exceptions rather than hiding them.

## Guided practice

In a disposable Ubuntu VM, run a short playbook to install one package and template a service configuration. Run it
again and compare changed-task counts. Alter the test config manually, run check mode, then reapply and verify the
service. Review each privileged task before using Activity A15 on a fresh VM.

## Common mistakes

Using shell commands for every task, disabling host-key checks without reason, or believing check
mode simulates every custom operation perfectly.

## Mini-lab

Configure a clean Ubuntu VM with a service account, runtime packages, NGINX and the status
service.

## Readiness check

Reproduce the setup on a fresh VM, explain why a second run did not make unintended changes, and describe every
privileged operation with a rollback option. Identify one task that check mode cannot fully predict.

## Recall question

If an Ansible playbook reports a changed task on every run, does that prove useful work is still happening?

## Recall explanation

No. The task may be written in a non-idempotent way, such as appending duplicate text or running an opaque shell
command. Inspect the task and actual file/service state, then prefer a module that declares the desired state or a
guard that can be tested. Check mode is helpful but depends on module support.
