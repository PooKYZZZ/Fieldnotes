# Module 09: Docker Compose and service dependencies

## Introduction

Operate multiple cooperating services on one host and understand dependency, startup and state
boundaries.

## Prerequisites

Module 08 plus basic web architecture.

## Learning question

When the API starts before its database is ready, how should the application recover without relying on an arbitrary delay?

## Learning objectives

- [Compose services and service discovery](#module-09-compose-services-and-service-discovery)
- [Readiness and health checks](#module-09-readiness-and-health-checks)
- [Configuration and persistent state](#module-09-configuration-and-persistent-state)

## Lesson

Compose describes a group of containers, their networking, volumes and operational settings. Containers on the
same Compose network can often reach one another by service name; published ports are typically required only to
reach a service from outside the network.
Startup order is not readiness. A database container process may exist before migrations or connections succeed;
use health checks and application retry logic instead of hoping a fixed sleep will work. Healthchecks should test
meaningful functionality, not merely whether a process is alive.
Prefer configuration outside the image and protect credentials. Environment variables can still be exposed to
processes and tooling, so they are not an adequate secret-management system on their own. Keep database data on
named volumes and plan how schema changes and backups affect rollout and rollback.

### Compose services and service discovery

A Compose project defines related services, networks, volumes and runtime settings. Services on a shared network
can resolve each other by service name, so an API can connect to `db:5432` without publishing the database port to
the host. Publish only the service ports that a host user needs to reach. A published port is a network boundary,
not an authentication mechanism.

```diagram
browser ──published port──▶ reverse proxy ──private Compose network──▶ API ──▶ database
          host-facing route                         service-name DNS       named volume
```

### Readiness and health checks

Starting containers in order does not make a dependency ready. A database may have a running process but still be
recovering, applying initialization or refusing connections. A health check can report a meaningful local condition;
the application should also retry transient connections with a bounded delay and a clear error path. Avoid a fixed
sleep that is too short on a slow host and wasteful on a fast one.

Compose can wait for a dependency health condition when configured to do so, but that does not replace runtime
retry logic: dependencies can fail after startup. Choose a health test that checks the capability the next service
actually needs, not just that a PID exists.

### Configuration and persistent state

Keep nonsecret defaults in versioned configuration and provide a nonsecret `.env.example`. Keep local credentials
out of the repository and image build context. Environment variables are convenient but can be visible to the
application process or diagnostic tooling, so use an appropriate secret mechanism when the threat model requires it.
A named volume preserves database files across container replacement; it still needs tested backup and restore.

## Guided practice

Build a Compose stack with API, reverse proxy and a local database. Start the API while the database is stopped,
then restore the database and observe the bounded retry behavior. Restart only the API, recreate the containers,
and verify the same test record remains in the named volume.

## Common mistakes

Publishing database ports unnecessarily, writing passwords in example files, and mistaking
depends_on for guaranteed application readiness.

## Mini-lab

Create one-command local startup for API + NGINX + PostgreSQL with a nonsecret
.env.example.

## Readiness check

From a clean clone, start the stack with the documented command, verify that the API reaches the database by
service name, and confirm that no unneeded database port is published. Recreate the containers and retrieve a test
record from the volume; explain any health check that is failing.

## Recall question

Does starting the database container before the API guarantee that the database is ready to accept application queries?

## Recall explanation

No. Startup order only controls which container is started first. The process may still be initializing or may fail
afterward. Use an application-relevant health check plus bounded connection retry and error handling so the stack can
recover from later dependency changes too.
