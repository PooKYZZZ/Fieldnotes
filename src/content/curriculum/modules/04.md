# Module 04: Networking: from a packet to a web request

## Introduction

Understand how a request gets from one host to another; this is the foundation for debugging
cloud networks and container networking.

## Prerequisites

Basic Linux CLI (Modules 01-03).

## Learning question

If a hostname resolves but a browser cannot open the service, which part of the path should you test next and what evidence would distinguish the causes?

## Learning objectives

- [Addresses, subnets, and routes](#module-04-addresses-subnets-and-routes)
- [DNS and transport protocols](#module-04-dns-and-transport-protocols)
- [Ports, filtering, and application checks](#module-04-ports-filtering-and-application-checks)

## Lesson

### Addresses, subnets, and routes

An IP address identifies a network interface in a particular network. A prefix such as `/24` tells the host which
bits describe the local subnet; the route table chooses where to send traffic for other destinations. The default
gateway is the next hop for routes without a more specific match. Routers forward packets between networks; NAT
may translate addresses at a boundary, but it does not by itself authorize an application request.

```diagram
client process → local route decision → gateway/router → destination network
       │                                     │                  │
       └──── local firewall                  └── NAT/filter     └── host listener
```

An address from `203.0.113.0/24` is reserved for documentation. A command such as `ip route get 203.0.113.8`
shows the route decision your current host would make; it does not send a request or prove that the destination is
reachable.

### DNS and transport protocols

DNS resolves names to records such as addresses. A successful lookup tells you which answer a resolver returned;
it does not create a connection. TCP performs connection setup and provides an ordered byte stream; UDP sends
datagrams without TCP's delivery and ordering guarantees. The application protocol decides what the data means.

### Ports, filtering, and application checks

A port identifies a transport endpoint on a host. A service must bind a compatible address and port, and network
filters must permit the traffic. A successful ping tests an ICMP exchange only. It does not prove TCP port 443 is open,
TLS succeeds, or the application authorizes the user.

Work through evidence in order: resolve the name, inspect the selected IP and route, check the listener, check host
and network filters, then make an application-level request. Keep home-router rules, cloud network rules, host
firewalls and application authentication distinct because each has different logs and owners.

## Guided practice

Use `dig`, `ip route get`, `ss -ltn`, `curl` and (where appropriate) `ping` against a service you own. For each test,
write down what it proves and what it cannot prove. Change one safe lab rule, confirm the expected failure, restore
the rule, then verify the application request succeeds.

## Common mistakes

Assuming a private IP is reachable from the internet, treating DNS errors as firewall errors, and
opening broad inbound ports to “make it work.”

## Mini-lab

Map your own lab network and write a connectivity troubleshooting worksheet with at least four
distinct failure categories.

## Readiness check

Given a resolved hostname and failed HTTPS request, identify the next check using the error observed (route,
timeout, connection refusal, TLS or HTTP response). Explain what a ping result can and cannot establish.

## Recall question

DNS returns an IP address successfully, but `curl https://host/health` times out. Has a TCP connection or healthy application been proven?

## Recall explanation

No. DNS only supplied an address. The client still needs a route, permitted traffic, a listener, successful TCP/TLS
setup and an application response. A timeout narrows the symptom but can originate at multiple network boundaries;
compare route and connection evidence rather than changing DNS first.
