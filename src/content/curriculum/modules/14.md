# Module 14: Terraform and Infrastructure as Code

## Introduction

Make infrastructure explicit, reviewable and reproducible instead of manually rebuilding the same
environment.

## Prerequisites

Basic cloud resources, Docker and Git.

## Learning question

How can you predict an infrastructure change before it runs, and what records let Terraform connect configuration to real resources?

## Learning objectives

- [Desired configuration and plans](#module-14-desired-configuration-and-plans)
- [State, dependencies, and drift](#module-14-state-dependencies-and-drift)
- [Safe lifecycle and collaboration](#module-14-safe-lifecycle-and-collaboration)

## Lesson

Terraform compares a desired configuration against observed and recorded resource state to propose changes. The
plan is a prediction based on the provider and current state, not a substitute for reading the consequences. Review
creates, updates and destroys, especially for resources that hold persistent data.
Terraform state can contain sensitive values and resource identifiers. Keep it out of public repositories; choose a
suitable protected storage backend when collaboration requires shared state. Never edit state casually to “fix” a drift
issue without understanding the consequences.
Start with the official local Docker exercises; only later provision a small Azure resource group and VM. This avoids
spending credits while learning syntax. Terraform manages resource lifecycles, while Ansible is usually better suited
to configuring an operating system inside a provisioned VM.

### Desired configuration and plans

Terraform configuration describes resources and relationships; a provider translates those declarations into API
operations for a platform. `terraform init` installs provider dependencies, `validate` checks configuration shape,
and `plan` compares the desired configuration with the current state and provider observations. Read each planned
create, update and destroy. A plan is a preview, not a reservation: external changes can occur before apply.

```diagram
configuration + provider + state + live observations → plan → human review → apply
                                                          │
                                                          └── unexpected destroy? stop and investigate
```

### State, dependencies, and drift

State maps Terraform resource addresses to real objects and records attributes needed for future operations. It may
contain sensitive values, so protect access and storage. A resource dependency graph controls operation order, while
outputs expose selected values to callers. Drift occurs when live infrastructure changes outside the configuration
or Terraform; compare the plan and decide whether to update configuration or correct the resource.

### Safe lifecycle and collaboration

Start with a local or disposable provider. Keep the lock file, inspect the selected workspace and resource names, and
back up state before any manual intervention. `destroy` can remove real objects and data; verify the plan and target
workspace before approving it. For shared work, use a backend designed for remote state and locking rather than
committing state to Git. Use variables for configuration and a secret mechanism for sensitive inputs.

## Guided practice

Use a local Docker provider or a mock configuration. Run `fmt`, `validate` and `plan`, change one variable, then
review the proposed difference before applying. Make one controlled out-of-band change and inspect the resulting
drift. Destroy only the disposable objects after checking the target workspace and plan.

## Common mistakes

Committing state to Git, assuming apply is always reversible, running destroy on the wrong
workspace or forgetting that data volumes may be deleted.

## Mini-lab

Provision a local Docker resource first, then optionally reproduce one Azure network resource
after reviewing cost.

## Readiness check

Explain how the plan was derived, identify a resource dependency, find an out-of-band change, and reject a plan that
would destroy unintended data. Recreate and clean up only a disposable target while preserving a state backup.

## Recall question

What does `terraform plan` prove, and why must you still review it immediately before `apply`?

## Recall explanation

Plan shows proposed actions based on configuration, state and provider observations at that time; it does not apply
them or guarantee that live infrastructure will remain unchanged. Review creates, updates, deletes, target workspace
and data consequences before applying. Re-plan if important state or configuration has changed.
