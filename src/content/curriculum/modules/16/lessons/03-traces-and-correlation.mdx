<ConceptSection layout="split">
  <div className="learning-concept-copy">
A trace groups spans that represent work across service boundaries. Trace context must be propagated intentionally;
it does not automatically prove causality if identifiers are missing or reused. Start with a request ID in logs and a
few stable metrics, then add distributed tracing when there is a concrete cross-service question to answer.

For example, a log row with `request_id`, `route`, `status` and `duration_ms` can be compared with a time-series
increase in server errors. The ID should be random or opaque and should not encode a user identity or secret.

Read the trace from left to right. The gateway's 180 ms server span contains a remote call whose database
service span starts at 20 ms and lasts 145 ms. A cache operation overlaps part of that call. Adding the two child
durations would count overlapping time twice. The database span explains where most elapsed time is represented,
while a database log or a latency series can help determine whether that time was query work, queuing, or a wider
pattern. The example omits the gateway's client span for the remote call. See
[OpenTelemetry's span relationships](https://opentelemetry.io/docs/concepts/signals/traces/#spans).
