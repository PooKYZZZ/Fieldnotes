# Module 24: DevSecOps integration and architecture judgment

## Introduction

Combine delivery, security, observability and recovery into a defendable architecture without piling
on tools needlessly.

## Prerequisites

Most previous modules; revisit any weak foundation.

## Learning question

Can you trace one change from source commit to safe deployment, observe its behavior, and explain how you would recover without adding tools the system does not need?

## Learning objectives

- [Risk-based design and boundaries](#module-24-risk-based-design-and-boundaries)
- [Trace a complete release](#module-24-trace-a-complete-release)
- [Architecture decisions and handover](#module-24-architecture-decisions-and-handover)

## Lesson

DevSecOps is the integration of security practices into how software is developed, deployed and operated; it is not
simply a vulnerability scanner added at the end of a pipeline. Build protections into changes at the earliest stage
where they are effective and practical.
Select tools based on a concrete operational question. A small FastAPI service may need GitHub Actions, Docker,
Ansible and a single Azure VM; adding managed Kubernetes and multiple cloud vendors without user or reliability
needs increases complexity. Explain why an omitted tool is not necessary.
For a complete system, trace one release from a Git commit through tests, build and artifact identity, approved
deployment, health verification, monitoring, incident handling and recovery. Describe the trust boundaries, who has
privileged access and what an attacker or careless operator could change. This technical narrative is portfolio
evidence of judgment rather than a stack of product logos.

### Risk-based design and boundaries

Begin with the user need and likely failure or abuse cases. Map identities, data, build inputs and network paths;
then choose controls that address those risks. A small service might need a test pipeline, a pinned container image,
restricted deployment identity, backups and a useful health signal. Add another platform only when it solves a
real requirement such as scale, isolation or availability that the current design cannot meet.

### Trace a complete release

Follow one change end to end: commit and review, tests, build inputs, artifact digest, deployment approval, runtime
configuration, health check, telemetry, incident path and recovery. At each step record who can act, what evidence
is produced and what could be changed without detection.

```diagram
reviewed commit → CI evidence → identified artifact → approved deploy → observed service
        │                │                  │                   │             │
      owner           test logs          digest/trust        least privilege  alert/runbook
```

### Architecture decisions and handover

An architecture decision record (ADR) captures context, considered choices, the selected option, consequences and
review triggers. State operational assumptions, dependencies, cost boundaries, backup/restore procedures and
rollback limits. The handover is complete when another learner can set up the system, identify its health, diagnose
a controlled failure and clean up without undocumented access.

Security gates, reliability targets and recovery tests should be proportional to impact. A passing scanner or green
pipeline contributes evidence; it does not replace a threat model or operational demonstration.

## Guided practice

Audit your capstone architecture using an explicit rubric: functionality, reliability, security, maintainability,
cost and independent explainability.

## Common mistakes

Treating compliance labels as proof, automating destructive steps without review, and losing
operational visibility across too many services.

## Mini-lab

Produce a concise architecture decision record and a complete operational demonstration for
your capstone.

## Readiness check

Defend one important tradeoff, reproduce a release safely and demonstrate recovery
from a controlled failure.

## Recall question

What evidence would let another learner verify a release from source to runtime, and which single green check cannot establish all of it?

## Recall explanation

Useful evidence includes a reviewed commit, test results, build inputs, artifact identity, deployment record, runtime
health and telemetry, and a tested recovery path. No single green CI check, scanner result or health endpoint proves
the whole chain. State what each check covers and what remains unverified.
