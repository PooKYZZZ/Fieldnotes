# Module 20: Secrets, identities and secure configuration

## Introduction

Keep credentials and deployment authority out of source code, images and accidental log output.

## Prerequisites

Modules 10-15, especially CI and cloud permissions.

## Learning question

How can a deployment prove who it is and receive only the access it needs without storing a long-lived cloud password in the repository?

## Learning objectives

- [Configuration and secret lifecycle](#module-20-configuration-and-secret-lifecycle)
- [Identity, authentication, and authorization](#module-20-identity-authentication-and-authorization)
- [Federated deployment identity](#module-20-federated-deployment-identity)

## Lesson

A secret is any value whose disclosure would grant access or expose protected information. Environment variables
can be convenient configuration carriers but are not automatically secret storage; values may appear in process
environments, debug output or CI logs. Rotate and revoke credentials after suspected exposure.
Long-lived cloud keys in GitHub Actions create a difficult maintenance and leakage risk. When supported, OIDC
federated authentication lets a short-lived workflow identity exchange a trusted token for scoped cloud access.
Restrict which repositories, branches and environments can request that identity.
Treat identity and authorization separately: authentication proves who the caller is, while authorization limits what it
may do. Document owners, scopes and expiration conditions. Test failure with insufficient permission before raising
a role to owner; the narrower change is usually safer.

### Configuration and secret lifecycle

Configuration describes how an application behaves in an environment; a secret is configuration whose disclosure
could grant access or reveal protected data. Keep ordinary defaults in a documented template and put real
credentials in an appropriate secret store. Environment variables are convenient but can appear in process
inspection, crash reports or debug output. Avoid printing them and never bake them into an image layer.

A secret has an owner, scope, storage location, expiration or rotation path, and revocation procedure. If it is
published, remove its access by rotating or revoking it; deleting the visible file does not remove it from Git
history or copies already fetched.

### Identity, authentication, and authorization

Authentication establishes which identity is making a request; authorization decides what that identity may do.
Credentials are proof material such as a key or token, while an identity is the principal to which policies apply.
An access review should record principal, resource, permission, scope and expiry. Test a deliberately insufficient
permission and grant only the missing action rather than assigning Owner to make an error disappear.

### Federated deployment identity

Where the cloud and CI provider support it, OpenID Connect federation can exchange a short-lived workflow identity
token for cloud credentials. Trust conditions should restrict the repository, branch, environment or workflow that
may request the identity. Federation reduces the need to store a long-lived cloud key, but it does not make a
workflow safe by itself: protect workflow edits, apply least privilege and audit each deployment.

## Guided practice

Use a fake, nonfunctional token in a disposable test. Trigger an authentication failure and verify that logs show a
redacted reason without the token value. Review a workflow permission block and, if available in your lab, map the
OIDC trust conditions to one approved branch and environment.

## Common mistakes

Using root or owner roles for convenience, leaking secrets in build args, and forgetting to revoke
credentials once committed.

## Mini-lab

Prepare a nonsecret configuration template, credential inventory and GitHub Actions security
review.

## Readiness check

For each test credential, name its owner, location, scope, rotation and revocation path. Show a safe failed
authentication without value disclosure, and explain the difference between identity, credential, authentication
and authorization.

## Recall question

If a secret is removed from the latest commit after it was pushed, is the credential safe to keep using?

## Recall explanation

No. The value may remain in repository history, clones, logs, caches or external systems. Revoke or rotate the
credential first, investigate where it was exposed, and then remove it from current files and history as appropriate.
The credential lifecycle matters more than the visible file change.
