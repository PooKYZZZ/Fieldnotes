# Module 18: Kubernetes architecture, workloads and operations

## Introduction

Understand orchestration without assuming Kubernetes is required for every small application.

## Prerequisites

Linux, networking, Docker and Compose (01-09).

## Learning question

How does Kubernetes keep a requested application available when Pods are replaceable, and what evidence shows a rollout is safe?

## Learning objectives

- [Control plane and desired state](#module-18-control-plane-and-desired-state)
- [Pods, Deployments, and Services](#module-18-pods-deployments-and-services)
- [Probes, rollout, and resources](#module-18-probes-rollout-and-resources)

## Lesson

Kubernetes declares a desired workload state and controllers continuously reconcile actual state toward it. A
Deployment describes replicas and update behavior; Pods are the scheduling unit and can be replaced at any time.
Design your app so an instance can restart without losing essential state.
A Service gives a stable discovery and routing abstraction for changing Pods. It is not the same as a container port or
an external load balancer. Namespaces group resources but are not automatically a strong security boundary.
Kubernetes adds significant operational complexity: API authentication, scheduling, storage, networking and
upgrade maintenance. Learn it using a local cluster such as kind or minikube after you can deploy and debug the
same application with Compose. Managed Kubernetes in the cloud is unnecessary for the initial learning objective.
Readiness probes decide whether an instance receives service traffic; liveness probes can restart it when a defined
unrecoverable condition occurs. A liveness check that is too strict may create restart loops during temporary load.
Requests inform scheduling, while limits constrain resource usage; tune them using observed behavior rather than
arbitrary tiny values.
A rolling update reduces disruption when workloads are sufficiently replicated and their readiness conditions are
correct. It does not guarantee zero downtime for single-replica services or incompatible database changes. Record
rollout status, failures and rollback steps.
Persistent volumes introduce storage lifecycle decisions that do not disappear because the application is
containerized. Limit RBAC privileges, protect sensitive Kubernetes objects and avoid exposing the cluster dashboard
or API broadly. Cluster upgrades and node security are major future topics, not prerequisites for your first local
deployment.

### Control plane and desired state

The API server stores the declared objects; controllers compare desired state with observed state and take action to
close the gap. A Deployment creates and manages ReplicaSets, which maintain the requested number of Pods. A Pod
can be rescheduled or replaced, so do not depend on its IP or local writable layer as durable application state.

```diagram
Deployment spec → ReplicaSet → Pod replicas ← Service selector
       │              │           │                 │
 desired count   reconcile   replaceable      stable DNS/virtual IP
```

### Pods, Deployments, and Services

A Pod groups one or more tightly coupled containers that share network identity and volumes. A Deployment manages
replica count and rollout history. A Service selects matching Pods and provides a stable endpoint while Pod
addresses change. Check labels and selectors together; a Service with no ready endpoints may be a selector or
readiness problem rather than a network outage.

### Probes, rollout, and resources

Readiness decides whether a container should receive Service traffic; it does not restart the container. Liveness
can restart a container after a defined failure. A startup probe gives a slow-starting application time before
liveness checks begin. Poorly chosen probes can remove healthy Pods or create restart loops. Resource requests inform
scheduling; limits constrain use. A rollout is safe only when enough replicas are ready and compatible with the
current data and dependencies.

## Guided practice

Deploy an API locally; scale replicas, delete one Pod, inspect replacement behavior and test service
discovery. Also: Push a broken image tag or bad readiness route in a lab; inspect rollout status; roll back to a working
revision.

## Common mistakes

Mapping one Pod to one virtual machine, depending on Pod IPs staying fixed, or treating a local
Kubernetes lab as production-ready. Using liveness probes for dependency readiness, omitting resource requests, or
copying wide-open example RBAC to real clusters.

## Recall question

What does a readiness probe do that a liveness probe does not, and why should the two checks not always be identical?

## Recall explanation

Readiness controls whether the Pod should receive Service traffic. Liveness determines whether Kubernetes should
restart a container. A temporary dependency issue may make a Pod unready without making its process unrecoverable;
using that condition as liveness can cause needless restarts. Choose each check for the failure it should detect.
