# Module 17: Monitoring, dashboards and alert design

## Introduction

Detect failures proactively and make dashboards that support decisions rather than just display
attractive charts.

## Prerequisites

Module 16 observability.

## Learning question

How can a dashboard and alert tell an operator that users are affected and what action to take, instead of merely showing a changing graph?

## Learning objectives

- [From scrape to decision](#module-17-from-scrape-to-decision)
- [Service and user health](#module-17-service-and-user-health)
- [Actionable alerts and runbooks](#module-17-actionable-alerts-and-runbooks)

## Lesson

Prometheus scrapes metrics endpoints on a schedule and stores time-series observations. A scraper being reachable
does not guarantee the application is correctly serving requests, so include synthetic or application-level health
checks.
Dashboards should show what a responder needs: service availability, recent deployments, latency, errors and host
saturation. A graph without units or a clear question can hide a problem rather than reveal it. Alert on conditions
that need action; otherwise notifications become noise and are ignored.
An alert should identify the affected service, symptom, expected action and link to a runbook. Test alert recovery as
well as firing, and distinguish an infrastructure symptom from customer impact. Start locally with Prometheus and
Grafana; do not pay for a managed telemetry platform simply to build your first dashboard.

### From scrape to decision

Prometheus periodically scrapes a configured endpoint and stores time-series samples. Grafana queries those series
to render panels; alert rules evaluate conditions over time and can notify an operator. A missing scrape is a
monitoring failure, not proof that the target is healthy. Show the scrape target state beside the application-level
signal so missing data is visible.

```diagram
service /metrics → Prometheus scrape → time series → dashboard panel / alert rule
        │                 │                │                │
   instrumentation   target health     query/units      responder action
```

### Service and user health

Host CPU and memory can explain capacity pressure but do not directly establish that a user journey works. A process
can be up while returning incorrect data. Pair infrastructure signals with application success, error and latency
measurements. Define what a successful request means and label panels with units, time windows and service names.

### Actionable alerts and runbooks

Alert on sustained conditions where someone can take an action. A useful alert says which service is affected, the
observed symptom, why it matters, and where to investigate. A threshold should be based on a user or operational
objective, not chosen solely because a chart looks tidy. Test that the alert fires and clears, and include a concise
runbook with verification and escalation steps. Too many low-value alerts train people to ignore them.

## Guided practice

Stop a service in a controlled lab; watch scrape targets, error rates and an alert rule; note how long
detection takes.

## Common mistakes

Alerting on every metric spike, overlooking missing telemetry, and treating dashboards as
substitutes for incident procedures.

## Mini-lab

Build a local service dashboard with one actionable alert and a concise response runbook.

## Readiness check

Prove the alert fires and clears during a controlled incident; explain the difference
between service and host health.

## Recall question

If Prometheus stops receiving a target's metrics, does a dashboard value frozen at its last sample mean the service is healthy?

## Recall explanation

No. A stale value is not current evidence. Display target or data freshness and treat missing telemetry as its own
condition. Use an independent application check or another signal to determine whether the service is serving users.
