# Module 16: Logs, metrics and traces

## Introduction

Build the mental tools required to observe a system rather than guessing why it behaves badly.

## Prerequisites

Running service; Python and basic networking.

## Learning question

When one request fails, how can logs, metrics, and traces answer different parts of the investigation without collecting sensitive data?

## Learning objectives

- [Logs and request context](#module-16-logs-and-request-context)
- [Metrics and distributions](#module-16-metrics-and-distributions)
- [Traces and correlation](#module-16-traces-and-correlation)

## Lesson

Logs are records of events; metrics summarize measurements over time; traces connect work performed across
service boundaries. They answer different questions. A log may identify the error for one request, while a metric
reveals that a failure rate increased after a deployment.
Add request IDs and meaningful status fields to application logs, but avoid recording passwords, tokens and
personal data. Metrics such as request rate, error rate and latency can indicate customer impact. High-cardinality
labels such as unique user IDs can make time-series systems expensive and hard to operate.
A distributed trace represents causal relationships among operations, but instrumentation itself has cost and
complexity. For your initial lab, prefer clean JSON logs and a few stable metrics before adopting a full tracing stack.
Explain the trade-off rather than adding agents blindly.

### Logs and request context

A structured log records an event with fields such as time, severity, service, operation and outcome. Use consistent
timestamps and a request or trace identifier so related events can be found across services. Do not log passwords,
access tokens, full request bodies or other sensitive values merely because they are available. Logs answer what a
specific operation reported, but one noisy error does not show how widespread the problem is.

### Metrics and distributions

Metrics summarize numerical behavior over time. A counter accumulates events such as total requests; a gauge can
rise and fall, such as current queue depth; a histogram groups observations such as request duration into buckets.
Use stable labels such as route template and status class. Unique request IDs, user IDs or raw URLs create
high-cardinality series and can overwhelm a time-series database.

| Signal | Question it helps answer |
| --- | --- |
| Structured error log | What did this request report? |
| Request/error counter | Is the issue isolated or increasing? |
| Latency histogram | Is the tail of response time getting worse? |
| Trace spans | Which service or operation consumed the time? |

### Traces and correlation

A trace groups spans that represent work across service boundaries. Trace context must be propagated intentionally;
it does not automatically prove causality if identifiers are missing or reused. Start with a request ID in logs and a
few stable metrics, then add distributed tracing when there is a concrete cross-service question to answer.

For example, a log row with `request_id`, `route`, `status` and `duration_ms` can be compared with a time-series
increase in server errors. The ID should be random or opaque and should not encode a user identity or secret.

## Guided practice

Generate a successful and a controlled failing request. Record structured fields without bodies or credentials,
compare the error counter and latency distribution, and find the corresponding log using an opaque request ID.
Inspect the metrics endpoint and identify any label that could grow once per request.

## Common mistakes

Calling uptime a sufficient reliability metric, ignoring time zones and clock skew, or logging secrets
and request bodies indiscriminately.

## Mini-lab

Instrument the Status API with structured logs and request counters, then create a short
troubleshooting note.

## Readiness check

Find one failed request, explain its error reason from logs, and use a metric to decide whether the failure is
isolated or widespread. Identify whether a trace is needed to answer any remaining cross-service question.

## Recall question

Which signal is best for finding the details of one failed request, and which is better for seeing whether failures are increasing over time?

## Recall explanation

A structured log is usually best for the event details of one request. A counter or rate derived from metrics is better
for the trend and scope over time. A trace can help locate where work stalled across services. Combine signals using
consistent context, while avoiding sensitive fields and unbounded metric labels.
