# Module 22: Site reliability engineering and service objectives

## Introduction

Practice balancing availability, feature delivery and operational work with measurements and
realistic service expectations.

## Prerequisites

Monitoring, deployments and operating a service.

## Learning question

How do you measure reliability from the user's point of view, and what should change when observed performance falls short of the goal?

## Learning objectives

- [Define a useful SLI and SLO](#module-22-define-a-useful-sli-and-slo)
- [Calculate and interpret an error budget](#module-22-calculate-and-interpret-an-error-budget)
- [Toil and learning from incidents](#module-22-toil-and-learning-from-incidents)

## Lesson

An SLI is a measurement such as successful requests divided by total eligible requests; an SLO is a target for that
measurement over a specified window. Different systems value different user journeys, so start with an observable
endpoint and an explicit definition of what success means.
An error budget describes tolerated unreliability relative to an SLO. For a hobby lab, avoid copying a stringent
production target that you cannot measure or support; choose a learning objective you can test and explain.
Reliability is not only uptime: correct data, recovery and maintainability also matter.
Toil is repetitive operational work that scales with service demand and requires human attention. Automation helps
when it removes a repeatable source of toil without introducing hidden failure modes. Postmortems should explain
contributing conditions and improvement actions, not assign blame or invent certainty.

### Define a useful SLI and SLO

An SLI is a measurement; an SLO is a target for that measurement over a named window. Define eligibility and success
before calculating a ratio. For an API, an eligible request might be one that reaches a particular route, while
success might require an expected status and valid response. Excluding errors without a defensible rule can make the
number look better without improving user experience.

### Calculate and interpret an error budget

If 98 of 100 eligible requests succeed, the observed ratio is 98%. With a 99% target over that same sample, the
allowable unsuccessful fraction is 1%, or one request; two failures exceed that illustrative budget. A tiny sample
is highly variable, so do not claim production reliability from it. State the data source, window, exclusions and
limitations alongside the result.

```diagram
eligible events ──classify──▶ successful / eligible = SLI
                                      │
                                  compare with SLO
                                      │
                       remaining allowed failures = budget
```

Use an error-budget policy as a decision aid, not a universal rule. A hobby lab may choose to pause risky changes
after repeated failures, but it should match the system's impact and the quality of its measurements.

### Toil and learning from incidents

Toil is recurring operational work that consumes attention without creating lasting service value. Automate it only
after understanding its failure modes and measuring whether the automation helps. Review incidents without blame:
describe the timeline, contributing conditions, detection gaps and actions that reduce recurrence. Reliability also
includes correct data, recoverability and maintainability, not only uptime.

## Guided practice

Define one SLI from a sample log set, write what counts as an eligible and successful request, calculate the ratio,
and compare it with a clearly labeled lab SLO. Propose a small policy that responds to repeated failure without
pretending the sample predicts production behavior.

## Common mistakes

Chasing 100% uptime, hiding incidents, or treating a single availability metric as proof of user
satisfaction.

## Mini-lab

Write a service-level objective page, an incident classification and a small automation
opportunity assessment.

## Readiness check

Show your data source, measurement window, inclusion rules and calculation. Explain what the SLO helps decide and
when the sample size or missing data makes its result misleading.

## Recall question

What extra information is needed to interpret an SLI percentage besides its numerator and denominator?

## Recall explanation

You need to know what counts as an eligible event and a success, the measurement window, exclusions and data source.
Without those, two percentages may measure different user experiences. Sample size and missing telemetry also
limit how confidently the result can guide a release decision.
