# Module 07: Git, collaboration and technical documentation

## Introduction

Turn experiments into a history you can reproduce and discuss with teammates or future
employers.

## Prerequisites

Comfort with files and the shell.

## Learning question

How can you prove exactly which change is being shared, what review evidence supports it, and how another person can reproduce the result?

## Learning objectives

- [The working tree, index, and commits](#module-07-the-working-tree-index-and-commits)
- [Branches, remotes, and review](#module-07-branches-remotes-and-review)
- [Reproducible documentation](#module-07-reproducible-documentation)

## Lesson

Git tracks committed snapshots and their history; the working directory, staging area and local repository are
distinct. A remote is a copy of repository history, not a magical backup of every local file. Worktrees and stashes add
additional state that you must inspect before deleting or merging anything.
Good commits isolate a coherent change; reviews should discuss behavior, tests and risk rather than only
formatting. A branch is a pointer to a line of commits, not a separate folder by definition. Learn to inspect
differences and history before resolving a conflict.
Documentation should help a person who was not present: state prerequisites, setup steps, configuration sources,
expected behavior and recovery steps. Keep secrets and machine-specific files out of version control. A short
reliable runbook is more useful than a large README that nobody can execute.

### The working tree, index, and commits

Git keeps three states that are easy to confuse: files in the working tree, selected changes in the index, and
committed snapshots in repository history. `git diff` shows unstaged edits; `git diff --cached` shows what the next
commit will contain. Review both before committing, then inspect the saved commit with `git show`.

```diagram
edit files → inspect diff → stage selected paths → inspect staged diff → commit
    │                                                          │
    └── working tree                                            └── repository history
```

Untracked files are not in a commit. A stash is local working-state storage; pushing a branch does not upload a
stash. A commit is not a backup until it is pushed to a remote you trust.

### Branches, remotes, and review

A branch name points to a commit and moves as new commits are added. A remote-tracking branch such as
`origin/main` is your local record of a remote branch, updated by fetch. Review a change with `git log`,
`git diff base...HEAD` and relevant tests instead of assuming that similarly named branches contain the same files.

A good pull request describes behavior, risk, test evidence and operational considerations. Resolve conflicts by
understanding both versions; choosing one side blindly can delete correct functionality.

### Reproducible documentation

Write setup instructions from a clean checkout: prerequisites, commands, configuration source, expected output and
cleanup. Include a safe failure-recovery path. Use example values rather than credentials or private environment
files, and state limitations so readers do not mistake a local demonstration for production evidence.

## Guided practice

Create a feature branch, make two small edits, stage only one, and compare `git diff` with `git diff --cached`.
Resolve a harmless text conflict in a disposable repository and explain the final result before creating a reviewable
commit for Activity A07.

## Common mistakes

Committing .env secrets, force-pushing shared history without coordination, or assuming a git
stash has safely transferred into another branch.

## Mini-lab

Publish a lab repository with a clear README, setup, limitations, security notes and changelog.

## Readiness check

Explain the difference between working-tree, staged, committed and pushed changes. Recover from a harmless
conflict and let another person reproduce the lab from a clean checkout using only the README.

## Recall question

Does `git push` upload uncommitted edits or a stash, and which command helps inspect the next commit before creating it?

## Recall explanation

No. Push transfers commits and their reachable history; uncommitted edits and local stashes remain in the local
repository. `git diff --cached` reviews the staged content that will enter the next commit. Use `git status` as well
to find untracked files that are not included.
