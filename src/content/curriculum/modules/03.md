# Module 03: Linux users, processes and service management

## Introduction

Move from using Linux to administering a service: identities, permissions, lifecycle, logging and
troubleshooting.

## Prerequisites

Module 02: safe command-line use.

## Learning question

When a web service is unavailable, how can you tell whether the problem is its identity, process, service manager, log, or network listener?

## Learning objectives

- [Identity and file permissions](#module-03-identity-and-file-permissions)
- [Process and service lifecycle](#module-03-process-and-service-lifecycle)
- [Logs and fault isolation](#module-03-logs-and-fault-isolation)
- [SSH and safe administration](#module-03-ssh-and-safe-administration)

## Lesson

### Identity and file permissions

Linux processes run with a user ID and group IDs. For a file, owner, group and other permission bits control read,
write and execute access. On a directory, execute means a process may traverse the path; listing names also
requires read permission. A service account limits what a compromised or malfunctioning service can change.
`sudo` elevates a command temporarily, so use it only for the operation that needs administrative rights.

### Process and service lifecycle

`systemd` is a system and service manager on many Linux distributions. A unit describes how to start, stop and
supervise a process. `enabled` means it is configured to start during boot; `active` describes its present state.
Neither label proves the application is answering correctly.

```diagram
systemd starts unit ──▶ service account process ──▶ listening socket
         │                         │                         │
         └── restart policy        └── exit status/logs      └── client request
```

Signals request a process action: `SIGTERM` allows a program to shut down cleanly, while `SIGKILL` stops it
immediately and gives it no cleanup opportunity. Prefer the service manager's stop action over killing arbitrary
PIDs; the manager owns the lifecycle it started.

### Logs and fault isolation

When a service fails, compare the unit state, recent journal, process and listening socket. For example,
`systemctl status status-api.service` shows the unit state, `journalctl -u status-api.service --since "10 min ago"`
narrows the log window, and `ss -ltn` shows TCP listeners. Then request the local health endpoint. This moves from
process evidence toward application behavior without treating a restart as a diagnosis.

### SSH and safe administration

An SSH connection depends on several independent checks: network reachability, server policy, user authentication,
and permission to use the requested key or file. Change server settings only with a second session available and a
known rollback path. Apply OS updates through the distribution's package manager and verify service health after
changes.

## Guided practice

Create a non-root service account in a disposable VM, inspect file and directory permissions, and intentionally
start a test service with an invalid path. Compare unit status, journal output and listener state; correct one cause
and verify the local endpoint before moving on to Activity A03.

## Common mistakes

Changing sshd settings before testing another active session, running network-facing software as
root, and assuming restart loops fix the underlying failure.

## Mini-lab

Create a minimal systemd unit for a test web service with restart policy and a written rollback
procedure.

## Readiness check

Explain a permission denial using the process identity and every directory in the path. Start and stop a test service,
identify one failure from its log and demonstrate an SSH connection using a key without weakening server policy.

## Recall question

What is the difference between a systemd service being enabled, active, and healthy to a user?

## Recall explanation

Enabled describes whether the service is configured to start automatically at boot. Active describes the unit's
current manager state. User-visible health depends on the application actually completing a meaningful request.
Check the unit, its logs and a functional endpoint; do not treat one state label as proof of all three.
