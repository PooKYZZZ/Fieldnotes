# Module 01: How computers and operating systems work

## Introduction

Build a mental model of what happens from power-on to a running service. This makes later Linux,
Docker and cloud failures easier to interpret.

## Prerequisites

None; curiosity and a PC are enough.

## Learning question

What changes inside the operating system between opening an application and having it read a file or serve a request?

## Lesson

### From program to process

A program is a set of instructions and data stored as a file. Starting it asks the operating system to create a
process: a running instance with an identifier, virtual address space, open resources and one or more threads. The
loader maps executable sections into memory, prepares the initial process state and transfers control to the program.
The scheduler chooses when runnable threads get CPU time; a process can exist without currently executing.

Threads in one process share its address space and many process resources, while each thread has its own stack and
execution state. Shared memory makes communication fast, but concurrent writes need coordination. A blocked thread
waiting for a disk or network result is not necessarily consuming CPU.

### User space and the kernel

Ordinary applications run in user space with limited privilege. When code needs an operation such as reading a file,
sending network data or creating a process, it crosses a system-call boundary. The kernel validates the request and
mediates access to shared resources. This boundary is why an application cannot safely treat a disk or network card
as ordinary memory.

```diagram
Program file on disk
       ↓ loader creates a process
User-space process: PID, memory, threads
       ↓ system call (checked request)
Kernel: permissions, scheduling, drivers
       ↓
File system, network socket, or device
```

### Memory, storage, and failures

RAM holds active code and data and is normally lost when power is removed. Persistent storage keeps files across
restarts, but a write may still be buffered or fail before it is durable. A process using high CPU is doing work; a
process using much memory may be waiting or idle. These are different measurements and need different remedies.

When a service stops, separate an application exception, a signal or resource-limit termination, a permission error,
and a host-level failure. Start with evidence: process state and exit code, recent logs, memory pressure, filesystem
space, then the service's network path. The same reasoning works on a laptop, VM and cloud host.

| Observation | What it suggests | Next evidence |
| --- | --- | --- |
| CPU stays high | Threads are doing work or repeatedly retrying | Per-process CPU and application logs |
| Memory rises, then the process disappears | Possible memory pressure or configured limit | Kernel/service logs and memory limit |
| Process runs but request times out | It may be blocked or unreachable | Socket state, route and application logs |

### Boot and filesystems

On a typical Linux system using systemd, firmware initializes hardware and hands off to a bootloader; some systems
can load the kernel directly. The bootloader loads the kernel and an initramfs. After the root filesystem is found,
the system manager mounts remaining filesystems and starts configured services. Linux presents mounted filesystems
through one directory tree, so a directory can contain data backed by a different device. Exact boot steps vary
with firmware, distribution, and init system. Module 02 develops filesystem paths and mounts further.

### Virtual machines and containers

A virtual machine emulates hardware and runs a guest kernel, so it can isolate a different operating system. A
container isolates processes and resources but shares the host kernel. That makes containers lighter to start, while
kernel-level experiments belong in a disposable VM. Neither boundary removes the need to restrict privileges and
protect persistent data.

### Trace one simple failure

Suppose a process is visible but cannot read `/var/log/service.log`. The process exists, so startup succeeded. Next
check the file's owner and mode, the directory traversal permissions, and the service identity. A filesystem error
reported by the application is evidence of a permission or path issue; restarting the VM would not explain it.

Draw a diagram from application to syscall to kernel and disk. Open a process monitor; find a running

## Common mistakes

Confusing CPU saturation with high memory usage, assuming a VM and a container are identical,
or treating every unresponsive app as a network failure.

Without following the diagram, explain how a program becomes a process, why a process can wait without using CPU,
what survives a reboot, and what must be checked before a process reads a file.

## Recall question

If an application is running but waiting for a file read, what does the kernel do, and why might the process use little CPU?

## Recall explanation

The application requests the read through a system call. The kernel checks access and coordinates the filesystem and
storage device. While the operation waits for data, the thread can be blocked and another runnable thread can use the
CPU. The process still exists; it is simply not executing during that wait.
