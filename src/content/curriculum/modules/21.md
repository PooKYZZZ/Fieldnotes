# Module 21: Software supply chain and secure CI/CD

## Introduction

Understand how dependency, build and artifact compromise can undermine otherwise correct
source code.

## Prerequisites

Docker, CI/CD, secure identity and dependency basics.

## Learning question

How can you trace what went into a released artifact and decide what evidence supports trusting it?

## Learning objectives

- [Build inputs and dependency review](#module-21-build-inputs-and-dependency-review)
- [Artifact identity and provenance](#module-21-artifact-identity-and-provenance)
- [Security gates and limits](#module-21-security-gates-and-limits)

## Lesson

A build consumes more than your own code: package dependencies, base images, action dependencies, compiler
toolchains and configuration can all change its behavior. Record versions, review dependency updates and restrict
who can alter the pipeline.
Vulnerability scanners identify known problems within their coverage; results require triage. They do not prove that
the build process is trustworthy or that the running application is safe. A software bill of materials describes known
components but is not a substitute for testing and patching.
The NIST SSDF provides practices to prepare, protect software, produce well-secured software and respond to
vulnerabilities. OWASP CI/CD guidance emphasizes protecting pipeline access, secrets, dependencies and artifacts.
Use these as a basis for a small practical checklist rather than claiming full compliance with a complex standard.

### Build inputs and dependency review

The artifact can include your code, package dependencies, base images, build tools, workflow actions and generated
configuration. A lock file records resolved versions for supported package managers; review updates and test them
instead of blindly accepting every bot change. Pinning improves repeatability but does not make an old dependency
safe, so combine identity with timely updates and vulnerability review.

### Artifact identity and provenance

An SBOM lists known software components and versions. Provenance records how an artifact was produced and which
inputs or workflow created it. A signature or attestation can help verify origin and integrity when the signing
identity and verification policy are trustworthy. These records improve traceability; they do not prove the code is
correct or free of vulnerabilities.

```diagram
source + dependencies + base image + workflow → build → image digest + SBOM/provenance
                                                            │
                                             verify identity before promotion
```

### Security gates and limits

Use a small set of gates with clear ownership: tests, dependency review, image scanning and permission checks.
Define what blocks a release, how a finding is triaged, and how a false positive is documented. A scanner covers
known patterns and databases; it may miss new vulnerabilities, malicious maintainers, unsafe behavior or a
compromised workflow. Separate untrusted pull-request testing from deployment credentials and production writes.

## Guided practice

Add dependency and image scanning to a test pipeline. Record the source revision and resulting image digest, inspect
one finding, and document how it would be triaged. Add an intentionally failing gate in a throwaway branch and
verify that release promotion is blocked.

## Common mistakes

Pinning nothing, giving an untrusted pull request deployment keys, and interpreting a scanner exit
code as a comprehensive security audit.

## Mini-lab

Create a secure pipeline that tests, scans, versions and records a deployable container artifact.

## Readiness check

Show that a failing security gate blocks promotion, trace the image digest to its source revision, and explain what
the selected scanner and SBOM cannot establish about runtime safety.

## Recall question

Does generating an SBOM and passing a vulnerability scan prove that a container is safe to deploy?

## Recall explanation

No. An SBOM improves component visibility and a scan checks known issues within its coverage. Neither proves
artifact provenance, workflow integrity, correct application behavior or absence of unknown vulnerabilities. Use
them as separate evidence alongside tests, permissions, artifact verification and operational checks.
