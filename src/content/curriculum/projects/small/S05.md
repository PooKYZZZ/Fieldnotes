# Backup verifier

## Scenario

A small internal tool says “backup complete,” but nobody has demonstrated that its copy can be opened or that important records survived. Build a verifier that snapshots a disposable SQLite dataset, restores it to a new path, checks database integrity, and compares known application records.

## Why this matters

A backup job succeeding is not the same as a recoverable service. Recovery confidence comes from testing the restore path, comparing expected data, and recording how long the check took. The exercise uses synthetic data so it cannot overwrite or expose a real database.

## Learning objectives

- Distinguish backup creation, file integrity, and application-level recovery.
- Use SQLite's online backup support rather than copying a live database file blindly.
- Verify a restored database in a separate destination against known records.
- Document retention, failure behavior, and the limits of a single local snapshot.

## Prerequisites and setup

Use Python's built-in `sqlite3` module and a fresh temporary directory. Create a tiny fixture schema with a few deterministic rows and one optional index. The project must refuse paths outside its disposable workspace unless the learner explicitly chooses a test destination; never point it at Fieldnotes or another live application database.

## Requirements and boundaries

- Create the source database from a fixture during setup, then back it up to a new file using the SQLite backup API exposed by Python.
- Restore or copy the backup to a second, fresh path; open that destination independently and run `PRAGMA integrity_check`.
- Compare table names, row counts, and selected deterministic rows or hashes; do not compare only file size.
- Make destination collisions explicit. Do not silently overwrite an existing file or delete a path supplied by the user.
- Report separate outcomes for backup creation, database integrity, expected-record comparison, and cleanup.
- Do not use real user data, cloud storage, encryption keys, or production retention policies in the baseline.

## Architecture and decisions

`synthetic source → consistent SQLite backup → fresh restore target → integrity check + logical comparison → recovery report`

Keep source and restore paths separate and make both visible in the report. Decide how to select representative records, how to handle schema differences, and whether the project should compare a full fixture or a bounded sample. A successful integrity check says the database structure is consistent; it does not prove that the application can use every restored record correctly.

## Build milestones

### S05.1 — Create the recovery fixture

**Purpose:** Establish a known source of truth before testing a backup.

**Work:** Build a disposable database with two or three tables, a few deterministic records, a nullable field, and one index. Define a manifest of expected counts and selected rows. Make the fixture generator repeatable and safe to rerun in a new temporary directory.

**Checkpoint:** A second run generates the same logical records, and the project never opens a path outside its test workspace.

**Evidence:** Commit the fixture generator, schema, manifest, and expected query results.

#### Hint 1 — Make the manifest independent

Write the expected row counts and selected values from the fixture definition before creating a backup. After restoration, query the new destination and compare it with that manifest; comparing the restored database only with the source file size would miss logical changes.

### S05.2 — Snapshot and restore to a fresh path

**Purpose:** Demonstrate a usable recovery copy instead of a file-exists check.

**Work:** Use `sqlite3.Connection.backup()` to create the snapshot, then restore or copy it into a second, non-existing target database. Handle connection closure and exceptions, and refuse to clobber a pre-existing destination.

**Checkpoint:** Both source and restored database can be opened independently; the restore path is not the source path.

**Evidence:** Record the command, separate source and restore paths, and completion timestamps.

### S05.3 — Verify integrity and logical contents

**Purpose:** Catch corruption and incomplete recovery with independent checks.

**Work:** Run `PRAGMA integrity_check` on the restored database, query the expected tables, compare counts and selected rows, and deliberately alter a disposable restored fixture to prove the logical comparison detects a mismatch. Do not corrupt the source or an unrelated database.

**Checkpoint:** A normal restore reports `ok` and matching fixtures; the altered test copy fails the logical comparison with the affected check named.

**Evidence:** Include passing and controlled-failure test output.

### S05.4 — Write the recovery runbook

**Purpose:** Make the recovery path understandable to another operator.

**Work:** Document the exact restore steps, expected checks, failure messages, test-data boundary, and cleanup. Record observed backup and restore times. If your runbook claims service recovery, point a disposable application instance at the restored copy and verify one known record through its normal read path.

**Checkpoint:** A clean clone can recreate the fixture, restore it elsewhere, verify it, and remove only paths created by the test.

**Evidence:** Publish the runbook, test suite, manifest, sanitized report, and a short recovery walkthrough.

## Verification plan

Run the fixture from a clean checkout. Confirm the restored database passes `PRAGMA integrity_check`, matches expected counts and selected rows, and is different from the still-open source path. Run the controlled mismatch test and verify it fails for the logical comparison even if the copied database remains structurally valid.

## Troubleshooting

- **Backup API reports a locked database:** retry only within a bounded policy and report the source state; do not switch to blind file copying while writes are active.
- **Integrity check passes but records differ:** integrity is structural, so inspect the application-level manifest and queries separately.
- **Restore target already exists:** stop and ask for a new disposable path; never delete an unknown destination automatically.
- **The copied database appears to have fewer recent changes:** verify the snapshot timing and ensure the source transaction had committed before the backup began.

## Acceptance criteria

- The project creates a snapshot from a synthetic database and restores it into a distinct, fresh file.
- `PRAGMA integrity_check` returns `ok` for the normal restore.
- At least three logical checks (table counts and selected values) match; a controlled altered copy is detected.
- Existing destinations are not overwritten, and no live or personal data is used.

## Portfolio deliverables

Provide the fixture generator, source and restore code, tests, manifest, recovery runbook, sanitized report, and a brief explanation of why “backup succeeded” and “integrity check passed” are each insufficient alone.

## Stretch goals

- Add SHA-256 checksums for the closed backup artifact and explain what the hash does and does not prove.
- Track a small retention policy inside the temporary fixture directory with a dry-run preview.
- Compare a SQLite backup with a logical export and explain the restore trade-offs.

## Technical references

- [SQLite Online Backup API](https://www.sqlite.org/backup.html) — make a consistent snapshot while SQLite manages the database connection.
- [Python `sqlite3` documentation](https://docs.python.org/3/library/sqlite3.html) — use `Connection.backup()` and independent connections.
- [SQLite `PRAGMA integrity_check`](https://sqlite.org/pragma.html#pragma_integrity_check) — check database structure while recognizing that application-level comparisons are still needed.
