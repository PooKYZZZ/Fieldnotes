# Metrics and alert probe

## Scenario

A small service can return errors while its process is still running. Build a local observability exercise that exports a few useful metrics, scrapes them with Prometheus, and raises an alert when a controlled failure occurs—then proves that the alert resolves after recovery.

## Why this matters

Monitoring is useful only when measurements help someone decide what to do. A small set of clearly named signals and a tested response is more valuable than a large dashboard of unexplained charts.

## Learning objectives

- Distinguish a process health probe from service-level behavior.
- Expose and scrape counters, a gauge, or a latency distribution with bounded labels.
- Write and test an alert rule that has a clear threshold, duration, and recovery behavior.
- Diagnose the difference between “target down,” “target up but returning errors,” and “alerting system not evaluating.”

## Prerequisites and setup

Use Docker Compose and a tiny service that you own, bound to localhost. Generate synthetic requests from a local script; do not export real user identifiers, request paths, credentials, or personal data as metric labels. Keep data retention short for the lab.

## Requirements and boundaries

- Expose `/metrics` only on the local lab network. Track a request count, error count, and one service-level measure such as request duration or in-flight work.
- Use low-cardinality labels such as service and status class. Never use raw URL paths, user IDs, email addresses, request IDs, or exception messages as labels.
- Configure a Prometheus scrape job and one actionable alert with an explicit `for` duration and a useful summary/description.
- Test rule expressions with `promtool test rules` where supported. Simulate one service outage and one application-error condition, then observe firing and resolution.
- Do not expose Grafana/Prometheus publicly, add alert credentials, or claim that an alert proves the service is healthy between scrapes.

## Architecture and decisions

`synthetic client → service metrics endpoint → Prometheus scrape and rule evaluation → local alert state → operator runbook`

Keep metrics collection distinct from alert evaluation and dashboard display. Choose the service-level symptom first, then select a metric and threshold that represent it. Consider scrape interval plus alert `for` duration when estimating detection time.

## Build milestones

### S07.1 — Choose signals and a failure hypothesis

**Purpose:** Tie each metric to a question an operator may need to answer.

**Work:** Define one service symptom, one useful rate or latency signal, an expected baseline, and a controlled failure. Choose metric names and labels before instrumenting; estimate the maximum possible label combinations.

**Checkpoint:** Every signal has a question and unit; the design contains no unbounded labels or real user data.

**Evidence:** Commit a one-page metric contract and a small architecture sketch.

#### Hint 1 — Start with the operator's question

Write the user-visible symptom in plain language before selecting a metric. Then name the unit, population, and time window that would let someone test that symptom. Host CPU or a live scrape target can provide context, but neither alone proves users can complete the service's main operation.

### S07.2 — Instrument and collect a local baseline

**Purpose:** Ensure Prometheus can observe the service before adding alerts.

**Work:** Instrument the toy service, configure Prometheus to scrape it, and generate a small repeatable batch of requests. Confirm the target is up and that counter changes match the requests. Keep the exposition port bound locally.

**Checkpoint:** Prometheus shows fresh samples for each metric and the service remains usable when monitoring is stopped.

**Evidence:** Save a sanitized target status, sample query results, and the Compose configuration.

### S07.3 — Test the alert lifecycle

**Purpose:** Verify an alert can detect a useful symptom and clear after recovery.

**Work:** Write an alert rule with a documented threshold, `for` period, labels, and response-oriented annotations. Test the rule expression, stop the toy service or inject controlled 5xx responses, wait for the rule to fire, then restore the service and observe resolution.

**Checkpoint:** The failure is detected within the expected scrape-plus-pending window, the alert message says what to inspect, and recovery returns the alert to normal.

**Evidence:** Include rule tests, timestamps for injection/firing/recovery, and a short alert timeline.

### S07.4 — Make the signal useful to a responder

**Purpose:** Connect an alert to a first diagnostic action without creating noise.

**Work:** Add a compact dashboard panel or Prometheus query view and a runbook with scope, initial checks, recovery, and a link to relevant evidence. Note a false-positive condition and how the chosen threshold avoids or accepts it.

**Checkpoint:** Another learner can trigger the same failure, identify why the alert fired, and prove it resolved; monitoring failure itself is visible as a missing target.

**Evidence:** Publish dashboard export, alert file, runbook, test output, and cleanup instructions.

## Verification plan

Use `promtool` to test alert expressions where available, then run the local stack. Confirm counters match generated requests, the service-down alert fires after the documented delay, and it clears after service recovery. Separately show that an HTTP error with the exporter still up is distinguishable from a scrape target being down.

## Troubleshooting

- **Prometheus target is down:** check the scrape address from Prometheus's container network namespace; `localhost` inside a container is that container.
- **Metric count is unexpectedly high:** inspect label values and remove user-specific or unbounded dimensions.
- **Alert never fires:** check target freshness, query labels, units, scrape interval, and pending duration before changing the threshold.
- **Alert flaps:** compare observed noise with the `for` period and recovery behavior; do not lengthen it without explaining detection delay.

## Acceptance criteria

- Three documented service metrics are scraped with bounded labels.
- One controlled outage or error condition fires the intended alert and recovery clears it.
- The expected alert delay is measured and reported within one scrape interval plus its configured pending period, allowing scheduling jitter.
- The lab is local-only, contains no real credentials or user labels, and includes a first-response runbook.

## Portfolio deliverables

Provide the service instrumentation, Compose files, scrape configuration, alert rule and tests, dashboard export, failure timeline, runbook, and a short explanation of why the selected signal is actionable.

## Stretch goals

- Add a simple service-level objective and compare observed request success with the target over the lab window.
- Add alert grouping or a local notification receiver and test both firing and resolved messages.
- Compare scrape-based detection with a user-facing synthetic check and document what each can miss.
