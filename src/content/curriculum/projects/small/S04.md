# Compose configuration validator

## Scenario

A small team has several Compose files for local development. A typo, missing required variable, duplicate host port, or unpersisted database path can waste debugging time or erase a learner's fixture. Build a preflight validator that checks the rendered Compose model before anyone starts the stack.

## Why this matters

Configuration should be reviewed as the platform will interpret it, not as a text file that merely looks plausible. Compose can merge files and substitute variables, so a static grep may disagree with the effective configuration.

## Learning objectives

- Use Compose's own parser and normalized model as the validation boundary.
- Turn requirements into named checks with actionable, non-secret output.
- Test validator behavior using valid and invalid disposable project fixtures.
- Explain why a preflight pass cannot prove that containers will run correctly.

## Prerequisites and setup

Install Docker Engine and the Compose v2 plugin, then create a separate repository with a tiny web service and disposable data directory. Use `.env.example` values only. Do not point the tool at a real deployment file or print the fully resolved model into a shared log.

## Requirements and boundaries

- Accept an explicit Compose project directory and a list of Compose files; never silently inspect a parent or home directory.
- Ask `docker compose config --format json` to render the effective model, parse the JSON in memory, and capture stderr separately. Never print the resolved environment or environment values.
- Check required service names, referenced build/config files, required interpolation variables, duplicate published host address/port/protocol tuples, and declared persistence for stateful services.
- Explain which check failed and identify the service or file without echoing secret values.
- Do not start, stop, pull, build, or delete containers. Validation is a read-only preflight.

## Architecture and decisions

`explicit project files → Compose normalization → in-memory model checks → findings with severity → exit status`

Compose performs YAML parsing and interpolation; your tool evaluates policy on the resulting JSON. Decide which services count as stateful, how host IP affects a duplicate-port check, and whether warnings or errors block a run. Keep these policy choices in a small config file or documented constants rather than scattering heuristics.

## Build milestones

### S04.1 — Model the policy and fixture set

**Purpose:** Make the checks precise before parsing real projects.

**Work:** Create a valid fixture and separate fixtures for missing file, unresolved required variable, duplicate host port, missing named volume, and healthy configuration. Write down which checks are errors and which are warnings.

**Checkpoint:** Each invalid fixture fails for one expected reason; the valid fixture has no unexpected finding.

**Evidence:** Commit the fixtures, policy table, and a short explanation of why rendered Compose data is used.

#### Hint 1 — Change one thing at a time

Start from a fixture that passes, then make one deliberate policy violation in each new fixture. This makes a failing test explain which rule caught the change. Compose can confirm that a model parses and resolves; your validator still needs to enforce the project's own policy.

### S04.2 — Render and inspect the effective model

**Purpose:** Check what Compose would apply without starting services.

**Work:** Invoke `docker compose -f … config --format json` with a subprocess argument list and timeout. Parse stdout only after success; treat nonzero exit as a Compose rendering failure. Keep raw stdout, stderr, and environment out of normal report output.

**Checkpoint:** Valid multiple-file configuration resolves correctly; missing required variables and invalid syntax fail before policy checks.

**Evidence:** Save the validator's sanitized summary and exit status for a valid fixture.

### S04.3 — Add structural policy checks

**Purpose:** Catch risks that Compose accepts but this lab wants to prevent.

**Work:** Validate referenced paths, required service names, normalized published-port conflicts, and persistent storage for services declared stateful in the fixture. Decide how `127.0.0.1` bindings differ from wildcard or distinct host-address bindings.

**Checkpoint:** Every invalid fixture is detected once with a specific file or service reference and a correction. For the same protocol and host port, show that an IPv4 wildcard overlaps a loopback binding and that two distinct explicit IPv4 addresses do not overlap. Treat those as model checks. An actual connection through a running fixture is separate runtime evidence.

**Evidence:** Include unit tests for policy checks plus integration tests that call Compose on the disposable fixtures.

### S04.4 — Make it safe to adopt

**Purpose:** Ensure the preflight is informative without becoming a deployment tool.

**Work:** Add CLI help, severity filtering, exit codes, concise JSON/text reports, and a clean setup guide. Review logs for resolved environment values and prove that the validator never invokes `up`, `down`, `pull`, or `rm`.

**Checkpoint:** A clean clone can validate the fixture without changing the Docker host or disclosing a sentinel value in `.env`.

**Evidence:** Publish the policy table, tests, sample sanitized report, and command history for the disposable fixture.

## Verification plan

Run the full fixture matrix. Capture only the validator's sanitized report, not the raw resolved Compose JSON. Confirm a valid config exits 0, blocking findings exit nonzero, warnings remain visible, and the tool does not create or change containers. After preflight, start the valid toy stack manually and run a separate smoke test to demonstrate the boundary between configuration validation and runtime verification.

## Troubleshooting

- **Compose cannot render JSON:** verify Compose v2 and the selected file paths; do not replace its parser with broad regular expressions.
- **A valid model reports duplicate ports:** compare normalized host IP, port, and protocol; two services can both use the same container port while publishing different host ports.
- **The validator leaks an env value:** suppress raw Compose output and stderr from normal logs; emit variable names or source locations only.
- **A preflight passes but a service fails:** inspect image build, runtime health, and dependency readiness; static configuration checks are not a smoke test.

## Acceptance criteria

- The valid fixture passes; at least four distinct invalid fixtures produce the expected finding and actionable reason.
- Interpolation and YAML interpretation come from Compose's normalized JSON output.
- A secret sentinel never appears in report output, and the validator does not start or alter containers.
- Tests cover duplicate host ports and a declared stateful service missing persistence.

## Portfolio deliverables

Include the CLI, policy table, synthetic Compose fixtures, automated tests, sanitized JSON and text examples, setup instructions, and a brief note describing a false positive the validator avoids.
