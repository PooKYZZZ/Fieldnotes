# Network diagnostic notebook

## Scenario

A teammate reports that a service URL sometimes fails. The browser only says “could not connect,” which does not tell the team whether name resolution, routing, TCP, TLS, or the HTTP application is responsible. Build a small diagnostic notebook that collects bounded evidence for one target at a time and explains where the connection path stops.

## Why this matters

Network troubleshooting becomes slower and riskier when operators jump straight to configuration changes. A layered check narrows the failure boundary while keeping probes read-only and scoped to a host the learner is allowed to test.

## Learning objectives

- Explain the sequence from name resolution through route selection, TCP, TLS, and HTTP.
- Use bounded probes and preserve each tool's exit status and useful output.
- Avoid treating a failed later layer as proof that every earlier layer is healthy.
- Write a report that distinguishes evidence from inference and names the next check.

## Prerequisites and setup

Use a Linux VM, WSL, or macOS terminal with the listed tools. Start with a local container or test service that you own. If you use an external target, obtain approval and test a single hostname and port only. Set a short timeout for every probe.

## Requirements and boundaries

- Accept one hostname and one port; validate both before launching subprocesses.
- Check DNS answers, route selection for a resolved address, TCP connection, TLS certificate/handshake when HTTPS is expected, and HTTP status when a URL is provided.
- Use bounded connection and total timeouts. Do not add port ranges, subnet discovery, credential guessing, request floods, or certificate bypass flags.
- Record command result, exit code, duration, and sanitized summary. Avoid storing full certificate chains or response bodies by default.
- A check may be “not run” when an earlier layer fails. Report that state distinctly from pass and fail.

## Architecture and decisions

`approved target → DNS answers → route lookup → TCP connect → TLS handshake → HTTP response → evidence report`

Keep each probe as a separate step with its own timeout and result type. Decide how to handle multiple DNS answers and IPv4/IPv6. Do not call a TLS failure an HTTP failure: an HTTP response may not have been reached. Record why your tool considers a target authorized, such as a local fixture or an explicit allowlist.

## Build milestones

### S02.1 — Define the target and evidence contract

**Purpose:** Keep the diagnostic safe, repeatable, and clear about what it observes.

**Work:** Choose a local service and a hostname/port you control. Draw the five connection layers, decide which are applicable to a target, and define pass, fail, and not-run states. Set a maximum total run time and decide which output fields must be redacted.

**Checkpoint:** The plan cannot run against an arbitrary list of hosts or ports, and every check has a timeout and a documented meaning.

**Evidence:** Save the target scope, layer diagram, timeout budget, and sample report shape.

#### Hint 1 — Separate the layers

Treat name resolution, route selection, TCP connection, TLS negotiation, and HTTP response as different questions. For each, decide what evidence would answer it and whether the layer applies to your local target; a successful earlier layer does not prove the later ones work.

### S02.2 — Implement the layered probes

**Purpose:** Collect evidence in the order the connection is established.

**Work:** Implement DNS lookup, route lookup, a single TCP connect, TLS handshake where appropriate, and an HTTP request with response-body capture disabled. For a manual baseline, compare with `getent ahosts HOST`, `ip route get ADDRESS`, `openssl s_client -connect HOST:PORT -servername HOST -brief`, and `curl --connect-timeout 3 --max-time 8 -I https://HOST/`.

**Checkpoint:** A working local HTTPS service reaches the expected layers; an unknown hostname stops after DNS without reporting later layers as failed.

**Evidence:** Save one sanitized success report and the exact bounded commands or code path used.

### S02.3 — Test failure boundaries

**Purpose:** Verify that each distinct failure produces a different diagnosis.

**Work:** Use controlled local cases for an unresolved name, closed port, TLS name mismatch, HTTP 404, and slow endpoint. Capture the earliest failing layer, exit status, and elapsed time. Test both a hostname with one answer and, if available, one with multiple addresses.

**Checkpoint:** The report separates name-resolution, route, connect, TLS, and HTTP outcomes; an HTTP 404 is a successful HTTP exchange with an application-level response, not a TCP failure.

**Evidence:** Add a test matrix with expected layer, observed result, and interpretation for every case.

### S02.4 — Make the notebook useful to another operator

**Purpose:** Turn raw probes into a safe next action.

**Work:** Add a concise CLI or README flow, examples for HTTP and HTTPS targets, a “what this does not prove” note, and a troubleshooting guide. Review output for private hostnames, IPs, headers, and response bodies before sharing.

**Checkpoint:** A learner can reproduce the local cases and identify the next diagnostic step without applying a network change.

**Evidence:** Publish the sanitized report, test matrix, diagram, limitations, and a short incident-style summary.

## Verification plan

Run the complete failure matrix against only the controlled fixture. Confirm each probe stops within its timeout, reports not-run states when blocked by a prior layer, and never uses a TLS bypass. Repeat a successful run and compare its layer statuses while allowing durations and DNS ordering to vary.

## Troubleshooting

- **DNS works but TCP fails:** compare the resolved address and selected route; inspect the service's listening address and port without changing firewall rules.
- **TCP connects but TLS fails:** check the requested hostname, certificate names, trust chain, and system clock; do not “fix” the diagnosis with `-k`.
- **TLS succeeds but HTTP returns 404:** the transport is working; verify the path and application routing separately.
- **A probe hangs:** verify the timeout applies to both connection and entire operation, including subprocess termination.

## Acceptance criteria

- A single scoped target is tested through independent DNS, route, TCP, TLS, and HTTP states.
- Controlled fixtures distinguish at least five failure or response outcomes, including HTTP 404.
- Every external operation has a bounded timeout; response bodies and credentials are not saved.
- The report labels evidence, inference, and the next suggested check separately.

## Portfolio deliverables

Provide the source, test fixtures or setup instructions, layer diagram, failure matrix, sanitized sample report, and a brief explanation of one diagnosis. State which target was local, which was approved, and what the evidence could not establish.

## Stretch goals

- Add IPv6-aware output while retaining the same one-target scope.
- Add JSON report export and compare multiple approved probes without merging their failure states.
- Test DNS answers that change between runs and explain why one observation is not a durable inventory.
