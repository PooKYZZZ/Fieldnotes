# Service watchdog report

## Scenario

On-call engineers receive a short “the service is down” message but no evidence about the service state, its process, disk capacity, or health endpoint. Build a read-only watchdog report for a small allowlist of services on a lab VM. It must collect facts and make failures visible without trying to repair the machine.

## Why this matters

Automated restarts can hide a recurring failure or make an incident worse. A trustworthy first report identifies what was checked, when, and why it failed so the operator can choose the next safe action.

## Learning objectives

- Query systemd and host state without changing it.
- Apply explicit timeouts and severity thresholds to a small set of health checks.
- Return machine-readable and human-readable results from the same check model.
- Test success, failure, timeout, and unavailable-tool behavior without depending on the learner's personal services.

## Prerequisites and setup

Use a disposable Linux VM that runs systemd. Create a small local test service and a local health endpoint. The tool should run as the regular learner account and should not need `sudo`. Test with stub commands or a local fixture so the suite does not depend on the health of the learner's laptop.

## Requirements and boundaries

- Read service state from an explicit allowlist; never enumerate all services or inspect unrelated users' processes.
- Check systemd active state, main process identity where available, filesystem free space against a documented threshold, and an optional local HTTP health URL.
- Record check name, timestamp, duration, result, and reason. A failed check must make the overall command exit nonzero.
- Use request and subprocess timeouts. Do not restart, stop, enable, reconfigure, or install anything.
- Keep thresholds configurable and explain their units. Do not claim a disk percentage or process state is itself proof of application health.

## Architecture and decisions

`allowlisted targets → read-only probes → normalized check results → text/JSON report → operator action`

Separate check collection from report formatting. Decide whether a missing optional check is skipped or fails the whole report, and set a threshold that is useful for a disposable fixture. Keep “unknown” separate from “healthy.”

## Build milestones

### S03.1 — Define the health contract

**Purpose:** Decide what “healthy enough to investigate” means for this small service.

**Work:** Pick one disposable service, document its expected systemd unit, local health URL, disk threshold, and the evidence each check can provide. Create a result schema with pass, fail, and unknown states.

**Checkpoint:** Every check names its target and source; there is no automatic remediation or open-ended service discovery.

**Evidence:** Commit the health contract, allowlist example, and report schema.

### S03.2 — Implement read-only probes

**Purpose:** Collect facts without mutating the VM.

**Work:** Query the unit with `systemctl is-active` and `systemctl show`, read filesystem capacity with `df`, and request the local health endpoint with a short timeout. Use structured subprocess arguments, not shell interpolation. Treat unavailable systemd or a missing unit as explicit results.

**Checkpoint:** A known-good fixture reports each check and a stable summary; the tool exits nonzero if a required check fails.

**Evidence:** Save one sanitized healthy report and the command versions used.

### S03.3 — Exercise failure and timeout paths

**Purpose:** Ensure the report helps with the first diagnostic step rather than hiding failure.

**Work:** Use test doubles for inactive unit, missing unit, endpoint refusal, slow endpoint, unavailable command, and disk threshold boundary. Confirm subprocesses are terminated when their timeout expires.

**Checkpoint:** Each failure has a distinct reason, missing optional data is not mislabeled healthy, and no test invokes a restart or privilege escalation.

**Evidence:** Include automated test output and a table mapping failure to next operator check.

### S03.4 — Schedule only after the report is trustworthy

**Purpose:** Demonstrate repeatable operations without creating an uncontrolled daemon.

**Work:** Add an example systemd timer or cron entry as optional documentation. Make output location and retention explicit, avoid storing secrets, and document how to disable the schedule. Re-run the tool manually before enabling any timer.

**Checkpoint:** The manual command remains the source of truth; the schedule records results but cannot restart or modify the service.

**Evidence:** Publish the report, tests, sample timer configuration, retention choice, and disable procedure.

## Verification plan

Run tests with stubbed system commands and one local endpoint. On the lab VM, manually compare the report with `systemctl is-active UNIT`, `systemctl show UNIT`, `df -P PATH`, and the endpoint response. Trigger one controlled failure and confirm the report becomes nonzero without changing service state.

## Troubleshooting

- **systemd is unavailable:** use a disposable systemd VM for the integration check; keep the core parser tests independent of systemd.
- **The HTTP check passes while the service is unhealthy:** verify that the endpoint tests the needed dependency and not just process liveness.
- **The command reports permission denied:** reduce the inspected scope or use public read-only properties; do not add `sudo` to make the warning disappear.
- **A timeout leaves a child running:** manage the subprocess lifecycle and test termination, not only the timeout message.

## Acceptance criteria

- Four documented read-only checks return normalized results with timestamps and reasons.
- At least six good, bad, missing, or slow fixtures are covered by tests.
- A failed required check produces a nonzero exit status and identifies the failed boundary.
- The project contains no restart or configuration-changing code, requires no root access, and can be disabled cleanly if scheduled.

## Portfolio deliverables

Include the source, allowlist example, test suite, sanitized healthy and failed reports, a concise operating note, and a decision note explaining what the health endpoint does not prove.

## Stretch goals

- Add a rate-limited local notification with a quiet period and recovery notification.
- Compare two successive reports to highlight changes without retaining sensitive process arguments.
- Add a plugin interface for checks while keeping the default allowlist small.
