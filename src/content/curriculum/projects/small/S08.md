# Terraform cleanup checker

## Scenario

After a cloud lab, an engineer wants to know whether billable resources remain. Terraform state lists what that workspace manages, but a state file alone cannot prove that no resource was created manually or left outside the current state. Build a cleanup review that compares a planned teardown with an independent inventory of the lab's explicitly scoped resources.

## Why this matters

Cloud cleanup is a cost and safety control. A command that says “destroy complete” may still leave manually created resources, while an overly broad cleanup can remove the wrong environment. The learner should practice preview, scope verification, and independent confirmation.

## Learning objectives

- Explain the difference between Terraform configuration, state, a plan, and actual provider resources.
- Preview planned changes before applying them and verify the target account/project/region.
- Compare managed resources with an independent inventory bounded to a disposable lab scope.
- Write a cleanup checklist that detects leftovers without automatically deleting them.

## Prerequisites and setup

Terraform basics and a disposable project directory are required. The baseline can use a local provider and generated inventory fixtures; connecting a cloud account is optional and may incur charges. If you use a provider, create or choose a dedicated lab scope, set a budget/alert, and record the account, subscription/project, and region before any apply.

## Requirements and boundaries

- Read Terraform state and a speculative destroy plan for the selected workspace; do not apply or destroy automatically.
- Produce a manifest with resource address/type, owning workspace, planned action, and an independent inventory result.
- For the optional cloud adapter, enumerate only the dedicated project/resource group and filter by a unique lab tag. Do not scan an organization or subscription-wide environment by default.
- Warn that Terraform state may be incomplete when resources are unmanaged or drifted. Confirm cleanup with the provider inventory or console and the expected billing/resource view.
- Never print state contents, tokens, or full saved plan files to a public log; plan files and state may contain sensitive values.
- Require a human to inspect the final plan and confirm the target scope before any destructive action outside the baseline fixture.

## Architecture and decisions

`chosen workspace → state + speculative plan → scoped provider inventory → compare and classify → human-reviewed cleanup → independent empty-scope check`

Keep “managed and planned,” “unmanaged but tagged,” “unmatched,” and “unknown” as separate states. Decide whether the project reports resources only or also expected monthly cost; if estimating cost, label the provider price and observation date because prices vary.

## Build milestones

### S08.1 — Define the cleanup boundary

**Purpose:** Prevent the checker from acting on the wrong account or resource set.

**Work:** Create a local fixture with managed, unmanaged-tagged, and unrelated resources. Define the required workspace, account/project, region, and lab tag. Add a preflight summary that must be reviewed before an optional provider query.

**Checkpoint:** Unrelated resources are excluded, and missing or mismatched scope details make the report fail closed.

**Evidence:** Commit a sample manifest and the written scope rules; do not commit state or credentials.

### S08.2 — Preview Terraform's intended cleanup

**Purpose:** Learn what Terraform believes it will change before changing anything.

**Work:** Run `terraform plan -destroy` or a saved speculative plan for the selected test workspace, then inspect its JSON representation locally. List addresses and actions only; redact values and never apply automatically.

**Checkpoint:** A plan with zero, changed, and destroy actions is represented correctly; the tool clearly states that it has not changed infrastructure.

**Evidence:** Save a sanitized plan summary, workspace name, and target identifiers.

### S08.3 — Compare plan and independent inventory

**Purpose:** Find resources Terraform state may not account for.

**Work:** Build an inventory adapter for a local fixture and, optionally, one provider-scoped lab group. Compare addresses/tags and classify unmatched resources for review. Add tests for stale state, manually created tagged resources, and unrelated resources that must be excluded.

**Checkpoint:** The checker detects a tagged resource absent from the plan and does not include an unrelated fixture resource.

**Evidence:** Include the before-cleanup comparison report and tests for both leftover and out-of-scope cases.

### S08.4 — Demonstrate cleanup as a reviewed operation

**Purpose:** Verify the lifecycle while keeping destructive action under human control.

**Work:** For the local fixture, exercise removal and rerun the checker. If using cloud resources, inspect the final destroy plan manually, confirm scope, apply only to the disposable group, and independently query that same group afterward. Record cleanup timing and any intentionally retained resource.

**Checkpoint:** The fixture inventory is empty after cleanup; the tool itself did not execute a destroy; any provider resource that remains is named and explained.

**Evidence:** Publish the runbook, sanitized before/after manifests, manual-review checklist, and cost/cleanup note.

## Verification plan

Run the local test matrix first. Confirm the speculative plan is read-only and the manifest shows the intended workspace. For the optional cloud run, verify account/project, region, and tag before review; inspect the proposed destroy plan manually, clean only the dedicated lab scope, then query that same scope independently. Do not treat an empty Terraform state as proof that the provider has no leftovers.

## Troubleshooting

- **The plan includes unexpected resources:** stop; verify workspace, state backend, and variable files. Do not use `-target` to hide unexpected changes.
- **State is empty but inventory is not:** classify unmanaged resources and determine their owner before cleanup; never delete them just to make the report empty.
- **Provider query returns too much:** require the explicit project/resource-group identifier and a unique lab tag; fail closed if either is missing.
- **A saved plan or state appears in Git:** remove it from the candidate commit, rotate any exposed credentials, and document remediation; do not assume terminal redaction protects the file.

## Acceptance criteria

- The checker distinguishes plan state from independent inventory and reports at least one intentionally unmanaged fixture resource.
- The scope preflight rejects a mismatched account/project/region or missing lab tag.
- No code path automatically calls `terraform apply` or `terraform destroy`.
- The local cleanup leaves no fixture resources; any cloud run is bounded to a dedicated lab scope and independently checked afterward.

## Portfolio deliverables

Include the checker source, local fixtures, sanitized manifest, cleanup runbook, one plan summary, independent before/after inventory, and a decision note explaining why state is not the same as a complete resource inventory.

## Stretch goals

- Add a budget estimate with provider, region, pricing source, and “checked on” date.
- Add a CI job that runs only local fixture tests and never receives cloud credentials.
- Add a tag report that identifies owner, creation date, and expiry without performing deletion.
