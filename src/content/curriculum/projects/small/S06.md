# CI failure gallery

## Scenario

New engineers often see a red pipeline but do not know which log line identifies the real cause. Build a small teaching repository with controlled examples of common CI failures, then show how to locate the earliest useful signal and verify a minimal fix.

## Why this matters

Continuous integration is a feedback system, not a badge that turns green. Engineers need to understand which check failed, whether later errors are only consequences, and how a trustworthy workflow prevents an unverified change from advancing.

## Learning objectives

- Explain the relationship between a pull request, workflow, job, step, and artifact.
- Trigger controlled lint, test, missing-configuration, and container-build failures in an isolated repository.
- Identify the first meaningful failure rather than patching downstream noise.
- Apply least-privilege workflow permissions and keep credentials out of test jobs.

## Prerequisites and setup

Create a new public-safe repository with a tiny Python service and a GitHub Actions workflow. Use synthetic values and no deployment secrets. Keep the default branch passing; put each intentional defect on its own branch or tag so it cannot accidentally become the release state.

## Requirements and boundaries

- Provide a passing baseline and at least four reproducible failure cases: lint, unit test, required environment/configuration, and image build.
- Each case must contain a short “symptom,” the earliest useful log location, a diagnosis, the smallest fix, and the verification rerun.
- Keep failure branches isolated from the default branch and use pull requests or documented local branches to show the repair.
- Give workflows only the `GITHUB_TOKEN` permissions they need; do not expose secrets to pull-request code or print environment values.
- Make the workflow fail when a required check fails. Do not mark a later deploy or publish job successful by ignoring an earlier failed job.

## Architecture and decisions

`commit or pull request → lint/test/build jobs → workflow summary and logs → reviewed fix → green rerun`

Use separate jobs only when parallelism or isolation is useful. Decide which checks are required before merge and why. For each intentional failure, distinguish the root cause from follow-on messages emitted after the first failing step.

## Build milestones

### S06.1 — Establish the known-good baseline

**Purpose:** Make a reliable comparison point for each failure exercise.

**Work:** Add a small application, deterministic tests, a lint command, and a workflow triggered on pull requests and pushes to the default branch. Set minimum workflow permissions and document the required checks.

**Checkpoint:** A clean commit passes all checks; a deliberately failing unit test blocks the workflow before any publish step.

**Evidence:** Save the passing run URL or sanitized log excerpt, workflow file, and branch protections used in the lab.

#### Hint 1 — Prove the baseline first

Keep one known-good commit and run as your comparison point. Introduce one intentional failure on an isolated branch, identify the earliest failing step, then repair it and rerun. If several defects change together, the logs become harder to interpret.

### S06.2 — Create isolated failure cases

**Purpose:** Practice recognizing different classes of pipeline failure.

**Work:** Add one failure at a time: a lint violation, an incorrect assertion, a missing required variable, and a deliberate image build error. Keep each case in a separate branch or tagged commit and state what the failing check should prove.

**Checkpoint:** Every case fails at its intended step while the default branch remains green; no case requires a real secret or a deployment credential.

**Evidence:** Maintain a gallery entry with commit link, job and step name, expected first useful log, and observed exit state.

### S06.3 — Diagnose and repair with minimal changes

**Purpose:** Use evidence to select the smallest correct repair.

**Work:** For every case, write a one-sentence hypothesis before editing. Use the workflow log and local reproduction to test it, change only the relevant defect, and rerun the same check. Note which later errors disappeared after fixing the earliest failure.

**Checkpoint:** Each failure has a verified minimal fix and a passing rerun; no check is skipped or marked `continue-on-error` to hide the result.

**Evidence:** Save before/after run links, root-cause notes, and the exact changed file.

### S06.4 — Review the pipeline as a maintained system

**Purpose:** Turn a troubleshooting gallery into a safe learning repository.

**Work:** Add a README with the baseline, failure index, branch/tag instructions, log-reading approach, permission rationale, and cleanup. Review action dependencies and pin trusted actions to full commit SHAs or use a verified lockfile.

**Checkpoint:** Another learner can reproduce one failure, identify its first useful log, repair it, and return to a passing default branch.

**Evidence:** Publish the repo, sanitized workflow records, and a short walkthrough that explains one misleading downstream error.

## Verification plan

Check out each documented case in an isolated branch and confirm that the expected job fails. Apply the documented repair and rerun the same workflow. Verify the default branch remains green, the test failure prevents later jobs from running, no secret is available to untrusted pull-request code, and the workflow's permission block is no broader than necessary.

## Troubleshooting

- **The log is long:** start at the first failed step and its exit code, then read only upstream setup steps needed to interpret it.
- **A missing variable is silently empty:** make required configuration explicit and validate it before build or deploy steps.
- **A failure appears only in Actions:** compare runtime versions, working directory, file permissions, and environment inputs with the local reproduction.
- **A test failure does not block publishing:** inspect `needs`, job conditions, and allowed-failure settings; correct the dependency rather than hiding the check.

## Acceptance criteria

- Four distinct controlled failure types are reproducible and separately documented.
- Every gallery item identifies the earliest useful log, root cause, minimal fix, and passing rerun.
- The default branch stays green and required verification blocks downstream release work.
- Workflow permissions are explicit and minimal; no test failure uses live credentials.

## Portfolio deliverables

Include the repository, workflow, failure index, commit or pull-request links for the four cases, sanitized before/after logs, and a short postmortem explaining how the earliest failure was distinguished from secondary noise.

## Stretch goals

- Add a supported-runtime matrix and explain which failures are matrix-specific.
- Add an artifact upload for test results with a documented retention limit.
- Compare a local workflow runner with GitHub-hosted execution and document differences without treating them as identical environments.
