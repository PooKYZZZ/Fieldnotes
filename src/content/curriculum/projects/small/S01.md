# Log explorer

## Scenario

A small support team receives a sanitized export after users report intermittent errors. The file is too large to inspect manually, and copying raw log messages into a ticket could expose private data. Build a command-line report that helps an operator see when and how often errors occurred without printing message text.

## Why this matters

Operators need to turn noisy event streams into a small, reproducible signal. A useful log tool preserves enough context to guide the next investigation while avoiding unsupported conclusions and unnecessary exposure of raw data.

## Learning objectives

- Define and validate a small input contract instead of guessing at arbitrary log formats.
- Stream a file line by line, filter by severity and time, and summarize error categories.
- Distinguish malformed input from a valid search that finds no matches.
- Use deterministic fixtures and tests to make a report reproducible.

## Prerequisites and setup

Be comfortable running a Python script and creating a virtual environment. Use Python's standard library for the baseline so another learner can reproduce the project without installing packages. Create a new repository and a `fixtures/` folder containing only synthetic events. Do not feed it employer, customer, or production logs.

## Requirements and boundaries

- Accept newline-delimited JSON records with a timezone-aware `timestamp`, `level`, `service`, and `error_code`; treat `message` as untrusted and never print it.
- Provide `--level`, `--since`, `--until`, `--format text|json`, and built-in `--help` options. Document whether the time window includes its start and end.
- Report total matching records and counts grouped by service and error code. A valid query with zero matches is a successful result.
- Define a clear policy for malformed records: report line numbers, continue in normal mode, and offer a strict mode that exits unsuccessfully.
- Stream the input; do not load a multi-gigabyte file into memory. Bound the number of distinct aggregate groups and document what happens when that limit is reached.
- Do not add network access, upload logs, or emit raw messages, paths, secrets, or unbounded high-cardinality labels.

## Architecture and decisions

`input file → validation and filtering → aggregate counters → text or JSON report`

Keep parsing, filtering, aggregation, and rendering as separate functions so each boundary can be tested. Decide whether filtering is case-sensitive and how unknown severity values behave. Record the alternatives you considered; do not silently normalize invalid timestamps into local time.

## Build milestones

### S01.1 — Define the event contract and fixtures

**Purpose:** Make the input and privacy boundaries explicit before writing the parser.

**Work:** Create a README contract with two valid JSON lines, one malformed line, one unknown level, one event outside the selected time window, and one synthetic message containing a marker that must never appear in output. Write down timestamp format, grouping keys, and inclusive or exclusive window boundaries.

**Checkpoint:** A second person can predict the report counts from the fixture without reading your implementation.

**Evidence:** Commit the fixture, contract, and a short expected-count table.

### S01.2 — Implement parsing, filters, and summaries

**Purpose:** Turn a defined input into useful operational evidence.

**Work:** Add a CLI with `argparse`. Build the tool in small, testable passes rather than writing the whole report at once:

1. **Parse one record.** Turn one valid JSON line into a small internal event containing only the approved fields. Decide how to represent a rejected line without copying its raw contents into an error message.
2. **Predict and filter.** Before running the CLI, use your S01.1 count table to predict which records match `--level`, `--since`, and `--until`. Compare timestamps as timezone-aware instants; apply the inclusive or exclusive boundary you documented.
3. **Stream and aggregate.** Read the file line by line and update counts without retaining every event. Keep the aggregate bounded: choose a maximum number of distinct service/error-code groups and decide whether reaching it stops the report or routes excess groups into an explicitly named summary.
4. **Render the result.** Keep collection separate from output formatting. Make text and JSON report the same totals, and choose a stable ordering so repeated runs are easy to compare.

Add one focused test as you complete each pass. Use the fixture you created; do not copy a report from another machine or invent expected values.

**Checkpoint:** The sample command `python log_report.py fixtures/sample.jsonl --level ERROR` reports the totals and grouping counts from your hand-calculated table; text and JSON agree, and `--help` explains every option and time-window rule.

**Evidence:** Save the command, exit status, sanitized sample output, group-limit decision, and one sentence explaining why a matching count is evidence of frequency rather than proof of root cause.

#### Hint 1 — Start with the smallest useful boundary

Make the parser accept one line and return either a normalized event or a small rejection reason. Keep file reading, filtering, counting, and printing outside that function so one test can isolate one decision.

#### Hint 2 — Treat time as an instant

An ISO timestamp can include a UTC offset. Normalize or compare aware timestamps consistently; do not compare their displayed clock text or silently assign the machine's local timezone to a naive value.

#### Hint 3 — Keep memory tied to the report, not the file

Use an iterator over input lines and update only the counters you need. Your counters can still grow if every record creates a new group, so test the limit behavior with synthetic service and error-code values.

### S01.3 — Make failure behavior useful

**Purpose:** Help the operator distinguish a bad file from a genuine no-match result.

**Work:** Test a missing file, unreadable file, malformed JSON, missing fields, invalid severity, naive timestamp, empty file, and zero-match filter. Choose exit codes and messages that identify the failing line or argument without echoing its raw contents. Add tests for the time-window boundary you chose.

**Checkpoint:** A no-match query exits successfully; an unreadable file exits unsuccessfully, malformed rows warn and continue in normal mode, and strict mode makes malformed rows fail with a clear reason; the privacy marker never appears in stdout or stderr.

**Evidence:** Include test output and one example of each distinct result state.

#### Hint 1 — Find the failing stage

Separate file access, JSON parsing, field validation, filtering, and rendering. A readable file with valid records and zero matches is different from a record the parser cannot safely use.

#### Hint 2 — Test the privacy boundary directly

Put a unique marker in a synthetic `message`, capture both stdout and stderr, and assert the marker is absent for valid, malformed, and strict-mode cases. Report a line number and a safe reason instead of echoing the record.

### S01.4 — Package a reviewable tool

**Purpose:** Make the report usable by someone who did not build it.

**Work:** Add a clean setup path, usage examples, a short explanation of what grouped counts can and cannot prove, and a reproducibility note describing the fixture. Run the tool twice against the same fixture and compare outputs.

**Checkpoint:** A clean clone can run the tests and sample command using the documented Python version, with no hidden files or personal logs.

**Evidence:** Publish the repository URL, README, tests, fixture, and one sanitized report.

## Verification plan

Run the test suite on the synthetic fixture, then repeat the documented CLI command from a clean checkout. Compare each count with the hand-calculated table. Exercise strict and normal malformed-line modes, an empty file, and a valid filter with no matches. Search captured stdout and stderr for the fixture's private-message marker.

## Troubleshooting

- **Every record is rejected:** inspect one fixture line with a JSON parser; compare its field names and timestamp offset with the contract.
- **Time filtering changes between machines:** require an explicit UTC offset and compare parsed instants, not local clock strings.
- **Counts do not match:** test filtering before grouping and print temporary aggregate keys to stderr only while debugging; remove verbose raw-event output before release.
- **A valid query exits nonzero:** separate the “input was readable” result from the “matches were found” result.

## Acceptance criteria

- The known fixture produces the documented totals and group counts on two consecutive runs.
- Tests cover malformed records, missing files, empty input, zero matches, and time boundaries.
- The tool never prints raw message content, and invalid records are reported without copying their contents.
- A clean clone can run help, tests, and the sample report using only the documented prerequisites.

## Portfolio deliverables

Include the source, fixture, tests, README, sample output, a small data-flow diagram, and a decision note about malformed lines and time windows. In a portfolio walkthrough, explain one result that points toward another investigation and one conclusion the counts cannot support.

## Stretch goals

- Add a bounded multi-file mode while preserving deterministic ordering.
- Add an output option that writes atomically to a path chosen by the user.
- Compare runtime and memory use on generated synthetic files of increasing size.
