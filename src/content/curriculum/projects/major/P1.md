# Automated Deployment Platform

## Scenario

A small product team has a backend service that works on one engineer's laptop, but each release involves copying files, rebuilding containers by hand, and hoping the new version is healthy. Build a delivery path that lets another engineer move a reviewed change into a reproducible release and recover if the release fails.

## Why this matters

Reliable delivery is a system of traceable changes, repeatable builds, controlled access, verification, and recovery. The goal is not to collect DevOps products; it is to reduce uncertainty at the handoff from code to a running service.

## Learning objectives

- Design a small delivery architecture and defend the choice of local Compose or a single VM over unnecessary orchestration.
- Test and build a versioned container artifact from a reviewed commit.
- Configure a host repeatably and deploy the same artifact through an explicit release step.
- Prove health after deployment, practice rollback, and document the operational boundaries.

## Prerequisites and setup

Complete the Linux, Git, containers, CI, and automation modules listed above, or be comfortable with their equivalent skills. Start with a synthetic FastAPI service in a new repository. The default route should expose a version/commit identifier and a simple smoke-testable operation. The required path can run locally with Compose; a cloud VM is optional and must use a disposable account or resource group with a budget limit.

## Requirements and boundaries

### Functional scope

- Build and test a small API with `/health` and `/version` endpoints. `/version` must identify the exact source commit or immutable image digest currently running.
- Pull requests run tests, lint, and an image build check; the release path publishes an immutable tag or digest only from an approved branch/tag.
- A deployment changes the running version through an explicit, reviewable action, then runs a smoke check against the deployed endpoint.
- Keep the previous known-good version available and document a tested rollback.

### Quality and safety constraints

- A clean clone can build and test locally from documented prerequisites.
- Do not copy application source to a host as the release artifact; deploy the versioned image built by CI.
- Do not commit secrets. Use narrowly scoped repository/environment permissions; prefer short-lived OIDC federation for an optional cloud deployment where the provider supports it.
- Restrict inbound traffic, bind local-only services locally, and avoid exposing the Docker socket or monitoring/admin ports.
- The default path has no required cloud spend. Record any VM, registry, DNS, or storage cost and an exact cleanup procedure.
- Use Ansible for repeatable host configuration. Terraform is optional for provisioning; it is not required to learn the release path.

## Architecture and decisions

`reviewed commit → CI tests and image build → immutable image reference → release approval → Ansible host configuration → Compose deployment → health smoke test → rollback to previous digest`

For one service, a single VM running Compose is intentionally simpler than managed Kubernetes and has fewer moving parts to explain and maintain. A local Compose-only deployment is an acceptable baseline. Add a VM only if you can explain why a remote host is necessary. Keep the registry and deployment process separate: the versioned image is what the smoke test and rollback refer to.

Before implementation, write short architecture decision records for: where the artifact is stored, how a release is approved, how the deploy identity authenticates, where configuration lives, and what “healthy” means. Compare at least one alternative for each decision.

## Build milestones

### P1.1 — Define service, release, and recovery contracts

**Purpose:** Agree on the success conditions before choosing tooling.

**Work:** Define the API behavior, version identifier, health check, release boundary, rollback target, environment configuration, and network exposure. Draw the request and artifact paths with trust boundaries. Estimate optional VM/registry cost and set a maximum lab lifetime.

**Checkpoint:** Another engineer can tell which commit is running, how a release is authorized, and how to restore the previous release from the design alone.

**Evidence:** Commit an architecture diagram, acceptance table, threat notes, cost/scope note, and at least three decision records.

### P1.2 — Build a testable service

**Purpose:** Make the application small enough to reason about but representative enough to deploy.

**Work:** Implement the API, input validation, structured startup/error logs, `/health`, and `/version`. Add tests for normal behavior and one failure case. Keep secrets and environment-specific values outside the image.

**Checkpoint:** The tests run locally from a clean environment; `/version` reports the injected commit or artifact identifier rather than a hard-coded “latest.”

**Evidence:** Save test output, API examples, and the documented local run command.

### P1.3 — Build a reproducible container artifact

**Purpose:** Package one artifact that can be tested and promoted.

**Work:** Write a minimal Dockerfile, add a health check or equivalent smoke procedure, pin base-image versions deliberately, and use a non-root runtime user where compatible. Build with a commit-based tag, then record the image digest and inspect the final image for secrets and unnecessary build files.

**Checkpoint:** Two builds from the same source/configuration produce an artifact with the expected version identity; a clean Compose run passes the API smoke test.

**Evidence:** Commit the Dockerfile and Compose file, image metadata, build log, and a sanitized container inspection.

### P1.4 — Gate changes in CI

**Purpose:** Prevent broken changes from becoming release candidates.

**Work:** Add pull-request jobs for lint, tests, and image build. Use explicit minimum `GITHUB_TOKEN` permissions; pin third-party actions to reviewed immutable commits or use a lockfile. Make the release job depend on all required checks.

**Checkpoint:** A deliberately failing test blocks the release job; a passing change produces a versioned artifact linked to its commit.

**Evidence:** Save one passing and one failing workflow run with the earliest useful log step identified.

### P1.5 — Configure the target repeatably

**Purpose:** Ensure a fresh host has the prerequisites and boundaries the deployment expects.

**Work:** Use an Ansible playbook to install or verify the container runtime, create an application directory, set nonsecret configuration, and configure only the required service/ports. Make the playbook idempotent; use an inventory for the single disposable host. Skip this milestone for the local-only baseline only if your README explains the equivalent reproducible environment setup.

**Checkpoint:** Running the playbook twice makes no unintended changes on the second run; the service's data/config directories and exposure are explicit.

**Evidence:** Include the playbook, inventory template without private hosts, first-run and second-run summaries, and host setup notes.

### P1.6 — Deploy and verify a versioned release

**Purpose:** Promote the artifact with a visible release identity.

**Work:** Add an explicit approval boundary for deployment. Authenticate the runner with short-lived OIDC where supported or a narrowly scoped, protected credential; never put private keys in the image. Deploy by image digest or immutable version tag, wait for readiness, run `/health` and `/version` smoke checks, and record the result.

**Checkpoint:** The version returned by the running service matches the release artifact; a failed readiness check makes the deployment fail visibly.

**Evidence:** Save the approval, artifact digest, deployment log, and sanitized smoke-test response.

### P1.7 — Practice rollback and diagnose a bad release

**Purpose:** Demonstrate how the operator recovers when a release is wrong.

**Work:** Publish a deliberately broken test version that fails the smoke check, observe the failure, and restore the previous known-good digest using the documented procedure. Do this only in the local fixture or disposable VM. Record the point at which rollback becomes necessary and verify the restored API.

**Checkpoint:** The bad version is identified, the rollback completes without rebuilding source, and the restored `/version` matches the previous artifact.

**Evidence:** Write a short incident timeline with detection, action, result, and one improvement to the release process.

### P1.8 — Prepare the handoff and clean up

**Purpose:** Make the platform understandable to a new team member and safe to stop.

**Work:** Write a README with architecture, clean setup, CI, deployment, configuration, rollback, known limitations, and cost/cleanup. Add a small runbook for failed health checks. Destroy optional lab infrastructure only after checking the exact plan and target.

**Checkpoint:** A reviewer can identify the active version, reproduce the local build, understand the deployment boundary, and follow the rollback/cleanup steps without your help.

**Evidence:** Publish a tagged release or demo, README, runbooks, diagram, decision records, sanitized logs, and cleanup confirmation.

## Verification plan

Run a clean-clone test, a passing CI path, and a deliberately failing test that blocks release. Build and inspect the image; confirm the running `/version` matches its digest or source commit. Deploy to the local fixture or disposable host, fail the health check with a controlled bad version, and restore the prior artifact. Verify network exposure and that no secret appears in Git, workflow logs, or the image. Record each result in a matrix.

## Troubleshooting

- **CI passes but the deployed service is old:** compare the deployed image digest with the release output; do not trust a mutable `latest` tag.
- **Ansible reports changes every run:** check timestamps, generated files, and commands that are not idempotent; prefer state-aware modules over repeated shell commands.
- **Deployment succeeds but smoke test fails:** separate container start, readiness, reverse-proxy routing, and application behavior; inspect the first failing boundary.
- **Rollback cannot pull the previous image:** verify registry retention and credentials before release; keep the tested rollback artifact available.
- **A workflow exposes credentials:** stop the deployment path, rotate the credential, review job permissions and log masking, then verify with a synthetic sentinel.

## Acceptance criteria

- Clean local setup builds and tests without undocumented state.
- A failed test blocks release; a passing release identifies an immutable artifact.
- Deployment runs a health check and confirms the live version matches the artifact.
- A controlled bad release is detected and rollback restores the previous verified version.
- CI/deployment credentials are not committed or printed; host/network scope and optional cost are documented.
- A new learner can follow the README and cleanup runbook.

## Portfolio deliverables

Publish the repository, labeled architecture and trust-boundary diagram, decision records, CI workflow, Docker/Compose and Ansible configuration, artifact identifier, sanitized release and rollback logs, test matrix, runbook, and a 3–5 minute walkthrough. State which parts you personally designed and implemented.

## Stretch goals

- Add Terraform for a small disposable host/network only after the local path works; use plan review and an explicit cleanup gate.
- Add artifact provenance or a dependency/security scan and explain what it covers and misses.
- Add a second environment with a different nonsecret configuration and the same artifact digest.
