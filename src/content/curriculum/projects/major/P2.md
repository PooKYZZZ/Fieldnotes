# Self-Hosted Monitoring & Recovery

## Scenario

A small home-lab service is running, but when it becomes slow or unavailable the operator has no reliable way to see what users experienced, when the issue began, or whether data can be restored. Build a local monitoring and recovery setup for one or two services you own.

## Why this matters

Operating a service means more than drawing charts. A useful system connects a user-visible symptom to a signal, a notification to a response, and a backup to a demonstrated restore. The monitoring stack itself also has limits and can fail independently.

## Learning objectives

- Select service indicators based on user impact and write a small, testable objective.
- Instrument and scrape a bounded set of metrics and useful logs.
- Build an alert that includes an actionable summary, response link, and tested resolution.
- Exercise one controlled outage and one isolated data restore; explain residual risks.

## Prerequisites and setup

Use Docker Compose, a toy service, Prometheus, and Grafana on a local machine or disposable Linux VM. Synthetic requests and data are sufficient; do not ingest household, employer, or personal logs. Bind administrative ports to localhost or protect them with authentication. Keep retention and disk use small.

## Requirements and boundaries

- Observe at least one user-facing availability or error indicator and one resource or latency indicator; define units, scope, and a baseline.
- Use bounded metric labels and sanitize logs. Do not log tokens, request bodies, or personal identifiers.
- Configure scrape intervals, short local retention, one dashboard, and one actionable alert with a tested pending and recovery behavior.
- Add a runbook that starts with evidence collection and safe diagnosis; no automatic remediation is required.
- Back up only a disposable database fixture. Restore to a fresh isolated destination and compare known records.
- Demonstrate what happens when the service fails and when monitoring cannot scrape it. The monitoring stack must not be treated as proof of service availability by itself.

## Architecture and decisions

`service + metrics endpoint → Prometheus → rules → Grafana alert state`

`service logs → sanitized operator investigation`

`disposable database → backup artifact → isolated restore target → integrity + logical comparison`

Local Prometheus/Grafana is sufficient for learning but is not highly available and should not be publicly exposed. Prefer a handful of actionable signals over a broad dashboard. Decide which checks represent user experience, what delay is acceptable for detection, and which dependencies need separate health signals.

## Build milestones

### P2.1 — Define the service and reliability questions

**Purpose:** Choose the operational problem before choosing dashboard panels.

**Work:** Select one or two owned services and define one service-level indicator (SLI), such as successful requests divided by total requests over a lab window. Choose an achievable target for the demo and state its measurement limitations. Add a data-flow diagram, threat boundaries, retention limit, and failure hypotheses.

**Checkpoint:** Every metric and alert answers a stated operator question; user impact is distinguished from host load.

**Evidence:** Commit the SLI definition, architecture diagram, failure table, privacy rules, and local resource/retention budget.

### P2.2 — Instrument service behavior

**Purpose:** Make the service's own outcomes observable.

**Work:** Expose counters for requests and failures plus one latency or resource measure. Use stable labels and structured, sanitized logs. Add a health endpoint whose semantics are explicit; distinguish process liveness from readiness to serve the chosen request.

**Checkpoint:** A deterministic request batch changes the expected counters, and the service still operates when monitoring is stopped.

**Evidence:** Save example metric names/units, sanitized log samples, and instrumentation tests.

### P2.3 — Collect and query baseline data

**Purpose:** Verify the end-to-end collection path before creating alerts.

**Work:** Configure Prometheus scrape targets and retention. Load a normal synthetic request pattern and query the SLI and latency/resource signals. Compare query output with the client-side request totals; do not assume scrape samples are exact event accounting.

**Checkpoint:** Each target reports fresh data, query units are understood, and normal traffic produces the expected trend.

**Evidence:** Include scrape configuration, query expressions, baseline values, and a short explanation of sampling limits.

### P2.4 — Build a focused dashboard and alert

**Purpose:** Help a responder see whether users are affected and where to begin.

**Work:** Create a dashboard with a few panels: service outcome, latency or resource signal, and target health. Define one alert with threshold, evaluation interval, pending duration, clear summary/description, and a runbook reference. Test the rule with `promtool` or a controlled synthetic time series.

**Checkpoint:** An alert message tells the operator what happened, how to inspect it, and which runbook to follow; alert and target-down states are distinguishable.

**Evidence:** Export the dashboard and rule files, test output, and alert rationale.

### P2.5 — Run a controlled incident drill

**Purpose:** Validate detection, diagnosis, and recovery without risking a real service.

**Work:** Stop the toy service or inject a bounded error condition. Capture when the symptom begins, when the alert enters pending/firing, which signals help identify the cause, and when service and alert recover. Avoid triggering failures in household or work systems.

**Checkpoint:** The incident can be repeated, the alert resolves after recovery, and the runbook does not recommend restarting blindly before collecting evidence.

**Evidence:** Write an incident timeline with hypothesis, evidence, action, outcome, and one follow-up improvement.

### P2.6 — Prove backup restoration

**Purpose:** Turn a backup artifact into evidence of recoverability.

**Work:** Generate a small synthetic database fixture, create a consistent backup, restore it into a fresh isolated target, run a database integrity check, and compare known records. Use a separate deliberate mismatch to prove the comparison catches missing or altered data.

**Checkpoint:** Restore verification detects both structural failure and logical mismatch; the original fixture remains unchanged.

**Evidence:** Include source manifest, backup/restore durations, restore check output, and a recovery runbook.

### P2.7 — Review operational limits and hand off

**Purpose:** Make the complete system understandable and safe to reproduce.

**Work:** Document setup, dashboards, alerts, failure drill, restore, retention, port exposure, cleanup, and known blind spots. Stop Prometheus or break its scrape path once to show how monitoring failure appears. Remove only lab data that your cleanup command created.

**Checkpoint:** A new learner can recreate the baseline, trigger the drill, restore the fixture, and identify when the monitoring data itself is unavailable.

**Evidence:** Publish the repository, diagram, dashboard/rule exports, incident report, restore proof, setup and cleanup runbooks, and a short demo.

## Verification plan

Run a baseline, controlled service failure, recovery, monitoring-target failure, and restore drill. Compare the request generator's counts with service metrics; measure alert timing against scrape interval and pending duration; confirm firing and resolved states; restore only the synthetic fixture and compare known records. Review ports, label cardinality, retention, and saved logs for private data.

## Troubleshooting

- **Dashboard shows no data:** check target health from Prometheus's network namespace, scrape path, metric name, label filters, and time range in that order.
- **The alert is late:** calculate scrape interval plus pending period and evaluation delay before changing the threshold.
- **Target is up but users still fail:** inspect the user-visible request indicator; target health only says the scrape endpoint responded.
- **Notifications flood:** group related conditions and refine the alert to actionable symptoms; do not suppress all alerts to silence noise.
- **Restore integrity passes but rows differ:** compare the fixture manifest; database structure and service-level correctness are separate checks.

## Acceptance criteria

- At least two user or operator questions have corresponding documented signals and reproducible queries.
- The dashboard exposes service outcome, one latency/resource view, and monitoring-target health.
- A controlled outage produces a documented alert and a resolved state after recovery.
- Monitoring failure is visible and no admin endpoint is publicly exposed by the default setup.
- A synthetic backup restores to a fresh location and passes integrity plus logical comparison.
- README and runbooks allow another learner to recreate and clean up the lab.

## Portfolio deliverables

Provide the service and Compose configuration, metric contract, dashboard export, alert rules/tests, sanitized incident timeline, backup/restore fixture and results, setup and response runbooks, architecture diagram, and a demo. Explain one signal you deliberately did not alert on and why.

## Stretch goals

- Add a second service and define which signals need service-specific labels versus shared labels.
- Add an external synthetic check from a second local container to compare internal readiness with client reachability.
- Add alert grouping, a local receiver, or a short service-level objective report without adding cloud credentials.
