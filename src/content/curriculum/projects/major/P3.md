# Secure Software Delivery Capstone

## Scenario

A small engineering team needs to release a service without losing track of what is running, who can publish it, how failures are noticed, or how data is recovered. Build and present one end-to-end delivery system that makes those controls observable and testable.

## Why this matters

The capstone combines the work that usually crosses application, platform, security, and operations roles. A successful demo shows how a change moves through the system, what evidence gates it, and what a responder can do when a release or dependency fails.

## Learning objectives

- Turn a scenario into measurable functional, security, reliability, and cost requirements.
- Draw the end-to-end architecture, trust boundaries, data flow, and failure paths.
- Choose a right-sized stack and defend alternatives instead of accumulating tools.
- Demonstrate a verified release, an intentional failure, a recovery path, and an honest portfolio handoff.

## Prerequisites and setup

This is the final integrated build. Learners should be comfortable with Git, containers, a CI system, infrastructure or configuration automation, basic observability, and database backup/restore. Begin with an owned demo service and synthetic data. Local Compose is a complete baseline. Reuse the assessed P1 delivery path and P2 monitoring or recovery assets where appropriate. Ask a reviewer to reproduce a small schema or configuration change from a clean checkout and run a documented recovery check. A cloud provider, Terraform, Kubernetes, and public deployment are optional; use none unless they solve a stated requirement and fit a documented cost/safety boundary.

## Requirements and boundaries

### Required behaviors

- Build a service with tests, a health check, a version endpoint, and one meaningful operation that can be demonstrated.
- Produce a versioned, immutable artifact from a reviewed source revision. A failing required test or build must block release.
- Deploy through one documented and repeatable path. Identify the artifact actually running and verify it with a smoke test.
- Restrict release identity and workflow permissions. Protect configuration and secrets; show that a synthetic secret marker is not committed or printed.
- Collect at least one useful service signal and exercise one controlled outage or bad-release diagnosis.
- Test rollback to a previously verified artifact and restore a synthetic data fixture to an isolated location.
- Include setup, deploy, incident, recovery, and cleanup instructions that another learner can follow.

### Scope and safety

- Do not deploy to an employer, customer, household-critical, or shared production system.
- Use synthetic data and non-sensitive logs. Do not put tokens in repository files, images, screenshots, or progress notes.
- Keep cloud spend optional, time-bounded, and tied to a named scope and cleanup checklist.
- Choose a VM/Compose stack unless Kubernetes solves a clear requirement such as multiple independently operated services or a learning objective. Explain the operational cost of any extra component.
- No automatic destructive infrastructure changes. Review plans and confirm account, project, region, and target before applying or removing resources.

## Architecture and decisions

`source change → review and CI checks → immutable artifact → approval and deployment → health/version verification → metrics and logs`

`                                                        ↘ rollback to prior artifact`

`synthetic database fixture → backup → isolated restore → integrity and logical checks`

Start from the smallest architecture that can satisfy the required evidence. Document trust boundaries, artifact identity, credential flow, configuration source, network ingress, monitoring path, data persistence, and recovery. For each major choice, compare one alternative and name its cost or failure mode. The final system should remain explainable on one diagram.

## Build milestones

### C1 — Frame scope, risks, and acceptance

**Purpose:** Define what the capstone proves and what it intentionally leaves out.

**Work:** Choose the demo service and its user, write measurable requirements, list assets and trust boundaries, identify the main failure modes, and estimate resource/cost limits. Select local Compose or a disposable deployment target and explain why. Set a time-boxed cleanup condition.

**Checkpoint:** Every required behavior maps to an observable test or piece of evidence; excluded services and data are explicit.

**Evidence:** Commit a one-page project charter, threat sketch, acceptance matrix, cost/scope note, and first architecture decision records.

#### Hint 1 — Trace one user action

Choose one meaningful request and follow it through the proposed system: caller, network boundary, application, data store, and observable result. That path will reveal which components and evidence the assignment actually needs before you choose extra tools.

### C2 — Provision and configure the deployment target

**Purpose:** Prepare the bounded environment where the reviewed service will run.

**Work:** Start with a local Compose target; use a disposable VM only when remote deployment is a stated requirement. Configure the runtime, application directory, nonsecret settings, persistence location, and only the required network access. Use Ansible for repeatable host setup when appropriate. If using Terraform, inspect the plan and verify account, region, and resource scope before applying it. Record the expected cleanup command and target.

**Checkpoint:** A clean setup creates only the intended lab resources, and a second configuration run makes no unintended changes.

**Evidence:** Include the target configuration, sanitized first and repeat run output, network/persistence notes, and the reviewed plan or local-only explanation.

### C3 — Build, test, and package the application

**Purpose:** Produce a small, testable service and the artifact that the release path will promote.

**Work:** Implement the API, normal/error behavior, input validation, health and version endpoints, structured logs, and automated tests. Build a minimal container image tied to a source revision; keep runtime configuration external to the image. Create a synthetic database fixture only if the service needs persistence.

**Checkpoint:** A clean local run passes tests; the packaged artifact reports its source revision and produces reproducible health, version, and user-visible results.

**Evidence:** Include test results, local run/build commands, API behavior examples, image identity, and a configuration template with placeholders only.

### C4 — Protect and automate the release

**Purpose:** Ensure only reviewed, passing changes can become a release candidate.

**Work:** Run tests and an image build in CI. Use least-privilege workflow permissions, protect publishing and deployment jobs, review third-party action dependencies, and require the chosen approval boundary. Publish or deploy the immutable artifact from the reviewed source revision. Add a vulnerability or provenance check only if you can explain its result and limits.

**Checkpoint:** A failing test blocks release; a passing reviewed change produces an immutable artifact reference linked to its source revision, and the deployment path can identify that version.

**Evidence:** Save the workflow, artifact identifier, one passing run, one blocked run, approval evidence, and a short supply-chain risk note.

#### Hint 1 — Compare the deployed identity

Record the source revision and the image digest produced from it, then identify what digest the deployment actually runs. A tag such as `latest` is a convenient name, not immutable proof that two environments received the same bytes. Keep configuration differences visible and verify the running version with a smoke check.

### C5 — Add monitoring and actionable alerting

**Purpose:** Give an operator useful evidence about service behavior and a clear first response.

**Work:** Collect one user-facing service signal and one latency or resource signal, with bounded labels and sanitized logs. Add a small dashboard or query view, one alert with an action-oriented message, and a runbook link. Test the rule with a synthetic time series or controlled local condition; do not expose monitoring administration publicly.

**Checkpoint:** A normal baseline is distinguishable from a controlled failure, the alert gives a responder a useful next step, and the service still works when monitoring is stopped.

**Evidence:** Include the dashboard/query, alert rule and test output, baseline values, sanitized example signals, and runbook.

### C6 — Exercise an incident and rollback

**Purpose:** Demonstrate a repeatable response to a failed release or bounded service outage.

**Work:** In the local fixture or disposable target, introduce one controlled bad release or bounded outage. Record the user-visible symptom, signal and alert timing, investigation steps, decision point, and action. If evidence points to the bad release, roll back to the prior known-good immutable artifact and repeat the same health, version, and user-path checks. If the cause is a dependency outage, explain why rollback is inappropriate and demonstrate dependency recovery. Use a distinct bad-release case to verify rollback.

**Checkpoint:** The incident is distinguishable from monitoring failure, the operator identifies the running version, and rollback restores the expected service behavior without rebuilding source.

**Evidence:** Save the alert rule, sanitized incident timeline, diagnosis, rollback output, and one post-incident improvement.

### C7 — Demonstrate data recovery and resource cleanup

**Purpose:** Test recovery and teardown without relying on claims or state alone.

**Work:** Back up a synthetic data fixture, restore it to a fresh isolated target, and check structural integrity plus known records. Point a disposable instance of the service at the restored data and repeat the same user request used before backup. Have a reviewer reproduce a small backward-compatible schema or configuration change from a clean checkout and follow the recovery runbook. If working solo, repeat the handoff from a fresh checkout using only the written procedure and record any missing steps. Review any Terraform destroy plan or Compose cleanup scope before acting. Independently verify the disposable resource scope is empty and explain intentional retention.

**Checkpoint:** The service returns the known fixture from the restored target. The agreed change survives a clean replay, and the rollback or forward-fix procedure preserves the documented behavior. Cleanup removes only this capstone's resources.

**Evidence:** Include before/after manifests, restore checks, cleanup plan or command, and confirmation of the target scope.

### C8 — Audit and present the portfolio result

**Purpose:** Show both the working system and the reasoning behind its boundaries.

**Work:** Run the acceptance matrix from a clean clone or documented reset. Review security, reliability, cost, observability, and maintainability gaps. Write a concise README and record which parts you designed, built, adapted, or used tools to produce. Prepare a live or recorded walkthrough with one success and one failure path.

**Checkpoint:** A reviewer can reproduce the baseline, identify the running artifact, follow one runbook, and understand the most important trade-off and remaining limitation.

**Evidence:** Publish the repository, diagram, decision records, tests, CI evidence, sanitized configuration, runbooks, restore proof, cleanup note, and demo script.

## Verification plan

Use a matrix with at least these cases: normal tests/build, failing test blocks release, artifact identity matches runtime, deployment health succeeds, controlled failure is detected, rollback restores the previous version, backup restore matches synthetic records, and cleanup leaves no untracked lab resource. Re-run the normal path from a clean checkout. Review repository history, workflow permissions, image contents, network exposure, and logs for secret markers before presenting.

## Troubleshooting

- **The wrong image is running:** compare the immutable artifact digest and `/version`; do not infer identity from a mutable tag.
- **The workflow can deploy from an untrusted pull request:** stop, reduce permissions, separate verification from publishing, and ensure untrusted code receives no deployment credential.
- **An alert fires without user impact:** check the signal's relationship to the service outcome and document false-positive behavior before changing thresholds.
- **Rollback restores code but not data:** state whether the change is backward compatible and whether the data migration has a tested reversal or forward-fix procedure.
- **Terraform state says empty but resources remain:** check the provider-scoped inventory and ownership tags; state is not a complete substitute for external inventory.
- **The project is growing into a platform:** map each component to an acceptance requirement and remove anything that adds no demonstrable learning or user value.

## Acceptance criteria

- **Function:** the documented service behavior works, tests pass, and one intentional failure is diagnosed.
- **Repeatability:** another learner can reproduce the local build and the chosen deployment path from the README.
- **Traceability:** the live version maps to a reviewed source revision and immutable artifact.
- **Security:** workflow permissions and deploy identity are scoped; no secrets are committed, baked into the image, or exposed in logs.
- **Reliability:** the controlled issue is detected and a tested rollback restores service behavior.
- **Recovery:** a synthetic backup restores to a fresh target and matches known records.
- **Operations:** a responder has a useful signal, incident steps, and cleanup instructions.
- **Judgment:** the learner can explain architecture choices, rejected alternatives, residual risks, and personal contribution.

## Self-review rubric

Rate each area as familiar, guided, or independent. Link to evidence and record an unresolved gap for each area where the evidence falls short.

- **Functionality** — A fresh checkout reproduces the documented user operation and the expected response.
- **Reliability** — The same user check shows the fault and confirms recovery. A separate check demonstrates that the restore contains known data.
- **Security** — A configuration or permission check shows what the chosen trust boundary allows and denies.
- **Maintainability** — A reviewer can repeat a documented change, identify the active artifact, and follow recovery steps.
- **Cost** — The resource inventory identifies material cost drivers and verifies cleanup or intentional retention.
- **Explainability** — The learner can defend a decision, explain a rejected alternative, and state what the evidence cannot establish.

## Portfolio deliverables

Present one repository with an opening problem statement, reproducible setup, one-page architecture diagram with trust boundaries, a few decision records, tests and workflow, immutable artifact identity, deployment/smoke/rollback evidence, sanitized monitoring view, restore proof, runbooks, cleanup confirmation, limitations, and a short walkthrough. Screenshots support the evidence; they do not replace runnable configuration or logs.

## Stretch goals

- Add a second independent environment using the same artifact and compare configuration drift.
- Add image provenance/attestation verification or a software bill of materials and explain its trust assumptions.
- Add a recovery-time objective and measure a repeatable restore/rollback drill without presenting one lab run as a production guarantee.
- Add Kubernetes only if you state a requirement it satisfies and include the operational work it adds.
