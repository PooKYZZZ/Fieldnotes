# Unverified backup

## Observation

A backup job reports success but the restore procedure fails.

## Investigation

1. Preserve the source backup and record its identifier, checksum, format, timestamp and the exact restore error. Do not test recovery by overwriting the source database or production target.
2. Create a new isolated restore target with restrictive access and use the backup format's documented read-only listing or validation command. Confirm the tool version and required encryption keys without placing key values in output.
3. Compare the backup's schema/version and documented prerequisites with a disposable service copy. Record missing extensions, configuration, permissions or dependent files as separate causes.
4. Restore to a separate empty target only after confirming its exact path. Verify integrity, expected synthetic records and one application-level read using the documented procedure.
5. Measure the restore and application-check intervals separately. A backup checksum or successful backup job proves neither that the application can read the restored data nor that the full service meets its recovery objective.

## Safety constraint

Work only on disposable resources or services you own, and record initial evidence before applying a
fix.

## Hint

A backup is validated by restoration, not by its creation log.

## Completion evidence

Record the preserved source checksum, format/schema validation, separate restore target, database-integrity and application-read checks, and separate measured intervals. State which backup keys, dependencies or service startup steps were not tested.
