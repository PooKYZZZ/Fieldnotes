# Permission denied

## Observation

A service runs interactively under your account but not under its systemd account.

## Investigation

1. Reproduce the failure only in the disposable VM and note the service name, time and exact operation. Do not broaden permissions as a diagnostic shortcut.
2. Read the effective unit identity and working directory:

   ```bash
   systemctl show fieldnotes-demo.service -p User -p Group -p WorkingDirectory -p ExecStart
   id fieldnotes-demo
   ```

   Replace the example account and unit with the lab names. For a system service, an unset `User=` normally means the service runs as root; verify the unit type and effective identity before diagnosing a path-access problem.
3. Inspect every directory component and the specific file, then compare those permissions with the service identity:

   ```bash
   namei -l /srv/fieldnotes-demo/index.html
   ```

4. Read the relevant service journal with `journalctl -u fieldnotes-demo.service --since "10 minutes ago" --no-pager`. Match the first failure time and operation to the inaccessible path.
5. Propose the narrow owner/group or path correction, make it only in the owned VM, and repeat the original service check. Keep unrelated files private.

## Safety constraint

Work only on disposable resources or services you own, and record initial evidence before applying a
fix.

## Hint

Do not solve access problems by making everything world-writable.

## Completion evidence

Show the effective service identity, the first inaccessible path component or file, the matching journal error, the narrow lab-only ownership or permission correction, and a repeatable service check. Confirm that no broad writable permission was added.
