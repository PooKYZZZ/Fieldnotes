# Ansible repeated changes

## Observation

The second run still reports several changed tasks.

## Investigation

1. Confirm the inventory and limit contain only the disposable host. Stop if either selects a shared machine.
2. Run a syntax check, then a check-mode preview and inspect the task recap and changed diff:

   ```bash
   ansible-playbook --syntax-check -i inventory.ini site.yml
   ansible-playbook --check --diff -i inventory.ini site.yml --limit fieldnotes-lab
   ```

   Replace the example host with the exact lab inventory name. Check mode is not a perfect simulation and a diff may expose secrets, so use only synthetic values.
3. Compare two actual runs against the lab target. A second run with unchanged inputs should report no unnecessary changes for tasks whose modules support idempotent behavior.
4. Inspect tasks that use shell/command, timestamps, generated random values, or unconditional handlers. Prefer a state-aware module and run a handler only when its input changes.
5. Introduce one harmless lab drift, rerun the playbook and verify the intended task restores the configured state; then record the rollback or snapshot path.

## Safety constraint

Work only on disposable resources or services you own, and record initial evidence before applying a
fix.

## Hint

Repeated changes are not necessarily harmless.

## Completion evidence

Compare the first and unchanged second-run recaps, show which task was non-idempotent, and record the drift correction and handler behavior. Include the exact single-host limit and the rollback/snapshot outcome.
