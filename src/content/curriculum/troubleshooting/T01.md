# DNS versus HTTP

## Observation

Your laptop resolves the server name, but the API request times out.

## Investigation

1. Set `HOST` and `URL` to the hostname and health path of a service you own; `app.lab.example` is only a placeholder. Record the client and time.
2. On the client, check name resolution and the selected route separately:

   ```bash
   HOST="app.lab.example"
   URL="http://app.lab.example:8080/health"
   TARGET_IP="$(getent ahostsv4 "$HOST" | awk 'NR == 1 { print $1 }')"
   printf 'Resolved address: %s\n' "$TARGET_IP"
   if [ -n "$TARGET_IP" ]; then ip route get "$TARGET_IP"; fi
   ```

   If the lab name does not resolve, do not guess an address. If it resolves, compare that destination with the address you intended to test.
3. On the owned service host, check whether the expected TCP port has a listener with `ss -ltn`. A listener bound only to loopback will not accept a remote client.
4. Retry the exact request with a short timeout using `curl -v --connect-timeout 3 --output /dev/null "$URL"`. Record whether the failure occurs before connection, during TLS, or after an HTTP response. A returned HTTP status means an HTTP server answered, even when the status is an error.
5. Compare the client destination and service listener with the owned firewall or cloud-rule evidence. Change one lab control at a time, then repeat the same request.

## Safety constraint

Work only on disposable resources or services you own, and record initial evidence before applying a
fix.

## Hint

Avoid changing DNS just because a browser displays a generic network error.

## Completion evidence

Record whether name resolution, route selection, TCP connection, TLS and HTTP response succeeded. Support the cause hypothesis with evidence from the failing boundary, make one authorized lab-only change, and repeat the same request to verify it.
