# Linux command line and filesystems

## Scenario

An operator receives an unfamiliar directory and needs a safe, repeatable inventory without opening files one by one or searching personal data.

## Learning objectives

- Create a bounded toy workspace and inventory only files created for this lab.
- Use filters, pipelines, counts and redirection to make a reproducible report.
- Distinguish a successful no-match search from a command error.

## Expected observations
The fixture should contain three files: two with text and one with size `0`. `find` returns relative paths, GNU file type `f`, byte sizes, and the current owner; `sort` makes row ordering reproducible. Searching `sample` should return two matching lines and status `0`; searching an absent word in readable files should return status `1`. A nonexistent path or invalid option is a command error, not an ordinary no-match. `tee` writes its input to both the terminal and report. Unless `pipefail` is enabled, `find | sort | tee` can appear successful when an earlier command failed because the final `tee` succeeded.

## Prerequisites

Complete or study Module 02 in 01_DevOps_Foundations.pdf.

Technical references: [GNU Bash pipelines](https://www.gnu.org/software/bash/manual/html_node/Pipelines.html), [GNU Findutils file information](https://www.gnu.org/software/findutils/manual/html_node/find_html/Print-File-Information.html), and the [GNU grep manual](https://www.gnu.org/software/grep/manual/grep.html).

## Challenge

Practice find, grep, sort, cut, wc, less, head, tail, tee and shell redirection. Compare file contents without
copying answers from a tutorial.

## Build outcome

Build a command-line directory inventory that records names, types, sizes and ownership into a
timestamped report.

## Environment
Use a Linux VM or shell with Bash and GNU Findutils. Work in a new temporary directory containing only toy files; do not search your home directory or collect personal or work data. The `find -printf` format below is GNU-specific. If your platform lacks it, identify the equivalent `stat` fields rather than copying output from another operating system.

## Lab steps
1. **Predict the inventory.** Before running commands, write the three file names you expect to create and what the empty file should report for size.
2. **Create a bounded fixture.** Use a fresh temporary directory, then create two text files, an empty file, and one nested directory. For example:

   ```bash
   work="$(mktemp -d "${TMPDIR:-/tmp}/fieldnotes-a02.XXXXXX")"
   mkdir -p "$work/nested"
   printf 'alpha sample\nbeta\n' > "$work/alpha.txt"
   printf 'sample gamma\n' > "$work/nested/beta.txt"
   : > "$work/empty.txt"
   report="$(mktemp "${TMPDIR:-/tmp}/fieldnotes-a02-report.XXXXXX")"
   ```

   Keep the report outside the fixture so the inventory does not accidentally list its own output.
3. **Build the inventory.** Run `find "$work" -type f -printf '%P\t%y\t%s bytes\t%u\n' | sort | tee "$report"`. The relative path, file type, byte size, and owner appear as columns; the rows should sort consistently. Compare the report with your prediction.
4. **Practice matching and no-match searches.** Search for `sample`, then for a deliberately absent word. Record each exit status. In `grep`, status `0` means a match, `1` means no match, and a value greater than `1` indicates an error such as an unreadable or missing path.
5. **Compare stream handling.** Run the inventory with `>` to replace a separate report, `>>` to append a clearly labeled second run, and `tee` to display and save at once. Avoid redirecting the report into the directory being enumerated.
6. **Check the pipeline boundary.** By default, a pipeline normally returns the status of its last command. Bash `set -o pipefail` makes a failing command in the pipeline visible; Bash `PIPESTATUS` records each command's status, but read it immediately before another command changes it.
7. **Review and clean up.** Check the report and one known file with `head`, `tail`, `wc`, or `less`. Remove only the exact temporary fixture and report you created after recording sanitized evidence.

## Hints
```bash
find "$work" -type f -printf '%P\t%y\t%s bytes\t%u\n' | sort | tee "$report"
grep -Rni --include='*.txt' 'sample' "$work"
find "$work" -type f | wc -l
```

`find -printf` is a GNU extension. Quote paths so spaces remain one argument. If you test the pipeline with `set -o pipefail`, remember that `grep` status `1` is a legitimate no-match outcome when used outside the pipeline; interpret it separately from I/O errors.

## Verification

- The report has one row per expected file and its ordering is reproducible.
- A known sample word is found; a deliberately absent word is not.
- The report exists in the temporary workspace and the pipeline's exit status is understood.
- The note explains the difference between a pipe, `>`, and `>>`.

## Troubleshooting

- **No files appear:** check that `$work` is the temporary directory you created and that the files were saved there.
- **A path with spaces breaks:** quote the complete path.
- **The report is empty:** check redirection order and whether the command writes to standard output or standard error.
- **`grep` returns 1:** the pattern was not found; check the sample text before treating this as a tool failure.

## Cleanup

Remove only the temporary directory you created after checking its exact path. Keep sanitized command output in your learning record; do not use broad cleanup commands.

## Evidence to record

Include the fixture layout, the final sorted inventory, the matching and no-match search results with exit statuses, the report path, and one correction made after an error. Keep the report limited to your toy workspace.
