# Cloud networking, IAM and cost controls

## Scenario

A permitted cloud or lab service can still be unreachable because network rules, guest firewall policy, route and application listener are separate controls.

## Learning objectives

- Draw the approved client-to-service path and inventory each relevant rule.
- Use an isolated test to compare one allowed request with one denied request.
- Make a narrow reversible change only in a lab you own, then verify the boundary again.

## Expected observations
Effective Azure rules combine NSGs associated with the subnet and NIC; a rule's priority and direction matter. The guest firewall and process listener are additional boundaries, not duplicates of the NSG. If using local-only practice, a connection to a stopped listener should fail while the same local address and route remain unchanged. After a narrow rule change, the intended test may succeed while unrelated paths remain denied; the outcome is valid only when the source and destination match your recorded path. A timeout alone is not proof that a particular NSG rule blocked traffic.

## Prerequisites

Complete or study Module 13 in 02_Infrastructure_and_Cloud.pdf.

Technical references: Azure CLI [`az network nic list-effective-nsg`](https://learn.microsoft.com/en-us/cli/azure/network/nic?view=azure-cli-latest), [effective-rule troubleshooting](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem), and [Azure RBAC least privilege](https://learn.microsoft.com/en-us/azure/role-based-access-control/best-practices).

## Challenge

Attempt a denied connection in your own lab, read the NSG rule and host firewall, then fix only the
necessary rule.

## Build outcome

Build a resource inventory and short security review for a single-VM Azure application.

## Environment

Use a local VM, isolated network, or existing cloud resource group that you own and have permission to test. Do not
open public inbound access or alter shared network security rules.

## Lab steps
1. **Choose the safe path.** If you do not already have an isolated lab you own, use the local VM path in this activity. Do not create a cloud VM or open a public port just to complete the exercise.
2. **Draw the request path.** Label the approved client, destination IP, route, subnet/NIC network rules, guest firewall, process listener, and application response. For each boundary, record the direction, protocol, port, source range, and why access is needed.
3. **Collect read-only evidence.** On an authorized Azure VM, identify its NIC and inspect effective NSG rules with `az network nic list-effective-nsg --resource-group "$RG" --name "$NIC"`. Review role assignments at the narrow resource scope. Sanitize principal IDs, subscription IDs, and public addresses before saving output. If using a local VM, inspect `ip route`, `ss -ltn`, and the guest firewall's read-only status instead.
4. **Predict a denied test.** Choose one test connection you expect to fail, state which boundary should deny it, and run only that test from an explicitly authorized client. Record the exact error and correlate it with route, effective rule, guest firewall, and listener evidence. A timeout by itself does not identify the cause.
5. **Make one narrow reversible change only in the isolated lab.** Record the before state, change one lab rule, and repeat the exact allowed and denied tests. Confirm no unrelated port or source range became reachable. Do not edit a shared NSG or expose administration ports publicly.
6. **Review access and cost.** Explain who can change the rule, at what scope, and which attached resources remain. If you created temporary resources for an already-approved lab, compare the final inventory with your starting list and verify cleanup.

## Hints
```bash
az network nic list-effective-nsg --resource-group "$RG" --name "$NIC"
ss -ltn
ip route
```

`az network nic list-effective-nsg` is a read-only inspection command and requires an authorized Azure context and an attached NIC. Review the effective priority and source/destination before deciding a rule is relevant. For access review, ask: principal, role, scope, action needed, and expiration. Do not paste raw tenant/subscription identifiers into your learning record.

## Verification

- The rule inventory names direction, protocol, port, source range, and justification for every allowed connection.
- The denied test is supported by evidence and is not inferred solely from a timeout.
- After the narrow change, the required test succeeds and unrelated paths stay denied.
- The account's permissions and resource cleanup are documented.

## Troubleshooting

- **A timeout is ambiguous:** compare DNS, route, listener, NSG, host firewall, and service logs.
- **A rule appears correct but traffic is denied:** check rule priority and effective rules, then confirm the host
  firewall and process listener.
- **The service is reachable from too many places:** close the lab exposure and restore the snapshot before continuing.

## Cleanup

Restore the saved lab firewall/NSG configuration and verify it. Remove only the disposable resources created for this exercise; never delete a shared rule set.

## Evidence to record

Include an owned lab path diagram, sanitized rule direction/protocol/port/source, evidence from the denied and allowed requests, the narrow change and rollback, and confirmation that unrelated paths stayed denied.

## Self-check

Identify allowed inbound connections, justify each permission and show that unused cloud resources
were removed.
