# Container fundamentals with Docker

## Scenario

A container can be replaced during an update, so an operator needs to know which parts are immutable image content and which state is mounted elsewhere.

## Learning objectives

- Build and run a uniquely named local image with a loopback-only published port.
- Inspect container state, logs, health, network and mount points.
- Recreate the container and verify where a harmless marker persists.

## Expected observations

The API responds through the host's loopback port and container logs correspond to the request. Inspect shows the published host address and mount destinations. A marker written to the named volume remains after replacing only the container; a marker in the writable layer does not. Container state and application health are separate observations.

## Prerequisites

Complete or study Module 08 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Build an image for your status API; inspect logs, health, networks and mounts. Delete and recreate it
while testing whether data persisted.

## Build outcome

Package the Status API in a Dockerfile and document its build/run and shutdown commands.

## Environment

Use Docker Desktop or a local Linux Docker Engine and the Status API source in a disposable working directory.
Use a unique Compose project/container name. Do not run global prune commands or inspect other projects' data.

## Lab steps

1. Build the Status API image and tag it with a local, descriptive version. Review the Dockerfile for copied files,
   exposed ports, user, and startup command.
2. Start one container with its web port bound to loopback; inspect its state, logs, network, and health if a
   health check is defined.
3. Request the local health endpoint and note the listener address used inside versus outside the container.
4. Store one harmless marker in the activity's named volume, remove and recreate only this container, and check
   whether the marker remains.
5. Compare the image, container writable layer, bind mount, and named-volume roles in your notes.

## Hints

```bash
docker image ls
docker ps --filter name=fieldnotes-a08
docker inspect fieldnotes-a08
docker logs fieldnotes-a08
```

Publish ports to `127.0.0.1`, not all host interfaces. Data persistence depends on the storage mount, not on
whether the image or container still exists.

## Verification

- The image builds from the intended context and the application starts with no unexpected privileged settings.
- The local health request succeeds and logs correspond to that request.
- The container can be recreated from the same image; the marker persists only when stored on the named volume.
- The report records exact image tag, container state, port binding, and mount type.

## Troubleshooting

- **Port conflict:** select another unused local port and update the request URL.
- **Container exits:** inspect `docker logs` and the exit code before rebuilding.
- **Health check fails:** distinguish application health from container process state and verify the endpoint path.
- **Marker disappears:** check that it was written inside the mounted volume path, not the container layer.

## Cleanup

Stop/remove only the uniquely named lab container and its test image/tag. Remove the named volume only after confirming it contains no work you need; do not use `docker system prune`.

## Evidence to record

Include the local image tag or ID, loopback port mapping, health/request and log observations, mount destination, marker persistence result after container recreation, and the exact test resources left for cleanup.

## Self-check

Explain an image versus a container, show where state resides, and diagnose a service failing to bind the
expected address.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
