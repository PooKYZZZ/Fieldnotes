# Container fundamentals with Docker

## Scenario

A container can be replaced during an update, so an operator needs to know which parts are immutable image content and which state is mounted elsewhere.

## Learning objectives

- Build and run a uniquely named local image with a loopback-only published port.
- Inspect container state, logs, health, network and mount points.
- Recreate the container and verify where a harmless marker persists.

## Expected observations

The image builds from the small A05 FastAPI app and serves `GET /health` on container port 8000. The published host port is bound only to `127.0.0.1:18080`; the health check reports application response, while `docker ps` also reports container state. The named-volume marker survives removal and recreation when the same volume is mounted; the `/tmp` marker disappears with the old writable layer. The app runs as a non-root UID, and the image ID/digest identifies resolved image content more reliably than its mutable tag.

## Prerequisites

Complete or study Module 08 in 02_Infrastructure_and_Cloud.pdf.

Technical references: Docker [container storage](https://docs.docker.com/engine/storage/), [published ports](https://docs.docker.com/engine/network/port-publishing/), and [image digests](https://docs.docker.com/reference/cli/docker/image/pull/).

## Challenge

Build the A05 Status API image with a reviewed context and pinned dependencies. Inspect its runtime user and health, then recreate the container and verify which marker survives.

## Build outcome

Package the A05 Status API in a non-root Docker image, publish it only on loopback, and demonstrate its health check, logs, image identity, and volume-versus-layer persistence.

## Environment

Use Docker Desktop or a local Linux Docker Engine and the Status API source in a disposable working directory.
Use a unique Compose project/container name. Do not run global prune commands or inspect other projects' data.

## Lab steps

1. **Prepare a small build context.** Copy the A05 `app.py` and tested FastAPI/Uvicorn dependencies into a new directory. Pin versions from a clean virtual environment or lock file; for this disposable exercise, `python -m pip freeze > requirements.txt` records the versions installed in that environment. Add `.dockerignore` entries for `.git`, virtual environments, local `.env` files, credentials, and unrelated files.
2. Create this Dockerfile. It installs the dependencies, uses a non-root runtime UID, provides a writable volume path, and checks the health endpoint:

   ```dockerfile
   FROM python:3.13-slim
   WORKDIR /app
   COPY requirements.txt .
   RUN python -m pip install --no-cache-dir -r requirements.txt \
       && mkdir -p /lab-data \
       && chown 10001:10001 /lab-data
   COPY --chown=10001:10001 app.py ./app.py
   USER 10001:10001
   EXPOSE 8000
   HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
     CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2)"]
   CMD ["python", "-m", "uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
   ```

   `requirements.txt` must pin the tested `fastapi` and `uvicorn` versions. The example base tag can move; record its resolved digest for repeatable release builds.
3. **Build and inspect.** Build only from this reviewed directory: `docker build -t status-api:dev .`. Inspect the image ID, layers, configured user, and build context. Never copy secrets into the image or pass them as build arguments.
4. **Start on loopback only.** Create a named volume and run the uniquely named container:

   ```bash
   docker volume create fieldnotes-a08-data
   docker run --detach --name fieldnotes-a08 --publish 127.0.0.1:18080:8000 --mount source=fieldnotes-a08-data,target=/lab-data status-api:dev
   ```

   The app listens on `0.0.0.0` inside its isolated container network; the host publishes it only on loopback. Do not use privileged mode, mount the Docker socket, or publish on all interfaces.
5. **Verify the running instance.** Request `http://127.0.0.1:18080/health`. Inspect `docker logs`, `docker port`, the configured user, and `.State.Health.Status`. A running process and a healthy HTTP response answer different questions.
6. **Write two harmless markers.** Use `docker exec` to write one marker to `/lab-data/volume-marker.txt` and one to `/tmp/layer-marker.txt`. Stop/remove only this container, then run the same command again with the same volume. Verify the volume marker remains and the `/tmp` marker is absent.
7. **Clean up deliberately.** Remove only this lab container and tag. Remove the named volume only after checking it contains no needed work; do not use global prune commands.

## Hints

```bash
docker image inspect --format '{{.Id}} {{json .RepoDigests}}' status-api:dev
docker inspect --format '{{.Config.User}} {{.State.Health.Status}}' fieldnotes-a08
docker port fieldnotes-a08
docker logs --tail=30 fieldnotes-a08
docker inspect --format '{{json .Mounts}}' fieldnotes-a08
docker exec fieldnotes-a08 sh -c 'printf "volume marker\n" > /lab-data/volume-marker.txt'
docker exec fieldnotes-a08 sh -c 'printf "layer marker\n" > /tmp/layer-marker.txt'
```

The app must bind to `0.0.0.0` inside the container; publish only on host `127.0.0.1`. A tag can move; record an image ID or digest to identify exact content. A named volume and the container writable layer have different lifetimes.

## Verification

- The image contains the A05 API, starts as UID 10001, and returns HTTP 200 with `{"status":"ok"}` through the loopback host mapping.
- Docker reports the configured health check and it becomes healthy after the API responds; container running state is reported separately.
- The exact image ID/digest, host-port binding, runtime user, and volume mount are recorded.
- After container recreation, only the named-volume marker persists; the writable-layer marker is absent.

## Troubleshooting

- **Build cannot find a dependency:** confirm the requirements/lock file is in the reviewed context and matches the A05 app.
- **Container exits:** inspect bounded logs and the exit code; check the module name, dependencies, and command.
- **Health check fails:** compare the `/health` path/port and application bind address; distinguish app response from Docker state.
- **Port conflict or exposure:** choose another loopback host port and verify `docker port` shows `127.0.0.1`, not all interfaces.
- **Marker is missing:** verify `/lab-data` is mounted and the same named volume was reused.

## Cleanup

Stop/remove only the uniquely named lab container and its test image/tag. Remove the named volume only after confirming it contains no work you need; do not use `docker system prune`.

## Evidence to record

Include the reviewed Dockerfile/build context, dependency lock method, local image tag plus image ID/digest, runtime user and health result, loopback port mapping, logs, mount destination, marker persistence after recreation, and cleanup state. Exclude secrets and unrelated build-context files.
