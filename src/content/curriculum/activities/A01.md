# How computers and operating systems work

## Prerequisites

Complete or study Module 01 in 01_DevOps_Foundations.pdf.

## Environment

Use a disposable Ubuntu virtual machine with a snapshot you can restore. Inspect only a process owned by your user. Do not change system settings or install tools for this exercise.

## Lab steps

1. **Prepare the VM.** Record its virtual CPU, memory, disk, network adapter, and the snapshot you can restore.
2. **Inspect a running process.** Choose an application you recognize and record its PID, parent PID, command, resident memory, and open file descriptors.
3. **Explain the operating-system interaction.** Draw and explain the path from the application through a system call and the kernel to storage or a device. Connect that explanation to the process you inspected.
4. **Verify and reflect.** Confirm the PID still exists, note any permission restriction without bypassing it, and record the commands, observed result, one failure case, and what you learned.

## Challenge

Draw a diagram from application to syscall to kernel and disk. Open a process monitor; find a running
application, its parent, memory footprint and open handles.

## Build outcome

Set up a disposable Ubuntu VM and document its virtual CPU, memory, disk, network adapter and
snapshot procedure.

## Evidence to record

One short readme/note containing expected result, actual result, commands or test case
evidence, and a failure case; avoid full solution copy-pastes.

## Hints

Start with a process you recognize. In the VM, list its process ID, parent ID, command, and resident memory:

```bash
ps -eo pid,ppid,comm,rss --sort=-rss | head
```

After choosing a process ID from that list, inspect its details and open file descriptors:

```bash
read -r -p "PID to inspect: " PID
ps -o pid,ppid,comm,rss -p "$PID"
ls -l "/proc/$PID/fd"
```

The `rss` value is reported in KiB. Access to another user's file descriptors may be restricted; use a process you own rather than elevating privileges.

## Verification

- The process listing shows a live PID, its parent PID, command name, and resident memory.
- The selected process details still show that PID. If it exited, choose another process and repeat the check.
- The file-descriptor listing is available for a process you own; explain any permission restriction you encounter without trying to bypass it.
- Your diagram connects an application request through a system call and the kernel to storage or a device.

Record the command output or a sanitized screenshot and explain what each observation confirms. A diagram alone is not evidence that a command ran.

## Troubleshooting

- **The PID no longer appears:** the process may have exited between commands. Choose another live process and rerun the checks.
- **The descriptor listing is denied:** process permissions can restrict inspection. Choose a process owned by your user; do not use `sudo` to bypass that boundary.
- **The memory value seems large:** `rss` is resident memory in KiB, not the process's virtual address-space size.

## Self-check

Explain what happens when an application starts, what is lost on reboot, and which boundary an
application must cross to access a file.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?

## Cleanup

Save only sanitized notes or evidence. Shut down the disposable VM when you finish. Keep or remove the VM according to your own storage plan; do not delete a VM that contains work you still need.
