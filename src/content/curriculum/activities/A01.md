# Investigate a running Linux process

## Scenario

You are the on-call operator for a small Ubuntu service. A teammate says the service feels slow and suspects a stuck process. Before anyone restarts it, investigate one process you own in a disposable VM and explain what its state can tell you about an application request. Gather evidence without changing the service.

## Learning objectives

- Find a live process owned by your account and identify its PID, parent PID, command, and resident memory.
- Check the process owner, status, and open file descriptors without crossing permission boundaries.
- Explain how an application request reaches the kernel and why a file read does not always require a physical disk access.

## Expected observations

The process table should contain one row for each live process under your user ID. Values are machine-specific; this is a shape to interpret, not measured output:

```text
PID  PPID  UID       COMMAND  RSS
<id> <id>  <your uid> <name>  <KiB>
```

Your process list and RSS values will vary by machine and may change between checks. Use actual output in your note; the example is illustrative only.

## Prerequisites

Complete or study Module 01 in 01_DevOps_Foundations.pdf.

## Environment

Use a disposable Ubuntu VM with a snapshot you can restore. Inspect only processes owned by your account. Do not change system settings or install tools for this activity.

## Lab steps

1. **Confirm your account.** In the VM, run `id -u` and note the user ID; you will use it to filter the process list and confirm ownership.

2. **Choose a process you own.** List processes for your user and select a familiar one that is still running:

   ```bash
   ps -u "$(id -u)" -o pid,ppid,uid,comm,rss --sort=-rss | head -n 8
   ```

   `PID` identifies the process, `PPID` its parent, `UID` its owner, `COMMAND` its short name, and `RSS` the resident memory reported in KiB. The owner filter limits this list to your account.

3. **Inspect the selected process.** Enter a PID from your list. The check below confirms it is still visible under your user before reading its status and descriptors:

   ```bash
   read -r -p "PID from the list: " PID
   if [[ "$PID" =~ ^[0-9]+$ ]] \
     && ps -u "$(id -u)" -o pid= -p "$PID" \
       | awk -v pid="$PID" '$1 == pid { found=1 } END { exit !found }'; then
     ps -o uid,pid,ppid,comm,rss -p "$PID"
     grep -E '^(Name|Pid|PPid|Uid|VmRSS):' "/proc/$PID/status"
     ls -l "/proc/$PID/fd"
   else
     printf 'Choose a live PID from your own process list.\n'
   fi
   ```

   Compare the UID and PID with the earlier listing. `VmRSS` is another view of resident memory. Descriptor numbers `0`, `1`, and `2` commonly refer to standard input, output, and error; other links depend on what the process is doing. If the process exits between checks, choose another from your list.

4. **Explain the request path.** As Figure 1 shows, application code asks for an operation through a library, crosses the system-call boundary, and receives data or an error from kernel services. The kernel checks access and consults filesystem or cached data; storage is read only if the needed data is not already available. Connect one process observation to this path without claiming that the process listing proves a disk read.

   ![A file read travels from application code through a library and system-call boundary to kernel checks and filesystem or cache; storage is accessed only if needed, and the result returns to the application.](/diagrams/module01/syscall-file-read.svg "Figure 1. A file request crosses into kernel services; cached data may avoid a physical storage access.")

## Hints

If your process exits before you inspect it, choose another from the same owner-filtered list. Do not use `sudo` to inspect another account.

**Optional extension — skip this for the core activity.** If `strace` is already installed and the VM permits tracing, observe a harmless read without attaching to another process:

```bash
if command -v strace >/dev/null 2>&1; then
  trace_file="$(mktemp)"
  if strace -e trace=openat -o "$trace_file" -- cat /etc/os-release >/dev/null; then
    grep -m 2 'openat(' "$trace_file"
  else
    printf 'Tracing is restricted in this VM; skip this extension.\n'
  fi
  rm -f -- "$trace_file"
else
  printf 'strace is not installed; skip this extension.\n'
fi
```

An `openat` line shows a system-call name, its path argument, and a returned descriptor or error. It does not prove that the file was read from a physical disk. Record a restriction rather than changing security settings.

## Verification

- The selected PID appears in the owner-filtered process list, and its UID matches your account.
- The status file reports the selected process; the descriptor listing describes resources currently open for it.
- Your explanation distinguishes a system-call request from the possibility of cached data, and your note cites actual command output rather than the illustrative row above.

## Troubleshooting

- **The PID is gone:** the process may have exited. Choose another live process from your user-filtered listing and repeat the check.
- **Status or descriptors are unavailable:** choose a process owned by your account. Do not bypass permissions with `sudo`.
- **RSS looks large:** RSS is resident memory in KiB, not total virtual address space.
