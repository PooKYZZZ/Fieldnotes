# How computers and operating systems work

## Scenario

During an incident, an operator needs to distinguish a running program from the process the operating system is scheduling, then explain how that process requests kernel services.

## Learning objectives

- Identify a live process owned by your account and relate its PID and parent to the process table.
- Inspect resident memory and open descriptors while respecting ownership boundaries.
- Explain how a user-space request crosses a system-call boundary and how the kernel returns a result.

## Expected observations

Your chosen process appears as one live row in `ps` while it exists. This is the output shape to interpret; placeholders are illustrative, not measured results:

```text
PID  PPID  UID       COMMAND  RSS
<id> <id>  <your uid> <name>  <KiB>
```

PID identifies the process, PPID its parent, and RSS is resident memory reported in KiB; the value can change between observations. Entries under `/proc/PID/fd` represent open descriptors, including standard input, output and error. They show what that process currently has open, not every resource it may use.

## Prerequisites

Complete or study Module 01 in 01_DevOps_Foundations.pdf.

## Environment

Use a disposable Ubuntu virtual machine with a snapshot you can restore. Inspect only a process owned by your user. Do not change system settings or install tools for this exercise.

## Lab steps

1. **Prepare the VM.** Record its virtual CPU, memory, disk, network adapter, and the snapshot you can restore.
2. **Choose a process you own.** List only processes running under your user ID, then choose one that is still active. The values vary between machines:

   ```bash
   ps -u "$(id -u)" -o pid,ppid,uid,comm,rss --sort=-rss | head -n 8
   ```

   The `UID` column lets you confirm ownership; `PID` identifies the process and `PPID` its parent. RSS is resident memory in KiB, not total virtual memory.

3. **Inspect the selected process.** Enter one PID from your listing and confirm its UID is yours before reading its details:

   ```bash
   read -r -p "PID to inspect: " PID
   ps -o uid,pid,ppid,comm,rss -p "$PID"
   grep -E '^(Name|Pid|PPid|Uid|VmRSS):' "/proc/$PID/status"
   ls -l "/proc/$PID/fd"
   ```

   The first row describes the process at the time of the check. `VmRSS` is a separate status-file view of resident memory. The descriptor directory contains links for resources that are open now; descriptors `0`, `1`, and `2` are commonly standard input, output, and error. A short-lived process can exit between commands, so repeat with another owned process if the PID disappears.

4. **Observe one system call if the tool is already available.** This optional trace starts a harmless `cat` process owned by you; it does not attach to or change the process you inspected. Do not install `strace` for the activity:

   ```bash
   if command -v strace >/dev/null 2>&1; then
     trace_file="$(mktemp)"
     if strace -e trace=openat -o "$trace_file" -- cat /etc/os-release >/dev/null; then
       grep -m 2 'openat(' "$trace_file"
     else
       printf 'Tracing is restricted in this VM; continue without installing tools.\n'
     fi
     rm -f -- "$trace_file"
   else
     printf 'strace is not installed; skip this optional observation.\n'
   fi
   ```

   An `openat` line shows a system-call name, its file/path arguments, and the returned descriptor or error. It confirms a request crossed the interface; it does not prove that a physical disk read occurred. If the VM restricts tracing, record that limitation rather than changing its security settings.

5. **Explain the boundary.** As Figure 1 shows, application code asks for an operation, enters a kernel service through a system call, and receives data or an error. The kernel may consult a cache or filesystem and device; a request does not guarantee that physical storage is accessed every time. Connect one observation from your process to the explanation.

   ![A file read travels from application code through a library and system-call boundary to kernel checks and filesystem or cache; storage is accessed only if needed, and the result returns to the application.](/diagrams/module01/syscall-file-read.svg "Figure 1. A file request crosses into kernel services; cached data may avoid a physical storage access.")

6. **Verify and reflect.** Repeat the PID check, explain what each field confirms, note any permission restriction without bypassing it, and record one failure case and what you learned.

Use one process you own to connect an observable process detail to the path an application takes through the operating system.

## Hints

Start with a process you recognize. In the VM, list its process ID, parent ID, command, and resident memory:

```bash
ps -u "$(id -u)" -o pid,ppid,uid,comm,rss --sort=-rss | head -n 8
```

After choosing a process ID from that list, inspect its details and open file descriptors:

```bash
read -r -p "PID to inspect: " PID
ps -o uid,pid,ppid,comm,rss -p "$PID"
ls -l "/proc/$PID/fd"
```

The `rss` value is reported in KiB. Access to another user's file descriptors may be restricted; use a process you own rather than elevating privileges.

## Verification

- The process listing shows a live PID, its parent PID, command name, and resident set size (RSS), reported in KiB.
- The selected process details still show that PID. If it exited, choose another process and repeat the check.
- The file-descriptor listing is available for a process you own; explain any permission restriction you encounter without trying to bypass it.
- Your diagram correctly connects an application request through a system call and the kernel to storage or a device.

Explain what each observation confirms. A diagram alone is not evidence that a command ran.

## Troubleshooting

- **The PID no longer appears:** the process may have exited between commands. Choose another live process and rerun the checks.
- **The descriptor listing is denied:** process permissions can restrict inspection. Choose a process owned by your user; do not use `sudo` to bypass that boundary.
- **The memory value seems large:** `rss` is resident memory in KiB, not the process's virtual address-space size.
