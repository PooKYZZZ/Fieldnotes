# Investigate a running Linux process

## Scenario

A teammate reports that an application is behaving unexpectedly and asks whether its process is still running. Before restarting anything, gather evidence from one process you own in an Ubuntu VM. Follow its identity and current state through `ps`, `/proc`, and systemd so you can explain what Linux reports—and what this first check cannot tell you about the application.

## Learning objectives

- Explain why Linux uses numeric user and process IDs when inspecting processes.
- Select one process owned by your account and read its PID, parent, effective UID, state, and resident-memory estimate.
- Compare that snapshot with `/proc`, inspect accessible file descriptors, and check a systemd unit relationship.
- Separate observed facts from interpretations and identify what further evidence a real service investigation would need.

## Prerequisites

Open a disposable Ubuntu VM with terminal access and a regular, non-root account. Before you start, confirm you can restore or remove the VM, have console access if a session breaks, and can run the read-only commands without installing tools. Review [Processes and threads in Module 01](/modules/01/lessons/m01-l02) first if needed, and use the [lab-readiness checklist](/guide#lab-readiness) to scope the environment. The activity reference PDF is an optional supplement.

Use the [Linux process status reference](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html) and [systemctl manual](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html) when interpreting results; the activity links to the relevant pages beside each task.

## Environment

Use a disposable VM and the read-only commands below. Do not use `sudo`, stop a process, change settings, or install tools. Keep saved observations sanitized. Confirm the target is the VM you selected before running each command; the activity should not change any system state.

## Lab steps

1. **Confirm your account.** Linux uses numeric user IDs in ownership and access checks; an account name is easier for a person to recognize. These two checks establish which identity is running your commands. The UID will scope your process search in Task 2.

   ```bash
   id -un
   id -u
   ```

   The first line prints your account name; the second prints its effective numeric UID. Values vary by machine. UID `0` is root, so switch to a regular account before continuing.

   **Record:** the numeric UID you will use to find your process. Keep the account name only if it helps interpret your note.

2. **Choose one process you own.** If a teammate asks about an application, begin with a process you can inspect under your own account. Its PID identifies this particular process instance. Before looking at the rows, predict which values might change if you take another snapshot later.

   ```bash
   ps -u "$(id -u)" -o pid,ppid,euid,stat,rss,comm --sort=-rss | head -n 8
   ```

   Select a familiar row that is still running. `PPID` is its immediate parent; `EUID` is the identity used for file-access checks; `STAT` is a point-in-time state; `RSS` estimates resident physical memory in KiB; and `COMMAND` is a short process name. These fields describe a snapshot, not whether a service is slow or stuck. See [`ps(1)`](https://man7.org/linux/man-pages/man1/ps.1.html) for the field definitions.

   **Record:** the PID and sanitized row values with your prediction. Revisit that prediction while comparing the second snapshot in Task 3.

3. **Compare that PID with `/proc`.** `ps` gives an overview; Linux also exposes process information through the `/proc` pseudo-filesystem. Compare the same process across both views. Do not select a different PID unless the original has exited.

   Replace `1234` with the PID from Task 2, then run these checks in the same terminal:

   ```bash
   PID=1234
   ps -p "$PID" -o pid,ppid,euid,stat,rss,comm
   grep -E '^(Name|State|Pid|PPid|Uid|VmRSS):' "/proc/$PID/status"
   ls -l "/proc/$PID/fd" | head -n 12
   ```

   Compare PID, parent PID, effective UID, state, and memory. `Uid:` lists real, effective, saved, and filesystem IDs. `VmRSS` is a resident-memory estimate and Linux documents it as potentially inaccurate. The descriptor directory shows links for resources open at that moment. Descriptors `0`, `1`, and `2` commonly represent standard input, output, and error, but their destinations vary. Separate commands sample at different times, so a small RSS difference is not automatically a mistake. See [`proc_pid_status(5)`](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html) and [`proc_pid_fd(5)`](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html).

   **Record:** which fields agreed, changed, or were unavailable; what that suggests; one limitation; and a descriptor's role or resource type. Do not save its target path. If the PID disappeared or access was denied, record that instead of bypassing the restriction.

4. **Check its systemd relationship.** systemd groups managed work into units. A `.service` describes a managed service; a `.scope` tracks processes started outside a service unit, such as a login session. This is different from `PPID`, which names only the immediate parent.

   ```bash
   systemctl status "$PID" --no-pager
   ```

   The result may identify a `.service`, `.scope`, another unit, or say that the PID cannot be mapped or the manager is unavailable. A unit can point you toward the manager responsible for a process; it does not show whether the application is healthy. See the [`systemctl` manual](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html).

   **Record:** the unit type and name, or the exact limitation. Treat either result as information about this lookup, not a pass/fail test.

5. **Write a conclusion for the teammate.** Use your Task 1–4 notes. State which process you inspected, cite one or two observations you actually made, and explain what they support. Then say what the evidence cannot establish and name one useful next check before anyone changes a real service. No new command is needed for this step.

   **Record:** a short conclusion that separates observation from interpretation, names one evidence limit, and recommends a next check. A process visible in `ps` existed at that instant; that alone does not show it answered requests or explain the reported behavior.

## Expected observations

- `ps` and `/proc` should usually describe the same selected process, although values can change and RSS figures are estimates.
- The descriptor list shows resources open at that moment if your account can inspect them; it does not show whether they are active.
- systemd may identify a service, a scope, another unit, or no unit. None of those outcomes alone establishes application responsiveness.

## Challenge

Trace one process through the three Linux views, then explain what the evidence supports and where your confidence must stop.
