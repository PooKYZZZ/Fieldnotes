# Investigate a running Linux process

## Scenario

A technician is learning how to inspect a running application before helping with a service investigation. In a disposable Ubuntu VM, you will choose one process you own, compare the process table with `/proc`, and ask systemd which unit contains its PID. The aim is to learn what these observations can tell you—and what they cannot establish about a service's responsiveness.

## Learning objectives

- Find a running process owned by your account and identify its PID, parent PID, effective UID, state, and resident memory.
- Compare process-list output with the corresponding information in `/proc` and inspect accessible file descriptors.
- Check whether systemd associates the process with a service or scope.
- Explain the limits of a point-in-time process snapshot and write a concise, reproducible investigation note.

## Prerequisites

Use a normal user account in an Ubuntu VM with a terminal. Review Module 01 in `01_DevOps_Foundations.pdf` if you have not studied process and operating-system basics yet.

## Environment

Use a disposable Ubuntu VM. Inspect only processes running under your account. These commands read system information; do not use `sudo`, stop a process, change settings, or install tools. Save only sanitized findings: descriptor targets, command arguments, and unit names can include private paths or other identifying details.

## Lab steps

1. **Confirm your account.** Run these commands and note your user name and numeric user ID:

   ```bash
   id -un
   id -u
   ```

   Linux credentials include real and effective user IDs. The process search in the next task uses your numeric ID to select processes whose effective UID matches your account.

2. **Choose one process you own.** List a few processes for your effective user ID, with the largest resident sets first:

   ```bash
   ps -u "$(id -u)" -o pid,ppid,euid,stat,rss,comm --sort=-rss | head -n 8
   ```

   `PID` identifies a process; `PPID` is its immediate parent; `EUID` is its effective user ID; `STAT` is its current state; `RSS` is resident memory in KiB; `COMMAND` is the short command name. Choose a familiar row that is still present. Most idle programs often show `S` (interruptible sleep); `R` means running or runnable, `D` means uninterruptible sleep, `T` stopped, and `Z` zombie. These are snapshots, not diagnoses of a slow or stuck service. See [`ps(1)`](https://man7.org/linux/man-pages/man1/ps.1.html) for the process-selection and output-field definitions.

   Record the row you chose, then predict which values might change if you check again later.

3. **Compare the process listing with `/proc`.** Replace `1234` with the PID from your row, then run:

   ```bash
   PID=1234
   ps -p "$PID" -o pid,ppid,euid,stat,rss,comm
   grep -E '^(Name|State|Pid|PPid|Uid|VmRSS):' "/proc/$PID/status"
   ls -l "/proc/$PID/fd" | head -n 12
   ```

   Confirm that `ps` still shows the same PID and compare its parent, effective UID, state, and RSS with your first observation. In `Uid:` the four values are real, effective, saved, and filesystem IDs; ordinary processes often show the same number in each position. `VmRSS` is another resident-memory estimate, in KiB. Linux documents this figure as approximate, so a difference from `ps` is possible; both values are estimates. See [`proc_pid_status(5)`](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html) and [`proc_pid_fd(5)`](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html) for the status fields and descriptor links.

   The descriptor directory contains symbolic links for resources the process currently has open. Descriptors `0`, `1`, and `2` commonly refer to standard input, output, and error; other entries can refer to files, pipes, sockets, or other kernel objects. Record a resource type or role, not a private path. If the process exits or access is denied, choose another row from your own list; do not bypass the restriction.

4. **Check the process's systemd unit.** On Ubuntu, ask systemd about that PID:

   ```bash
   systemctl status "$PID" --no-pager
   ```

   Note the unit name and whether it is a `.service` or a `.scope`. A scope can represent a login session; not every process is a service. `PPID` describes the immediate parent process, while the unit describes a systemd-managed group. If the command says systemd is unavailable, cannot identify the PID, or denies access, record that result and continue. This read-only check does not establish application health. The [systemctl manual](https://www.freedesktop.org/software/systemd/man/latest/systemctl) documents PID-to-unit status lookup.

5. **Connect your observations to an operating-system request.** Read Figure 1 and explain, in your own words, how application code asks the kernel to perform an operation. A process row, memory estimate, or open descriptor does not show that a request completed, that the application is responsive, or that storage was read from a physical disk.

   ![Application code calls a library, crosses the system-call boundary into kernel services, and receives data or an error. Filesystem and cached data may satisfy a request without physical storage access.](/diagrams/module01/syscall-file-read.svg "Figure 1. A file request enters kernel services; cached data may avoid physical storage access.")

   The Linux [`intro(2)` manual](https://man7.org/linux/man-pages/man2/intro.2.html) explains how library wrappers invoke system calls.

## Expected observations

- The PID and effective UID in `ps` match your selected process and the `/proc` status. Parent, state, and resident memory describe a moment and can change between commands.
- The descriptor listing shows resources currently open if access is allowed; it does not show whether they are active. `systemctl` may identify a service, a session scope, another unit, or no unit.
- A process state, RSS estimate, open descriptor, or unit name alone does not establish application responsiveness or physical disk activity.

## Challenge

Use one process you own to explain how Linux identifies a process and what its current operating-system information can—and cannot—tell you.

## Build outcome

Create a concise investigation note with enough sanitized evidence for you to repeat the checks and explain your conclusions.

## Evidence to record

Include the commands and sanitized process values, one `/proc` or descriptor observation, the systemd lookup result (or limitation), and one conclusion with its evidence boundary.

## Hints

- If a PID disappears between commands, select another process from the same user-filtered list and repeat the comparison.
- If the descriptor listing includes private paths, record only the kind of resource it represents. Never copy a full command line, socket address, or path into the learning record.
- A `.scope` is a managed group such as a login session; it does not mean that the process is a long-running application service.

## Verification

- Your note names the commands and records a sanitized PID, PPID, effective UID, state, and RSS value from the same process.
- You distinguish what the output shows from what you infer, including whether systemd mapped the PID to a unit.
- You explain the system-call boundary and avoid treating a process snapshot as proof of a slow application or physical storage read.

## Troubleshooting

- **The process has exited:** choose another familiar process from the first listing and update the PID before running the `/proc` commands.
- **`/proc` or the descriptor list is unavailable:** inspect only your own process and record the permission result. Do not use `sudo`.
- **`systemctl` cannot map the PID:** note that no unit was identified. Containers, user sessions, and non-systemd environments can have different process and unit views.
- **RSS changed between checks:** this is a point-in-time estimate. Record when you observed it rather than expecting a fixed value.

## Self-check

What does your process state say at the instant you checked? What additional measurements would you need before claiming an application was slow or stuck?

## Independent reflection

Which observation most changed your understanding of the relationship between a process and a service manager? What would you investigate next during a real performance incident?

## Cleanup

The activity makes no system changes. Save only sanitized findings, then shut down the disposable VM. Keep or remove the VM according to your own storage plan.
