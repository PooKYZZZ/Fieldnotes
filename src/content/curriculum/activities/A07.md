# Git, collaboration and technical documentation

## Scenario

A teammate needs a change reviewed, but two people edited the same line and Git cannot choose a correct merge automatically.

## Learning objectives

- Create branches and inspect changes in a new local practice repository.
- Resolve one harmless text conflict deliberately and inspect the resulting graph.
- Separate local Git evidence from hosted pull-request review.

## Expected observations
The merge should stop with an unmerged path and conflict markers in `status.txt`; this is an expected state, not repository corruption. After your resolution, `git diff --check` should report no whitespace errors, `git status --short` should be empty after the merge commit, and the graph should show both branch histories. Local Git evidence proves only the operations performed in that repository; it does not stand in for hosted review or CI.

## Prerequisites

Complete or study Module 07 in 01_DevOps_Foundations.pdf.

Technical references: [`git switch`](https://git-scm.com/docs/git-switch), [`git merge`](https://git-scm.com/docs/git-merge), and GitHub [pull request guidance](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests).

## Challenge
Create a local feature branch, review a harmless text change, and resolve one deliberate merge conflict. A remote pull request is an optional extension after the local workflow is understood; the required evidence is the local branch, conflict, resolution, and clean result.

## Build outcome

Publish a lab repository with a clear README, setup, limitations, security notes and changelog.

## Environment

Use a new local practice repository. If you want a pull request, use a throwaway remote repository with no secrets or
production deployment; a local merge exercise is sufficient for the learning objective.

## Lab steps
1. **Create an isolated repository.** In a new directory, initialize a local repository with a `README.md` and a `status.txt` line such as `status=planned`. Configure a local author name and an email ending in `example.invalid` for this repository only. Do not use your real project repository.
2. **Create the first branch.** Commit the baseline, create `change-a`, change the line to `status=checked`, and commit. Before each commit inspect `git status --short` and `git diff`; stage only the file you changed.
3. **Create a competing edit from the baseline.** Switch back to `main`, create `change-b`, change the same line to `status=blocked`, and commit.
4. **Predict, then merge.** Switch to `change-a` and merge `change-b`. Git should stop with a conflict because both branches changed the same line. Run `git status` and read the conflict markers. Compare the base and both proposed values before choosing an explicit final value.
5. **Resolve and verify.** Edit only `status.txt`, remove every conflict marker, run `git diff --check`, stage that file, and complete the merge with `git merge --continue`. Confirm `git status --short` is empty and inspect `git log --oneline --graph --decorate`.
6. **Document the collaboration boundary.** Add setup and reproduction steps to the README. Explain that the local graph proves a local merge occurred; it does not prove a hosted pull request, review, or CI check.
7. **Optional remote practice.** If you want to open a pull request, use a throwaway repository without secrets or deployment workflows. Keep credentials out of remote URLs, terminal history, and screenshots.

## Hints
```bash
git status --short
git diff
git merge --abort
git log --oneline --graph --decorate
```

Use `git merge --abort` only while the deliberate lab merge is still in progress and only in this new practice repository. Read the conflict before editing; do not choose `--ours` or `--theirs` without understanding which branch each name means. Stage only the resolved file.

## Verification

- The feature branch and merge are visible in the commit graph.
- No conflict markers remain and the resolved line reflects an explicit choice.
- The final diff contains only intended files and the README instructions work from a clean clone.
- The evidence distinguishes local Git verification from a hosted pull request review.

## Troubleshooting

- **Git refuses to merge:** inspect `git status` first; finish or cancel only the operation created for this lab.
- **Conflict markers remain:** search the practice repository for `<<<<<<<`, `=======`, and `>>>>>>>`.
- **Unexpected files are staged:** unstage only those files after verifying their paths; do not discard them.
- **Remote authentication fails:** complete the local exercise and do not place a token in the remote URL or README.

## Cleanup

Keep or delete the throwaway repository according to your preference. If you used a remote, close/delete only the practice PR/repository you created and preserve any personal notes you want to keep.

## Evidence to record

Include branch names, the relevant before/after diff, conflict resolution choice, status and commit graph, verification performed, and the local repository README. Do not include credentials or imply a hosted review occurred.

## Self-check

Explain what will be committed, recover from a merge conflict and let another person reproduce the lab
from the README.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
