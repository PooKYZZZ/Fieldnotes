# Logs, metrics and traces

## Prerequisites

Complete or study Module 16 in 03_Operations_and_Security.pdf.

## Challenge

Generate good and bad requests; correlate a timestamped error log with a metric rise; inspect how an
application exposes /metrics.

## Build outcome

Instrument the Status API with structured logs and request counters, then create a short
troubleshooting note.


## Environment

Run the Status API in a local container or disposable VM with synthetic requests and logs. Use no real user data,
credentials, or public traffic.

## Lab steps

1. Add structured request logs with a timestamp, route, status, and request identifier. Exclude authorization
   headers, tokens, query secrets, and personal data.
2. Add a request counter labeled by a small bounded set such as route and status class; do not label by raw URL,
   user ID, or request ID.
3. Generate one successful health request and one controlled 404 or application error, recording their timestamps.
4. Inspect the logs and `/metrics` output. Compare the error count with the test requests and explain what each
   signal can establish.
5. Write a short incident note that correlates one request to its log entry and describes whether the symptom is
   isolated or widespread in this small sample.

## Hints

```bash
curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8000/does-not-exist
curl -s http://127.0.0.1:8000/metrics
```

Use a bounded metric label set. A single local sample is not enough to claim production availability or user impact.

## Verification

- Each synthetic request has a timestamped log with status and a correlation identifier.
- The metrics counter changes by the expected amount and does not expose high-cardinality or sensitive labels.
- The note distinguishes logs (individual events), metrics (aggregated measurements), and traces (request path spans).
- Evidence contains only synthetic data and sanitized outputs.

## Troubleshooting

- **Counter does not change:** verify the instrumented handler and scrape/request path.
- **Metrics grow with unique values:** remove request-specific labels and use bounded dimensions.
- **Logs omit the failure:** check whether the error is handled before logging and avoid duplicating sensitive exception data.
- **Timestamps disagree:** record timezone and compare UTC timestamps consistently.

## Cleanup

Stop the local API/container and remove only synthetic fixtures and logs. Retain sanitized instrumentation changes and a short example output.

## Evidence to record

One short readme/note containing expected result, actual result, commands or test case
evidence, and a failure case; avoid full solution copy-pastes.

## Self-check

Show where to find a failed request, its error reason, and whether the failure is isolated or widespread.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
