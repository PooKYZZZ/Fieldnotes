# Logs, metrics and traces

## Scenario

One failed request may be an isolated defect or the first sign of a broader service problem; logs, metrics and traces answer related but different questions.

## Learning objectives

- Generate synthetic success and failure requests against a local API.
- Correlate a timestamped log with a bounded metric change.
- Explain what event details and aggregate signals can establish in a small sample.

## Expected observations
A successful `/health` request and a deliberate 404 appear as separate structured log events with UTC timestamps, bounded route labels, status, and generated correlation IDs. The request counter increases for each application request but does not create a new time series for every arbitrary URL or ID. Logs show individual events; metrics summarize counts; this small single-service exercise does not produce or verify a distributed trace.

## Prerequisites
Study Module 16 in 03_Operations_and_Security.pdf. Review the official [OpenTelemetry signal concepts](https://opentelemetry.io/docs/concepts/signals/) and its [metrics guidance](https://opentelemetry.io/docs/concepts/signals/metrics/).

## Challenge

Generate good and bad requests; correlate a timestamped error log with a metric rise; inspect how an
application exposes /metrics.

## Build outcome

Instrument the Status API with structured logs and request counters, then create a short
troubleshooting note.


## Environment

Run the Status API in a local container or disposable VM with synthetic requests and logs. Use no real user data,
credentials, or public traffic.

## Lab steps
1. Start from the local Status API used in A05 and make a copy or disposable branch. Keep requests synthetic and bind the test service to loopback or its private Compose network.
2. Add middleware that logs one JSON event after each response: UTC timestamp, a generated request ID, a normalized route (`/health` or `/other`), and numeric status. Do not log headers, query strings, tokens, or raw user input.
3. Add a counter grouped only by normalized route and status class (`2xx`, `4xx`, `5xx`). Exclude the `/metrics` scrape itself from the request counter so looking at metrics does not change the measurement. Document any other metric labels you add.
4. Record the counter, send one request to `/health` and one to a nonexistent path, then read the logs and counter again. Match the 200 and 404 using their generated IDs and compare the before/after counts.
5. Write a short incident note: what failed, which event supports that, whether the count suggests only this synthetic request or a wider pattern, and what additional signal or trace would be needed to investigate across services.

## Hints
For the A05 FastAPI service, a small implementation can use `@app.middleware("http")`, `datetime.now(timezone.utc).isoformat()`, and Python's `collections.Counter`. Normalize every path before using it as a label; do not use `request.url.path` directly because arbitrary paths create unbounded series.

After `app = FastAPI()` in the A05 app, this compact example records a generated ID and exports a bounded counter. It is for the local exercise, not a replacement for production instrumentation:

```python
from collections import Counter
from datetime import datetime, timezone
import json
import secrets

from fastapi import Request
from fastapi.responses import PlainTextResponse

request_counts = Counter()

@app.middleware("http")
async def observe_request(request: Request, call_next):
    response = await call_next(request)
    path = request.url.path
    route = "/health" if path == "/health" else "/metrics" if path == "/metrics" else "/other"
    event = {
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "request_id": secrets.token_hex(8),
        "route": route,
        "status": response.status_code,
    }
    response.headers["X-Request-ID"] = event["request_id"]
    print(json.dumps(event), flush=True)
    if route != "/metrics":
        request_counts[(route, f"{response.status_code // 100}xx")] += 1
    return response

@app.get("/metrics", response_class=PlainTextResponse)
def metrics():
    lines = ["# TYPE http_requests_total counter"]
    for (route, status_class), count in sorted(request_counts.items()):
        lines.append(f'http_requests_total{{route="{route}",status_class="{status_class}"}} {count}')
    return "\n".join(lines) + "\n"
```

```bash
curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8000/does-not-exist
curl -s http://127.0.0.1:8000/metrics
```

A 404 is a useful controlled client error: it should normally return a response and be logged. A server exception may need separate error-handling middleware. Keep the code illustrative; a production metrics endpoint should use a maintained instrumentation library and operational review.

## Verification
- The two synthetic responses produce distinct structured events with UTC timestamps, status, and correlation IDs, and no sensitive request data.
- The counter moves by the two test requests; the metrics scrape does not increment it, and labels remain bounded.
- The incident note correctly separates individual logs, aggregate metrics, and distributed traces, and states what the small sample cannot establish.
- Captured evidence is sanitized and can be matched back to the requests without storing user identifiers.

## Troubleshooting
- **No event appears for the 404:** check middleware order and confirm the request reached this API rather than a proxy error page.
- **The metrics count changes after scraping:** exclude `/metrics` from the counter and repeat the before/after comparison.
- **Series multiply for each URL:** replace raw paths or IDs with a small route category.
- **Logs disagree with request times:** use UTC consistently and compare the generated ID; timestamps alone can collide or arrive out of order.
