# Infrastructure and application security

## Scenario

A security review needs to reduce one unnecessary exposure without cutting off required access or disrupting unrelated services.

## Learning objectives

- Inventory the test VM's listeners, service identities and application paths.
- Map assets, trust boundaries, expected access, controls and residual risks.
- Change and retest one reversible path only inside a disposable environment.

## Expected observations

The before test identifies the exact address and port that can reach the lab service. After the narrow change, that path is denied while documented health and administration paths still work. A listener inventory describes local sockets; it does not prove reachability from every network.

## Prerequisites
Review the [Module 19 learning path](/modules/19) before starting; the activity reference PDF is optional. Use the [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) to structure system decomposition, threat identification, mitigations, and review.

## Challenge

List exposed ports and identities on your VM. Close one unnecessary path, test before/after and
document residual risks.

## Build outcome

Write a one-page threat model and a hardened configuration checklist for the Status API lab.

## Environment

Use a disposable VM or a copied local service configuration that you own. Take a snapshot or backup. Do not modify
the host firewall or close ports on shared, school, work, or production infrastructure.

## Lab steps
1. Use a disposable VM or copied A05 API config. Draw the request path and mark the trust boundary between the VM itself and its isolated lab network. List the test API, its data, service identity, listening address, and who can reach each interface.
2. Capture a baseline with `ss -ltnp` and `ps -eo user,pid,comm`. For each relevant listener, record the bind address and port; a socket listing is local evidence, not proof of reachability from every network.
3. Fill a small threat table with columns: asset, entry point/boundary, plausible threat, existing evidence/control, proposed mitigation, residual risk, and next test. Include at least one assumption that still needs validation.
4. Choose one unnecessary lab-only access path. For an API running directly in the disposable VM, change its bind address from `0.0.0.0` to `127.0.0.1` rather than editing a shared firewall. For a containerized API, keep its internal listener reachable on the container network and restrict only the host-published port to loopback. Restart only the lab API, repeat the same local request, and—if a second isolated lab peer exists—repeat the request to the VM's private address. Do not claim peer-network denial unless that test was actually run.
5. Confirm the intended local health path still works, compare listener inventory and connection results, and record the rollback command/config. Review privileges and identify one remaining risk that your change did not address.

## Hints
A useful decomposition asks what components, data stores, data flows, external entities, and trust boundaries exist. Then ask what can go wrong, what control addresses it, and what evidence would show the control worked. A listener such as `127.0.0.1:8000` accepts local connections only; `0.0.0.0:8000` listens on all IPv4 interfaces, but firewall and network policy still affect remote reachability.

```bash
ss -ltnp
ps -eo user,pid,comm
curl -i http://127.0.0.1:8000/health
```

Do not close a production, shared, school, or host firewall port for this exercise.

## Verification
- The threat model identifies assets, data flows, entry points, trust boundaries, assumptions, existing controls, mitigations, residual risk, and a way to test the proposed control.
- Before/after evidence is for the same test API and path; local listener evidence is distinguished from a remote reachability test.
- The single lab-only bind change reduces the intended exposure while the local health check still succeeds; rollback is documented.
- No unrelated listener is stopped and no real data, credentials, or public host details appear in the evidence.

## Troubleshooting

- **A connection still succeeds:** check both host and application listeners, and confirm the test used the expected
  address and port.
- **The service becomes unreachable:** restore the snapshot or revert only the lab change before proceeding.
- **An unexpected process is found:** record it and investigate rather than stopping an unrelated service.

## Cleanup

Restore the saved VM/firewall configuration and verify the original lab service state. Remove only test users or services created for this activity.

## Evidence to record
Include the redacted request-path/trust-boundary diagram, threat table, listener and identity inventory, exact bind change, local and optional isolated-peer tests, preserved health check, residual risks, and rollback evidence. State which network path was actually tested.

## Self-check

Justify privileges, services and ports; demonstrate one verified control and identify at least one
unresolved risk.


## Independent reflection

For an access-control claim, record both a client that still succeeds and an isolated client that demonstrably fails after the control change. If you cannot run the second client, compare a supplied or synthetic pair on paper and mark peer enforcement unverified.

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
