# Kubernetes architecture, workloads and operations

## Scenario

A Deployment can report running Pods while its Service selects no ready endpoints or a rollout is blocked by image or probe errors.

## Learning objectives

- Confine all Kubernetes objects to a named local cluster context and namespace.
- Observe how a Deployment replaces a deleted Pod and how its Service selects endpoints.
- Cause one manifest-only rollout fault, diagnose events and restore a known-good revision.

## Expected observations
The Deployment maintains the requested number of Pods and replaces a deleted Pod. The Service selects Pods by label but routes only to ready endpoints. With the A08 image loaded locally, `imagePullPolicy: Never` prevents an accidental registry pull. A wrong readiness path keeps the new running Pods out of ready endpoints without restarting them; during the rollout, existing ready replicas can continue serving. Restoring `/health` lets the new Pods become ready. Readiness controls traffic eligibility; liveness can restart a stuck process and should not fail merely because an external dependency is temporarily unavailable.

## Prerequisites
Study Module 18 in 03_Operations_and_Security.pdf. Review Kubernetes [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/), [container resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/), and [probe semantics](https://kubernetes.io/docs/concepts/workloads/pods/probes/) before applying the lab manifest.

## Challenge
Deploy the A05 Status API into a dedicated local namespace. Predict what should change when one Pod is deleted and when the readiness path is wrong; compare Pod conditions, Service endpoints, and rollout state, then restore the working manifest.

## Build outcome
Create a local-only Deployment and ClusterIP Service with explicit labels, resources, and a readiness probe. Demonstrate one Pod replacement, diagnose a readiness failure from observations, and recover the working revision.

## Environment

Use an isolated local Kubernetes cluster such as kind, minikube, or k3d. Before changes, check the active context
and cluster name. Never use a shared or production context for this lab.

## Lab steps
1. **Prove the cluster boundary.** Check `kubectl config current-context` and verify it is your named kind, minikube, or k3d cluster. Stop if it is shared or production. Create namespace `fieldnotes-a18`; keep every object there.
2. Build or select the A05 Status API image locally and load it into the chosen cluster. Use one explicit local tag such as `status-api:dev`; configure `imagePullPolicy: Never` for this lab so Kubernetes cannot silently pull a same-named remote image. Confirm the image is available to the cluster runtime before applying.
3. Create a Deployment with two replicas, matching `app: status-api` labels and selector, a readiness probe at `/health:8000`, and small documented resource requests/limits. Create a ClusterIP Service selecting that same label. The sample values in Hints are starting points for a toy API, not sizing guidance for another application.
4. Apply the manifest and inspect Pods, labels, events, rollout status, and `kubectl get endpoints status-api`. Confirm two ready endpoints and call the Service from a temporary client Pod in the same namespace. Ensure the API listens on `0.0.0.0` inside its container; loopback inside a container is not reachable through its Pod IP.
5. Delete exactly one matching Pod by name and watch the Deployment create a replacement. Compare the old and new Pod names and confirm the Service returns to two ready endpoints.
6. Change only the readiness path in the lab manifest to `/missing`. Apply it and inspect Pod readiness, events, and Service endpoints. The container should remain running but stop receiving Service traffic after probe failures. Restore `/health`, wait for two ready endpoints, and repeat the in-cluster request.
7. Delete only namespace `fieldnotes-a18` after collecting sanitized evidence. Do not push an image, apply cluster-wide resources, or change another context.

## Hints
This small manifest assumes the local image `status-api:dev` exposes the A05 `/health` route on port 8000. Load the image into the local cluster before applying. Resource values are illustrative and should be checked against the actual toy app:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: status-api
  namespace: fieldnotes-a18
spec:
  replicas: 2
  selector:
    matchLabels:
      app: status-api
  template:
    metadata:
      labels:
        app: status-api
    spec:
      containers:
        - name: api
          image: status-api:dev
          imagePullPolicy: Never
          ports:
            - name: http
              containerPort: 8000
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 256Mi
          readinessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 5
            failureThreshold: 2
---
apiVersion: v1
kind: Service
metadata:
  name: status-api
  namespace: fieldnotes-a18
spec:
  type: ClusterIP
  selector:
    app: status-api
  ports:
    - name: http
      port: 8000
      targetPort: http
```

For kind, load your built image using the documented `kind load docker-image` command for your cluster name; for minikube use `minikube image load`. Readiness failure removes a Pod from matching Service endpoints; it does not restart it. Add a liveness probe only when it measures an unrecoverable process failure, and do not make liveness depend on a backend outage.

## Verification
- All resources are in `fieldnotes-a18` on the verified local context, and the cluster did not pull a registry image or expose a NodePort/LoadBalancer.
- Two ready Pods are selected by the Service; deleting one produces a replacement and endpoint count recovers.
- The bad readiness path is diagnosed from Pod conditions/events and endpoint removal; restoring `/health` returns the endpoint and a successful request.
- The evidence distinguishes running, Ready, selected by Service, and reachable from a client; sample resource limits are not presented as universal values.

## Troubleshooting
- **Unexpected context:** do not apply; switch to the verified local context and check again.
- **`ImagePullBackOff` or image not present:** load the exact tag into the local cluster runtime and inspect the image name; `Never` intentionally will not fetch it.
- **Pod is Pending:** inspect events, scheduling and the requested resources instead of repeatedly deleting it.
- **Pod runs but has no endpoint:** compare Service selector with Pod labels and inspect readiness conditions and probe events.
- **Service request fails:** verify there is a ready endpoint, the app binds to `0.0.0.0` on the container port, and the client uses the Service port.

## Cleanup

Delete only namespace `fieldnotes-a18` after confirming the current context is still the local cluster. Stop the local cluster when finished; do not remove unrelated contexts or cluster data.

## Evidence to record
Include the verified local context/namespace, local image tag and load method, manifest, Pod labels/conditions, endpoints and request results before/after replacement, the readiness failure events, recovery evidence, and resource-value assumptions. Do not include production cluster details or push the broken configuration.
