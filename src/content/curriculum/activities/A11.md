# Continuous delivery, releases and rollback

## Scenario

A new release may pass a superficial startup check while breaking the health path or changing assumptions about stored data.

## Learning objectives

- Compare two locally tagged image versions using the same test.
- Record image identity, health response and rollback trigger before release.
- Restore the known-good version and verify it with the original smoke test.

## Expected observations
The known-good and candidate builds should have distinguishable tags and image IDs. A tag is a mutable name, so the lab must never reuse it for different content; the image ID or registry digest is the stronger identity to record. The candidate can pass the process health check and still fail the same user operation that passed for the baseline. Restoring the exact known-good image should restore its response. This test covers application image rollback only, not database or external state rollback.

## Prerequisites

Review the [Module 11 learning path](/modules/11) before starting; the activity reference PDF is optional.

Technical references: Docker [image digests](https://docs.docker.com/reference/cli/docker/image/pull/), [image inspection](https://docs.docker.com/reference/cli/docker/image/inspect/), and [Compose health checks](https://docs.docker.com/compose/how-tos/startup-order/).

## Challenge

Deploy a numbered image version, make it return a new version label, then roll back a deliberately failing
release.

## Build outcome

Create a deployment checklist and a script or documented procedure for versioned release plus
manual rollback.

## Environment

Use the [Status API starter](/labs/status-api.zip), the A10 image archive, and a local Docker Compose project. Keep releases and tags local; do not point the
procedure at production or a public registry.

## Lab steps
1. Load the A10 tested archive and attach a unique known-good local tag to that image. Verify the image ID matches the A10 build record before starting the isolated Compose project with `LAB_IMAGE` selecting that tag and `up -d --no-build`.
2. Through the same published proxy URL, check `/health`, `/version` and `/records/demo`. Record the expected row and verify the running API container’s image ID independently.
3. Build a disposable candidate under a distinct tag. Keep `/health` healthy, but change the test-only marker response so the same `/records/demo` assertion fails. Use a separate candidate marker in `LAB_REVISION`. Do not modify the database or change the smoke test.
4. Predict which check will fail. Select the candidate with `LAB_IMAGE` and recreate only the API in the same project with `up -d --wait --no-build --no-deps api`. Keep the proxy URL and volume unchanged. Record health and the failed user-path assertion.
5. Recreate the API with the recorded A10 image, without rebuilding. Verify the running image ID, the same smoke checks, and the unchanged database marker. Explain why rollback is compatible here and one schema change that could make a future rollback unsafe.
6. Write a release note with the artifact identifier, validation, rollback trigger, and authorizer. State which data or schema compatibility checks were not performed; an application image rollback does not undo a database migration.

## Hints
```bash
docker image inspect --format '{{.Id}}' fieldnotes-status:a11-good
docker image ls --digests --filter reference='fieldnotes-status:*'
docker compose -p fieldnotes-a11 ps
docker compose -p fieldnotes-a11 logs api
```

Tags can be moved; do not call a tag immutable. Record the built image ID locally and a content digest for a registry artifact when available. Use a unique tag per build and keep the known-good image present until rollback verification is complete.

## Verification

- The version and running image ID distinguish the releases. Process health stays green while the candidate fails the original user-path assertion.
- The rollback restores the known-good version and passes the same smoke test.
- The release checklist records version, validation, rollback condition, and data compatibility considerations.
- All steps run against the isolated local copy.

## Troubleshooting

- **Candidate appears unchanged:** confirm you rebuilt and ran the intended tag, then inspect its image ID.
- **Health check gives a false pass:** verify it exercises the actual application path and expected version.
- **Rollback fails:** check whether image tags were removed and whether the old image is still available locally.
- **State differs across versions:** distinguish application rollback from database/schema rollback.

## Cleanup

Stop and remove only the test containers and versioned images after preserving sanitized release evidence.

## Evidence to record

Include the initial and candidate image tags or IDs, the same health/smoke result for each, the rollback trigger, restored version, and a note on any state or schema compatibility that was not tested.

## Self-check

Release a specific version, reproduce a failure, roll back and verify functionality using a health and smoke
test.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
