# Continuous delivery, releases and rollback

## Scenario

A new release may pass a superficial startup check while breaking the health path or changing assumptions about stored data.

## Learning objectives

- Compare two locally tagged image versions using the same test.
- Record image identity, health response and rollback trigger before release.
- Restore the known-good version and verify it with the original smoke test.

## Expected observations

The initial and candidate builds have distinguishable tags or image IDs. The deliberately incorrect health configuration fails the same check used for the known-good image. Rollback returns to the recorded image and passes that check; it does not automatically reverse a database change.

## Prerequisites

Complete or study Module 11 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Deploy a numbered image version, make it return a new version label, then roll back a deliberately failing
release.

## Build outcome

Create a deployment checklist and a script or documented procedure for versioned release plus
manual rollback.

## Environment

Use a local container runtime and a disposable copy of the Status API. Keep releases and tags local; do not point the
procedure at production or a public registry.

## Lab steps

1. Build a working image tagged with a unique version and run it with a loopback-only port mapping.
2. Confirm its version endpoint and health check, then record the tag, image ID, and test result.
3. Build a second version that reports a new version label. Verify the new instance before considering it the
   current release.
4. Simulate a failed release by using a deliberately incorrect local health path or a controlled test configuration.
   Detect the failure with the smoke check.
5. Restore the recorded working image tag and repeat health and version checks. Write down the rollback trigger and
   who would authorize it in a real system.

## Hints

```bash
docker image inspect fieldnotes-status:v1
docker ps --filter name=fieldnotes-a11
docker logs fieldnotes-a11
```

Use immutable version tags for the comparison and record the image digest or ID. Do not rely on a mutable `latest`
tag as your rollback reference.

## Verification

- The initial and candidate versions are distinguishable and the health check identifies the failing candidate.
- The rollback restores the known-good version and passes the same smoke test.
- The release checklist records version, validation, rollback condition, and data compatibility considerations.
- All steps run against the isolated local copy.

## Troubleshooting

- **Candidate appears unchanged:** confirm you rebuilt and ran the intended tag, then inspect its image ID.
- **Health check gives a false pass:** verify it exercises the actual application path and expected version.
- **Rollback fails:** check whether image tags were removed and whether the old image is still available locally.
- **State differs across versions:** distinguish application rollback from database/schema rollback.

## Cleanup

Stop and remove only the test containers and versioned images after preserving sanitized release evidence.

## Evidence to record

Include the initial and candidate image tags or IDs, the same health/smoke result for each, the rollback trigger, restored version, and a note on any state or schema compatibility that was not tested.

## Self-check

Release a specific version, reproduce a failure, roll back and verify functionality using a health and smoke
test.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
