# Monitoring, dashboards and alert design

## Scenario

An alert should notice a service condition that matters to users, stay active for a defined reason and clear only after recovery is observed.

## Learning objectives

- Define one local health signal and an explicit failure window.
- Observe target health, dashboard data and alert state through a controlled API stop and restart.
- Measure detection and recovery from timestamps, then write actionable first checks.

## Expected observations

The test target is healthy before the planned stop, becomes unavailable in the monitoring view, and recovers after restart. The alert may include a pending interval before firing, so record observed timestamps and the configured interval separately. Target state, alert evaluation and notification delivery are distinct stages.

## Prerequisites

Complete or study Module 17 in 03_Operations_and_Security.pdf.

## Challenge

Stop a service in a controlled lab; watch scrape targets, error rates and an alert rule; note how long
detection takes.

## Build outcome

Build a local service dashboard with one actionable alert and a concise response runbook.

## Environment

Use a local Compose stack or disposable VM with the Status API and monitoring components. Configure alerts to a local
test receiver only; do not connect real paging, email, or public webhook destinations.

## Lab steps

1. Choose a user-facing health signal and define what counts as a failure and how long it must persist before alerting.
2. Confirm the API target is being scraped and that the dashboard query reflects the selected time window.
3. Stop only the test API. Observe target health, the signal, and the alert state; record the delay from failure to
   detection.
4. Restart the API and verify the alert resolves only after the service meets its recovery condition.
5. Write a short runbook with symptom, first checks, mitigation, and a recovery test. Distinguish host availability
   from service health.

## Hints

- Use one clear alert with a stable label set and an actionable description.
- Test the alert rule against the local failure before connecting any notification integration.
- Include the dashboard time range and scrape interval in your evidence.

## Verification

- The target is shown as healthy before and after the controlled outage.
- The alert fires after the defined condition and clears after verified recovery.
- Detection and recovery delays are measured from observations, not guessed.
- The runbook tells the operator what to check next and how to confirm recovery.

## Troubleshooting

- **No data appears:** check target configuration, service address, network, and scrape errors.
- **Alert never fires:** evaluate the expression and pending duration against the test signal.
- **Alert stays active after restart:** verify the metric recovers and the rule's resolution behavior.
- **Notification did not arrive:** check the local test receiver; do not assume that alert state and delivery are the same.

## Cleanup

Stop the local monitoring and API services using only this activity's Compose project. Remove its test volumes only after confirming they hold no needed data.

## Evidence to record

Include the signal and alert condition, scrape interval and dashboard window, target and alert state timestamps before/during/after the test, observed delays, and the local recovery check. Do not include real paging or webhook destinations.

## Self-check

Prove the alert fires and clears during a controlled incident; explain the difference between service and
host health.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
