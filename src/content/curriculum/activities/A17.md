# Monitoring, dashboards and alert design

## Scenario

An alert can show that a monitoring target stopped responding, but its state and notification path do not by themselves establish the full user impact or a verified recovery.

## Learning objectives
- Define a local scrape target and an explicit failure window for the test service.
- Observe Prometheus target health and the alert transition from inactive to pending to firing, then back after recovery.
- Measure the observed delay using scrape and evaluation intervals, and write an actionable first-response note.

## Expected observations
The target starts with `up == 1`. Stopping only the API leaves its configured target in place and changes the scrape result to `up == 0`; the alert becomes pending and then firing after its `for` interval. Restarting the API restores `up == 1` and clears the alert at a later evaluation. Detection includes scrape and rule-evaluation timing, so observed delays may exceed the configured `for` value. This `up` signal means Prometheus can scrape `/metrics`; it is not a full user-journey health check. Prometheus alert state does not itself prove that an external notification was delivered.

## Prerequisites
Study Module 17 in 03_Operations_and_Security.pdf. Review the official [Prometheus alerting rules guide](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/) for the meaning of pending alerts, the `for` duration, and the separation between alert state and notification delivery.

## Challenge
Create one local `up == 0` alert for the Status API. Stop and restart only that test service, then explain how the scrape interval, evaluation interval, and pending duration shaped the observed alert timeline.

## Build outcome
Produce a small local graph of target availability, one Prometheus alert rule, a timeline of a controlled outage and recovery, and a runbook with a first check and recovery test.

## Environment

Use a local Compose stack or disposable VM with the Status API and monitoring components. Configure alerts to a local
test receiver only; do not connect real paging, email, or public webhook destinations.

## Lab steps
1. Run the A05 Status API and Prometheus in an isolated local Compose project. Keep Prometheus and API on the same private Compose network; use the API service name and port as the target. Confirm `/health` works before touching monitoring.
2. Add a scrape job named `fieldnotes-a17` for the API's `/metrics` endpoint. Check the Prometheus Targets page or `up{job="fieldnotes-a17"}` and record the current scrape/evaluation intervals. Do not proceed until the target is healthy.
3. Graph `up{job="fieldnotes-a17"}` over a time window that includes the test. If Grafana is already in the local stack, use it for a simple panel; otherwise inspect the Prometheus graph view. Add the alert rule in Hints, validate/reload it using your local setup, and confirm it starts inactive while the API is healthy.
4. Record the time, stop only the API service in this Compose project, and observe target state, expression value, and alert state. Capture when it first becomes pending and firing. Do not configure a real pager or public webhook.
5. Restart the API. Confirm `/health`, target health, and alert resolution. Write a short runbook with symptom, first check, safe mitigation, and the recovery test; distinguish a missing target series from a configured but failed target.

## Hints
When Prometheus and the API share a Compose network, a scrape job can target the API service name:

```yaml
scrape_configs:
  - job_name: fieldnotes-a17
    metrics_path: /metrics
    static_configs:
      - targets: ["status-api:8000"]
```

A simple rule is:

```yaml
groups:
  - name: fieldnotes-a17
    rules:
      - alert: StatusApiUnavailable
        expr: up{job="fieldnotes-a17"} == 0
        for: 30s
        labels:
          severity: warning
        annotations:
          summary: "The local Status API is not being scraped"
```

This rule requires the target to be configured and then fail; deleting the target configuration can leave no series and will not match `== 0`. Pending time starts when the expression first matches, after a scrape. Add scrape interval, evaluation interval, and `for` together when estimating delay. Prometheus stores pending/firing state; Alertmanager or another receiver is a separate notification path.

## Verification
- The target is healthy before and after the test; the controlled API stop produces a failed scrape and the expected alert transition.
- Recorded timestamps show the observed detection and recovery delay, with scrape interval, rule evaluation interval, and `for` value kept distinct.
- The runbook identifies a first check, safe mitigation, and a service-level recovery test.
- Evidence shows Prometheus alert state only; no external delivery claim or real paging destination is used.

## Troubleshooting
- **No target appears:** check the scrape configuration, Compose DNS name, port, and network; an absent target is different from `up == 0`.
- **Target is down before the exercise:** restore API and `/metrics` reachability before recording the baseline.
- **Alert is still pending:** compare elapsed time with `for` and the rule evaluation interval; inspect the expression and labels.
- **Alert does not clear:** verify `up` has returned to 1 and inspect evaluation state; notification delivery is a separate path.

## Cleanup

Stop the local monitoring and API services using only this activity's Compose project. Remove its test volumes only after confirming they hold no needed data.

## Evidence to record
Include target/job and endpoint, the query and rule, scrape/evaluation/`for` intervals, timestamps and state transitions before/during/after the controlled stop, observed delays, runbook and recovery check. Do not include real webhook destinations or claim that a notification was delivered.

## Self-check

Prove the alert fires and clears during a controlled incident; explain the difference between service and
host health.

else?
