# Networking: from a packet to a web request

## Scenario

When a local website cannot be reached, a learner needs to locate the failing layer instead of changing DNS, routes or firewall settings at random.

## Learning objectives

- Map a request across name resolution, address, route, listener and HTTP response.
- Use local-only tests to compare a working listener with a stopped test service.
- Explain which boundary each network command can and cannot verify.

## Expected observations
`localhost` should resolve through the machine's name-service configuration to loopback; `getent` reports the resolver result but does not test a public DNS server. While the server is running, `ss` should show a listener on `127.0.0.1:18080` and curl should connect and receive an HTTP response. After Ctrl+C, the address resolution and route remain unchanged, but the TCP connection should be refused or time out. Restarting the listener should restore the response. An HTTP `404` is evidence that an HTTP server answered, not evidence that the requested route exists.

## Prerequisites

Review the [Module 04 learning path](/modules/04) before starting; the activity reference PDF is optional.

Technical references: [`ip` address and route tools](https://man7.org/linux/man-pages/man8/ip.8.html), [curl options](https://curl.se/docs/manpage.html), and [HTTP semantics (RFC 9110)](https://www.rfc-editor.org/rfc/rfc9110.html).

## Challenge

Use ip, ss, ping, tracepath/traceroute, dig/nslookup and curl against systems you own. Record expected
vs actual results.

## Build outcome

Map your own lab network and write a connectivity troubleshooting worksheet with at least four
distinct failure categories.

## Environment

Use loopback, a disposable VM, or an isolated lab network that you own. Do not scan, probe, or change routes or
firewall rules on networks you do not control.

## Lab steps
1. **Draw and predict.** Sketch a local client, `localhost`/loopback, TCP port `18080`, and the HTTP handler. Predict which part will change when only the listener stops.
2. **Record local state.** Run `ip -br address`, `ip route`, and `ss -ltn`. These show local addresses, route entries, and TCP listeners; they do not prove that an application returns the right page.
3. **Start a temporary listener.** In the server terminal, create the disposable directory with `work="$(mktemp -d)"` and write one harmless line to `"$work/index.html"`. Keep that terminal open so you can see the path and clean it up later. Serve only that directory on IPv4 loopback: `python3 -m http.server 18080 --bind 127.0.0.1 --directory "$work"`. Keep this process in the foreground in one terminal.
4. **Check name and HTTP separately.** In a second terminal run `getent hosts localhost` and `curl -i --max-time 3 http://localhost:18080/`. Record the resolved address, whether TCP connected, and the HTTP status/body separately. A response such as `404` still proves an HTTP server answered; it means the requested route or file was not found.
5. **Create a bounded failure.** Stop only your temporary server with Ctrl+C and repeat the exact request. Name resolution should be unchanged while the TCP connection fails. Restart the same listener and confirm the original request works again.
6. **Classify the evidence.** For each test label the boundary as name lookup, route, listener/port, TLS, or application/HTTP. Use `ping` only as an optional ICMP clue; ICMP reachability does not prove TCP or HTTP service health.
7. **Clean up.** Stop the listener and remove only the temporary directory you created. Do not change routes or firewall rules for this exercise.

## Hints
Start with the literal `127.0.0.1` in the client URL so DNS and IPv6 fallback cannot change this comparison. Then classify four evidence cases: a name does not resolve, the address resolves without a usable route, an established route reaches a host with no listener, and a connection returns HTTP 404. For each case, identify the first failed boundary and one observation that would distinguish it from the next boundary. Use supplied evidence or written predictions for layers this loopback lab does not exercise.


```bash
ip -br address
ip route
getent hosts localhost
ss -ltn
curl -i --max-time 3 http://127.0.0.1:18080/
```

The local service can be a simple temporary HTTP server. Keep the request on `127.0.0.1`; no external target is
needed.

## Verification

- The network sketch labels the client, address, route, port, and application endpoint.
- The working request shows connection and HTTP results separately.
- The stopped-service case is classified at the listener/transport boundary rather than blamed on DNS.
- The note states what each command can and cannot prove.

## Troubleshooting

- **Name resolves but the request fails:** check the selected address, listener, port, and protocol next.
- **`curl` connects but returns an error status:** the application answered; diagnose its HTTP response separately.
- **`ping` is blocked:** ICMP policy may differ from TCP; continue with the specific local service test.
- **No route output is expected:** loopback traffic is local and need not traverse an external route.

## Cleanup

Stop the test listener and remove only the temporary service/network created for this exercise. Save a redacted worksheet rather than a full network configuration dump.

## Evidence to record

Include a network sketch with sanitized addresses, the commands used, working and stopped-listener observations, and your classification of name, route, port, TLS and HTTP evidence. Do not include public or workplace network details.

## Self-check
