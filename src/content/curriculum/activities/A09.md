# Docker Compose and service dependencies

## Scenario

A multi-service application may start in the wrong order or appear healthy while a dependency is not ready; its stored data must also survive container recreation.

## Learning objectives

- Review and start a unique local Compose project with API, proxy and database services.
- Test the full request path and a harmless synthetic database record.
- Compare API restart and container recreation while retaining the named test volume.

## Expected observations
The database should report `healthy` only after its `pg_isready` check succeeds. The API service should start after that condition; the proxy response should succeed only when the API is also ready. The synthetic row should remain after an API restart and after `compose down` followed by `up` because the named database volume persists. `docker compose down -v` would remove that volume and invalidate the persistence test. A healthy database or proxy alone does not prove the complete request path works.

## Prerequisites

Complete or study Module 09 in 02_Infrastructure_and_Cloud.pdf.

Technical references: Docker Compose [startup order and health checks](https://docs.docker.com/compose/how-tos/startup-order/), [Compose networking](https://docs.docker.com/compose/how-tos/networking/), and [volumes](https://docs.docker.com/engine/storage/volumes/).

## Challenge

Build a Compose stack with API, reverse proxy and a local database. Restart only the API, then recreate
the whole stack and verify persistence.

## Build outcome

Create one-command local startup for API + NGINX + PostgreSQL with a nonsecret .env.example.

## Environment
Use Docker Compose in a new working directory with a unique project name. Reuse a small local API and proxy from A05/A08, or build equivalent toy services. Keep the database on the private Compose network; publish only the proxy on loopback. Keep database credentials in an ignored local `.env` file and commit a placeholder-only `.env.example`. Pin or record the resolved image versions used in the lab.

## Lab steps
1. **Review the topology before startup.** Your Compose file should define an API, NGINX proxy, and PostgreSQL service on the project network. Add a named database volume and a health check. A service dependency that must wait for database readiness needs `condition: service_healthy`, not just `depends_on: db`:

   ```yaml
   services:
     db:
       image: postgres:17
       env_file: .env
       volumes:
         - database-data:/var/lib/postgresql/data
       healthcheck:
         test: ["CMD-SHELL", "pg_isready -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
         interval: 5s
         timeout: 3s
         retries: 10
         start_period: 10s

     api:
       build: ./api
       depends_on:
         db:
           condition: service_healthy

     proxy:
       image: nginx:alpine
       ports:
         - "127.0.0.1:8080:80"
       depends_on:
         - api

   volumes:
     database-data:
   ```

   Adapt the API build and NGINX configuration to your A05 service. Do not publish PostgreSQL's port to the host for this test. Compose orders the proxy after the API container starts, but that alone does not prove the API is ready.
2. **Validate without exposing credentials.** Run `docker compose -p fieldnotes-a09 config --quiet` and `docker compose -p fieldnotes-a09 ps`. Do not paste the fully rendered configuration into evidence because interpolated values may reveal credentials.
3. **Start and observe.** Use `docker compose -p fieldnotes-a09 up -d --build`; inspect `ps` and bounded logs. Confirm the database health check passes and call the proxy from the host at `127.0.0.1:8080`.
4. **Create one synthetic database row.** Use `psql` inside the `db` service with the user/database supplied by the local environment file. Create a small `lab_marker` table and insert a clearly synthetic identifier. If your API is wired to PostgreSQL, create/read the row through that API too; otherwise state clearly that the SQL check tests volume persistence, not application-to-database integration.
5. **Test lifecycle boundaries.** Restart only the API, then query the synthetic row again. Run `docker compose -p fieldnotes-a09 down` without `-v`, start the project again, and query the row again. Never remove the named volume as part of this proof.
6. **Observe one bounded dependency failure.** Stop only the lab database, record what the API/proxy and health checks show, then start the database and wait for health before re-testing. Do not disable the health check to make startup appear successful.
7. **Clean up.** Stop only project `fieldnotes-a09`. Preserve or remove its named volume only after confirming it contains disposable lab data.

## Hints
```bash
docker compose -p fieldnotes-a09 config --quiet
docker compose -p fieldnotes-a09 ps
docker compose -p fieldnotes-a09 logs --tail=50
docker compose -p fieldnotes-a09 exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id FROM lab_marker ORDER BY id;"'
```

Compose's short-form `depends_on` controls startup order, not service readiness. A health check plus `condition: service_healthy` waits for a dependency check; applications still need to handle later disconnects and retries. Never paste resolved environment values into screenshots or notes.

## Verification

- All expected containers are healthy or their readiness state is explained.
- The API request through NGINX succeeds and the test record is readable after API restart and container recreation.
- The record's persistence is explained by the named volume, not an assumption about the container.
- `.env.example` contains placeholders only, and the actual environment file is ignored.

## Troubleshooting

- **API starts before the database is ready:** use health-based readiness and retry behavior, not only startup order.
- **Name resolution fails:** confirm services share the Compose network and use the Compose service name.
- **Data disappears:** check which named volume the database uses and whether it was removed.
- **Compose config shows an empty value:** check local environment configuration without printing real secrets.

## Cleanup

Stop only the `fieldnotes-a09` project. Remove its named test volume only after verifying that it contains disposable
data; never run a global volume or system prune.

## Evidence to record

Include sanitized Compose service and volume names, readiness and request checks, the synthetic record result before and after API restart and container recreation, and the dependency failure and recovery observation. Do not record credential values.

## Self-check

Start from a clean clone, verify services communicate by name, show data persistence and explain any
unhealthy service.
