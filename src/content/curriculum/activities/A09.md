# Docker Compose and service dependencies

## Prerequisites

Complete or study Module 09 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Build a Compose stack with API, reverse proxy and a local database. Restart only the API, then recreate
the whole stack and verify persistence.

## Build outcome

Create one-command local startup for API + NGINX + PostgreSQL with a nonsecret .env.example.

## Environment

Use Docker Compose in a new working directory with a unique project name, a toy API, NGINX, and a local database.
Keep database credentials in an ignored local environment file; commit only a nonsecret `.env.example`.

## Lab steps

1. Review the Compose file for service names, network exposure, health checks, named volumes, and environment
   variables before starting it.
2. Start the project with a unique project name. Check each service's state and read logs for startup ordering or
   readiness problems.
3. Call the API through NGINX, then verify the API reaches the database by creating a harmless test record.
4. Restart only the API and confirm the record remains. Recreate the project containers and confirm persistence
   still comes from the named database volume.
5. Test one dependency failure in the isolated lab, observe the symptom, restore the dependency, and write down
   the difference between "container started" and "service ready."

## Hints

```bash
docker compose -p fieldnotes-a09 ps
docker compose -p fieldnotes-a09 logs --tail=50
docker compose -p fieldnotes-a09 config
```

The project name scopes Compose resources. Review the rendered configuration before startup; do not publish the
database port to the host unless the exercise specifically needs it.

## Verification

- All expected containers are healthy or their readiness state is explained.
- The API request through NGINX succeeds and the test record is readable after API restart and container recreation.
- The record's persistence is explained by the named volume, not an assumption about the container.
- `.env.example` contains placeholders only, and the actual environment file is ignored.

## Troubleshooting

- **API starts before the database is ready:** use health-based readiness and retry behavior, not only startup order.
- **Name resolution fails:** confirm services share the Compose network and use the Compose service name.
- **Data disappears:** check which named volume the database uses and whether it was removed.
- **Compose config shows an empty value:** check local environment configuration without printing real secrets.

## Cleanup

Stop only the `fieldnotes-a09` project. Remove its named test volume only after verifying that it contains disposable
data; never run a global volume or system prune.

## Evidence to record

One short readme/note containing expected result, actual result, commands or test case
evidence, and a failure case; avoid full solution copy-pastes.

## Self-check

Start from a clean clone, verify services communicate by name, show data persistence and explain any
unhealthy service.

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
