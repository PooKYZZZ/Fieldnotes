# DevSecOps integration and architecture judgment

## Scenario

A capstone can look complete while its architecture contains unverified assumptions about recovery, security, operations or cost.

## Learning objectives
- Trace one representative user request through the local capstone and identify its dependencies and failure modes.
- Assess functionality, reliability, security, maintainability, cost, and explainability using evidence, and label gaps honestly.
- Write one reviewable Architecture Decision Record (ADR) and reproduce a safe failure and recovery test.

## Expected observations
Every architecture claim is linked to an artifact or marked partial/unknown; a single green health check supports only the behavior it exercises. The ADR names the context, options, decision, consequences, and a condition for revisiting it. The smoke and recovery procedures can be repeated from the documented local environment without private credentials.

## Prerequisites
Complete or study Module 24 in 03_Operations_and_Security.pdf. Review AWS Prescriptive Guidance on [architectural decision records](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html), including context, decision, consequences, and review.

## Challenge
Review one important request path in your capstone using an evidence-linked rubric. Choose one unresolved trade-off, write an ADR, and demonstrate the strongest recovery claim the available local evidence supports.

## Build outcome
Produce a request-path diagram, a six-dimension evidence review, one concise ADR, and a repeatable local smoke/failure/recovery note. Label any hosted or production behavior you could not verify.

## Environment

Use a local capstone copy, its documentation, and a disposable test environment. Do not deploy changes to a real
service as part of this assessment.

## Lab steps
1. Choose one important user request and trace it from entry point through each service, storage layer, and external dependency. Mark trust boundaries, ownership, a likely failure at each hop, and the evidence you can actually inspect.
2. Review six dimensions: functionality, reliability, security, maintainability, cost, and explainability. For each, choose `demonstrated`, `partial`, or `unknown`; link a test, configuration, diagram, bill/estimate, or runbook that supports the status. Do not invent a numeric score when evidence is missing.
3. Select one consequential trade-off. Write an ADR with title/status, context and constraints, at least two considered options, the decision, consequences (including operational and cost effects), and a specific trigger/date for revisiting it. Link the evidence behind the decision.
4. Run one documented local smoke check and record the exact expected and observed result. In an isolated test environment, cause one bounded failure and recover; record the evidence at each stage. Do not deploy to production or require real credentials for this assessment.
5. Ask another learner to follow the setup, smoke test, and recovery note without undocumented secrets. Record where they get blocked and revise the instructions. State clearly which CI/hosted/production claims remain unverified.
6. Remove only test resources and synthetic data created for the review. Keep the ADR, redacted diagram, and sanitized evidence links in the capstone portfolio.

## Hints
An evidence table can be short:

| Dimension | Status | Evidence | Gap / next check |
| --- | --- | --- | --- |
| Functionality | demonstrated / partial / unknown | Link to a focused test | What behavior remains? |
| Reliability | demonstrated / partial / unknown | Recovery drill or SLO evidence | What failure is untested? |
| Security | demonstrated / partial / unknown | Config review or scan | What threat is outside scope? |
| Maintainability | demonstrated / partial / unknown | Setup and rollback note | Can another learner reproduce it? |
| Cost | demonstrated / partial / unknown | Resource inventory or estimate | What usage assumption is missing? |
| Explainability | demonstrated / partial / unknown | Diagram and ADR | What decision still lacks context? |

A useful ADR skeleton is `Context`, `Options considered`, `Decision`, `Consequences`, and `Revisit when`. Evidence links support the decision; they do not replace stating the trade-off in plain language.

## Verification
- The request path names components, boundaries, dependencies, owners, and a plausible failure mode.
- All six review statuses have evidence or an explicit gap; no unsupported number or blanket “secure/reliable” claim is used.
- The ADR includes options, decision rationale, consequences, and a concrete revisit trigger.
- Another learner can repeat the local smoke and failure/recovery check from the instructions without private credentials.
- Local, CI, hosted, and production evidence are labeled separately.

## Troubleshooting
- **The rubric becomes opinion:** replace each assertion with a linked test/config/diagram/estimate or mark it unknown.
- **The health check passes but the workflow still fails:** trace the full request path and test dependencies and failure recovery separately.
- **A decision has no clear alternative:** describe the option not chosen and the operational cost it would have avoided or introduced.
- **The lab requires production credentials:** stop and replace it with a synthetic local fixture or label the evidence gap.

## Cleanup

Remove only test deployments and synthetic data created for this review. Keep the ADR, redacted diagram, and evidence links in the capstone portfolio.

## Evidence to record
Include the redacted request-path diagram, evidence-linked dimension table with `demonstrated/partial/unknown` statuses, ADR with rejected alternative and revisit trigger, repeatable local smoke/failure/recovery checks, peer reproduction notes, and explicit boundaries between local, CI, hosted, and production evidence.

## Self-check

Defend one important tradeoff, reproduce a release safely and demonstrate recovery from a controlled
failure.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
