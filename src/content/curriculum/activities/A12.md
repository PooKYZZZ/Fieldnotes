# Cloud concepts and Azure foundations

## Scenario

A cloud VM belongs to a chain of separately managed resources, and stopping compute does not necessarily remove attached resources or charges.

## Learning objectives

- Map a small hypothetical or existing lab VM to its network, storage and identity dependencies.
- Separate provider responsibilities from guest operating-system and application responsibilities.
- Use current official pricing and terms before any optional provisioning decision.

## Expected observations

The dependency map exposes resources that can exist independently of VM compute, such as disks, public addresses and snapshots. The responsibility table assigns guest access, patching, identity and application data to the appropriate party. Price and offer eligibility depend on current account and region terms, so unknowns remain explicitly unpriced; the local-only path needs no cloud resource.

## Prerequisites

Complete or study Module 12 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Draw resource ownership for one test VM; list every resource and investigate which could incur a charge
after a stop/deallocation.

## Build outcome

Create a resource dependency diagram and a cost/cleanup checklist. Provision an Azure Linux lab only if you have
reviewed the current terms and prices, accepted the potential spend, and can verify that every lab resource is
removed afterward.

## Environment

Start with a resource diagram, official pricing pages, and a local VM or container. Do not create a paid cloud
resource for this activity unless you have reviewed the current offer, selected an explicit spending limit you accept,
and intend to provision it.

## Lab steps

1. Draw a dependency graph for a small Linux VM, including its resource group, disk, network interface, virtual
   network/subnet, network rules, and any public IP.
2. Mark which party manages each layer for IaaS and which application/guest responsibilities remain yours.
3. Review current official pricing and account terms for each resource. Record the source and date checked; do not
   infer that an educational offer makes every service free.
4. Write a cleanup checklist that names each resource and the command or portal view that would confirm its
   removal. Explain which costs can remain after compute is stopped.
5. If you already have a suitable lab subscription and deliberately choose to provision, create only the planned
   small resource set, verify it, then inspect the resource group and remove the lab resources. Otherwise complete
   the diagram and local simulation only.

## Hints

- Treat each independently billed resource as a separate cleanup item.
- Use an isolated resource group and a clear activity tag if you provision.
- A budget or alert provides visibility; do not describe it as a guaranteed hard spending cap.
- Prefer local virtualization when it teaches the same dependency or operating-system concept.

## Verification

- The dependency diagram includes attached and separately billed resources, not only the VM.
- The responsibility table distinguishes provider-managed infrastructure from guest OS, identity, application, and
  data responsibilities.
- The cost notes link to current official terms and identify what is unknown.
- If resources were provisioned, the final inventory shows none of the activity's resources remain.

## Troubleshooting

- **Price or eligibility is unclear:** stop at the diagram and consult current official terms; do not guess or create
  the resource to find out.
- **A resource remains after cleanup:** inspect the activity's isolated resource group and dependencies before
  deleting anything.
- **A VM is stopped but cost remains:** check disks, IP addresses, storage, snapshots, and other services separately.

## Cleanup

For a cloud lab, verify the lab resource group and billing view after deletion; retain only sanitized notes. Otherwise, no cloud resources need to be created.

## Evidence to record

Include the dependency diagram, responsibility table, official pricing or terms sources and date checked, known unknowns, and a resource inventory proving cleanup if you chose to provision. No cloud resource is required for the local-only path.

## Self-check

Explain each VM dependency, the shared-responsibility model and your cost-safe cleanup method.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
