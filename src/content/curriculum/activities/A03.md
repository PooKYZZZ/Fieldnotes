# Linux users, processes and service management

## Scenario

A service that works in a terminal may fail under its service identity because its permissions, working directory or startup environment differ.

## Learning objectives

- Run a local test service as a dedicated non-root account in a disposable VM.
- Compare systemd state, journal messages, listener state and an HTTP health request.
- Introduce one reversible failure and verify recovery from evidence.

## Expected observations
The healthy unit should report `active (running)`, run under `fieldnotes-a03`, listen on `127.0.0.1:18080`, and return the synthetic page with HTTP `200`. During the bad-directory test, Python's `http.server` remains active and returns HTTP `404` for the missing serving directory; systemd does not restart it because the process has not exited. The journal and `curl -i` show different evidence: the unit is still active, while the requested page is unavailable. After restoring the directory, the same request should return `200` again. A process running does not prove that its endpoint works, and a restart policy does not diagnose or fix the underlying cause.

## Prerequisites

Review [Process and service lifecycle in Module 03](/modules/03/lessons/m03-l02) and [Logs and fault isolation](/modules/03/lessons/m03-l03), or use the activity reference PDF as a supplement.

Technical references: [systemd service units](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [systemd execution settings](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html), and [`journalctl`](https://man7.org/linux/man-pages/man1/journalctl.1.html).

## Challenge

Create a non-root service account; inspect chmod results and process signals; compare systemctl status
with journalctl logs.


## Build outcome

Create a minimal systemd unit for a test web service with restart policy and a written rollback
procedure.

## Environment

Use a disposable Ubuntu VM that you can restore. A system service requires administrator rights, so do not run these
steps on a shared, school, work, or production host.

## Lab steps
1. **Confirm the boundary.** Work only in a restorable Ubuntu VM with systemd. Choose the unique name `fieldnotes-a03` unless it already exists; if it does, pick another suffix and use it consistently. Record the snapshot name.
2. **Create a non-login service identity and a harmless response file.** These commands require administrator rights inside the disposable VM:

   ```bash
   sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin fieldnotes-a03
   sudo install -d -o fieldnotes-a03 -g fieldnotes-a03 -m 0755 /var/lib/fieldnotes-a03
   printf 'A03 lab response\n' | sudo tee /var/lib/fieldnotes-a03/index.html >/dev/null
   ```

   If account creation reports that the name already exists, stop and choose a different lab-specific name; do not reuse an account you did not create.
3. **Create a minimal unit.** Write `/etc/systemd/system/fieldnotes-a03.service` with the following content. The process serves only loopback and runs as the restricted account:

   ```ini
   [Unit]
   Description=Fieldnotes A03 disposable HTTP service
   After=network.target

   [Service]
   Type=simple
   User=fieldnotes-a03
   Group=fieldnotes-a03
   WorkingDirectory=/var/lib/fieldnotes-a03
   ExecStart=/usr/bin/python3 -m http.server 18080 --bind 127.0.0.1 --directory /var/lib/fieldnotes-a03
   Restart=on-failure
   RestartSec=2

   [Install]
   WantedBy=multi-user.target
   ```

   Review the absolute executable, account, directory, loopback bind, and restart policy before installation. Do not enable the unit at boot.
4. **Validate and start.** Run `sudo systemd-analyze verify /etc/systemd/system/fieldnotes-a03.service`, then `sudo systemctl daemon-reload` and `sudo systemctl start fieldnotes-a03.service`. Compare `systemctl status` with `journalctl -u fieldnotes-a03.service --since '5 minutes ago' --no-pager`; check `ss -ltn` and request `curl --fail -i http://127.0.0.1:18080/`.
5. **Predict and induce one failure.** Predict what a missing serving directory will do, then change only the unit's `--directory` to `/var/lib/fieldnotes-a03/missing`. Run `systemd-analyze verify`, reload the manager, restart this unit, and request `/` with `curl -i` (without `--fail`) so the HTTP `404` remains visible. Confirm the unit is still active and compare status and journal. Do not change `Restart=` just to hide the error.
6. **Recover and prove it.** Restore the original directory, validate, reload, restart, and repeat the exact `curl` request. Compare the service identity and listener address before and after.
7. **Clean up only this lab.** Stop the unit, remove the exact unit file and lab directory, reload systemd, and delete the dedicated account only after confirming the unit is stopped and the account owns no other files. Restore the VM snapshot if any cleanup step is uncertain.

## Hints
```bash
sudo systemd-analyze verify /etc/systemd/system/fieldnotes-a03.service
sudo systemctl status fieldnotes-a03.service --no-pager
sudo journalctl -u fieldnotes-a03.service --since "5 minutes ago" --no-pager
sudo systemctl show fieldnotes-a03.service -p User -p MainPID -p ActiveState
ss -ltn
curl --fail -i http://127.0.0.1:18080/
```

`daemon-reload` makes systemd reread unit files; it does not restart the service. Run it after editing the unit, then restart the lab unit explicitly. A system service needs administrator access in this disposable VM; do not practice on a shared host.

## Verification

Complete the [SSH identity practice](/modules/03/lessons/m03-l04) on a disposable guest to demonstrate a working key-based login. If you only classified the sample outcomes, record SSH as simulated.

- The service runs as the dedicated non-root account and listens only on loopback.
- The status output and journal agree about whether the service is active.
- A successful local request returns the test content; the controlled failure is visible in the journal.
- After restoring the unit, the health request succeeds and the rollback procedure is written down.

## Troubleshooting

- **Unit does not load:** validate its syntax and run `systemctl daemon-reload` in the VM.
- **Permission denied:** check ownership and permissions on the test directory; do not solve it by running the app as root.
- **Port is already in use:** select another unused high port and update both the unit and test request.
- **The service keeps restarting:** inspect the first failure in the journal before changing the restart policy.

## Cleanup

Stop and disable only the lab unit, remove its unit file and test directory, and delete the lab account only after confirming it owns no other files. Restore the VM snapshot if cleanup is uncertain.

## Evidence to record

Include the disposable VM and rollback point, sanitized unit configuration, service identity, status and journal observations, local health response, controlled failure, recovery check, and exact cleanup performed.

## Self-check

Explain a permission denial, start and stop a service, identify a crash from logs and securely connect
using an SSH key.
