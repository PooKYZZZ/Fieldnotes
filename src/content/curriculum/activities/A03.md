# Linux users, processes and service management

## Scenario

A service that works in a terminal may fail under its service identity because its permissions, working directory or startup environment differ.

## Learning objectives

- Run a local test service as a dedicated non-root account in a disposable VM.
- Compare systemd state, journal messages, listener state and an HTTP health request.
- Introduce one reversible failure and verify recovery from evidence.

## Expected observations

The healthy case shows an active unit, a listener on loopback and the expected local response. In the controlled failure, systemctl and journalctl provide different views: unit state versus recorded events. A running service process alone does not prove that the endpoint works.

## Prerequisites

Complete or study Module 03 in 01_DevOps_Foundations.pdf.

## Challenge

Create a non-root service account; inspect chmod results and process signals; compare systemctl status
with journalctl logs.


## Build outcome

Create a minimal systemd unit for a test web service with restart policy and a written rollback
procedure.

## Environment

Use a disposable Ubuntu VM that you can restore. A system service requires administrator rights, so do not run these
steps on a shared, school, work, or production host.

## Lab steps

1. Record the VM snapshot and inspect a user, process, and service before changing anything.
2. Create a dedicated non-login account for the lab and a small web-root directory owned by that account.
3. Define a systemd unit that runs a local-only test service on an unused high port. Review its user, working
   directory, executable, and restart policy before starting it.
4. Start the unit; inspect `systemctl status` and `journalctl`; request the local endpoint with `curl`.
5. In the disposable VM, introduce one reversible error such as an incorrect test path. Observe the failed state
   and journal entry, restore the unit, then confirm the service recovers.

## Hints

```bash
systemctl status fieldnotes-demo.service
journalctl -u fieldnotes-demo.service --since "10 minutes ago" --no-pager
ss -ltn
curl --fail http://127.0.0.1:18080/
```

Use a unique unit and account name for the lab. Check the unit with `systemd-analyze verify` before enabling it;
enabling at boot is unnecessary for this exercise.

## Verification

- The service runs as the dedicated non-root account and listens only on loopback.
- The status output and journal agree about whether the service is active.
- A successful local request returns the test content; the controlled failure is visible in the journal.
- After restoring the unit, the health request succeeds and the rollback procedure is written down.

## Troubleshooting

- **Unit does not load:** validate its syntax and run `systemctl daemon-reload` in the VM.
- **Permission denied:** check ownership and permissions on the test directory; do not solve it by running the app as root.
- **Port is already in use:** select another unused high port and update both the unit and test request.
- **The service keeps restarting:** inspect the first failure in the journal before changing the restart policy.

## Cleanup

Stop and disable only the lab unit, remove its unit file and test directory, and delete the lab account only after confirming it owns no other files. Restore the VM snapshot if cleanup is uncertain.

## Evidence to record

Include the disposable VM and rollback point, sanitized unit configuration, service identity, status and journal observations, local health response, controlled failure, recovery check, and exact cleanup performed.

## Self-check

Explain a permission denial, start and stop a service, identify a crash from logs and securely connect
using an SSH key.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
