# Continuous integration with GitHub Actions

## Scenario

A change can pass on one laptop and fail in a clean pull-request runner because the workflow depends on hidden local state or grants more permission than it needs.

## Learning objectives

- Run tests and a local image build from a pinned, disposable workflow.
- Observe one intentional test failure and its corrected passing run.
- Review event triggers, logs, secrets exposure and token permissions.

## Expected observations
The baseline pull request should run the test command and local image build with only `contents: read`; it should not publish or deploy. The deliberate failing assertion should fail the test step and make the job red; restoring it should make the job pass. For fork pull requests, GitHub normally withholds repository secrets and grants a read-only token; record any repository settings or approval requirements that change the observed run. A successful workflow is not a required branch check unless that policy is configured.

## Prerequisites

Complete or study Module 10 in 02_Infrastructure_and_Cloud.pdf.

Technical references: GitHub Actions [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [secure use](https://docs.github.com/en/actions/reference/security/secure-use), and [fork-event protections](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

## Challenge

Break a test intentionally; inspect the run log; compare branch and pull-request events; inspect default
token permissions.

## Build outcome

Implement PR checks for your API, including tests and a container build; require passing status
before merge where available.

## Environment

Use a disposable GitHub repository or a local workflow validation branch. Do not add credentials or use this exercise
to trigger deployment to a real environment.

## Lab steps
1. **Use a disposable branch or repository.** Add a workflow for `pull_request`. Start with a read-only token permission and no secrets, publishing, or deployment:

   ```yaml
   name: Validate pull requests
   on:
     pull_request:
   permissions:
     contents: read
   jobs:
     validate:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v7.0.1
         - uses: actions/setup-python@v7.0.0
           with:
             python-version: "3.13"
         - name: Install locked test dependencies
           run: python -m pip install -r requirements-dev.txt
         - name: Run tests
           run: python -m pytest
         - name: Build without publishing
           run: docker build --tag fieldnotes-a10:ci .
   ```

   Adapt the requirements and test command to your project. The action tags make this example readable; before relying on it, pin each action to the verified full commit SHA or a reviewed workflow dependency lockfile, and schedule safe updates. A clean checkout and lock file help avoid hidden laptop state.
2. **Predict the trust boundary.** Before running the workflow, identify which event triggers it, which source code it checks out, what `GITHUB_TOKEN` can do, and whether secrets are available. Use `pull_request`; do not substitute the more privileged `pull_request_target` for a build of untrusted pull-request code.
3. **Run the baseline.** Open a pull request in the disposable repository. Inspect the workflow summary and logs by job and step. Confirm that it ran tests and built locally on the runner without pushing an image.
4. **Test failure feedback.** Add a harmless assertion in the practice branch that is expected to fail, predict which step should fail, and open/update the pull request. Restore the assertion, rerun, and compare the failure and passing run.
5. **Review merge gating.** If the repository allows it, require the validation status check before merge. This setting is separate from a green workflow run; document whether the check was required or merely observed.
6. **Clean up.** Remove the deliberate failure and delete only the test branch/repository you created when you no longer need it.

## Hints
```yaml
permissions:
  contents: read
```

Prefer a full-length action commit SHA verified from the action's own repository, or an Actions workflow dependency lockfile, over a moving branch or major-version tag. `pull_request_target` runs with elevated trust; do not use it to check out and execute untrusted pull-request code. Treat a container build as a test artifact, not as a deployment.

## Verification

- The workflow runs tests and an image build on the intended pull-request event.
- The controlled failing assertion produces a failed check; the corrected branch passes.
- The job does not publish an image, deploy, or request write permissions it does not need.
- The README describes how to read a failed step and rerun the check.

## Troubleshooting

- **Workflow does not trigger:** check the event name, branch filters, and YAML indentation.
- **Dependency install differs locally and in CI:** use the lockfile and the package manager's reproducible install.
- **Permission denied:** identify the exact API operation and grant only its required permission.
- **Pull-request secrets are unavailable:** expected restrictions may apply to forked contributions; do not weaken them.

## Cleanup

Revert the deliberate failing assertion and keep the workflow only in your practice branch until its permissions and required checks are reviewed.

## Evidence to record

Include the workflow file, event and permission review, the failing and corrected check results or run links, the build/test logs needed to reproduce them, and confirmation that no image was published or deployed.

## Self-check

Explain every workflow step and identify why an intentionally failing test blocks merging.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
