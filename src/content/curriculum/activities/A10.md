# Continuous integration with GitHub Actions

## Prerequisites

Complete or study Module 10 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Break a test intentionally; inspect the run log; compare branch and pull-request events; inspect default
token permissions.

## Build outcome

Implement PR checks for your API, including tests and a container build; require passing status
before merge where available.

## Environment

Use a disposable GitHub repository or a local workflow validation branch. Do not add credentials or use this exercise
to trigger deployment to a real environment.

## Lab steps

1. Add a workflow that installs pinned project dependencies, runs the existing tests, and builds the application
   image without publishing it.
2. Set the workflow token to the minimum permissions needed (start with read-only contents access). Avoid
   third-party actions that are not necessary for the exercise.
3. Run the workflow on a pull request and inspect the job, step, and test logs.
4. Introduce a harmless test assertion failure in the practice branch, verify the check fails, then revert that
   assertion and verify the run passes.
5. Compare pull-request and branch events; document which events can access secrets and which workflow steps can
   write to the repository.

## Hints

```yaml
permissions:
  contents: read
```

Prefer immutable action versions and keep untrusted pull-request code away from privileged secrets. A successful
container build is not a deployment.

## Verification

- The workflow runs tests and an image build on the intended pull-request event.
- The controlled failing assertion produces a failed check; the corrected branch passes.
- The job does not publish an image, deploy, or request write permissions it does not need.
- The README describes how to read a failed step and rerun the check.

## Troubleshooting

- **Workflow does not trigger:** check the event name, branch filters, and YAML indentation.
- **Dependency install differs locally and in CI:** use the lockfile and the package manager's reproducible install.
- **Permission denied:** identify the exact API operation and grant only its required permission.
- **Pull-request secrets are unavailable:** expected restrictions may apply to forked contributions; do not weaken them.

## Cleanup

Revert the deliberate failing assertion and keep the workflow only in your practice branch until its permissions and required checks are reviewed.

## Evidence to record

One short readme/note containing expected result, actual result, commands or test case
evidence, and a failure case; avoid full solution copy-pastes.

## Self-check

Explain every workflow step and identify why an intentionally failing test blocks merging.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
