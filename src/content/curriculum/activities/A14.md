# Terraform and Infrastructure as Code

## Scenario

Terraform proposes changes from configuration and state, but a small variable edit can replace a resource or expose that the real resource has drifted.

## Learning objectives

- Use a disposable workspace and local-only provider for one test resource.
- Predict plan changes before each apply and inspect the resulting state.
- Compare configuration, state and the resource after one controlled out-of-band change.

## Expected observations
The first plan should propose creating only `local_file.lab_marker`; the first apply creates the synthetic file and state entry. Changing `message` should plan an update to that file. Editing the file outside Terraform should appear as drift when the local provider refreshes it; the next reviewed apply restores the configured contents. The destroy plan should name only the activity resource. This demonstrates Terraform's desired-state and state comparison on a local file; it does not prove behavior of a cloud provider or remote infrastructure.

## Prerequisites

Complete or study Module 14 in 02_Infrastructure_and_Cloud.pdf.

Technical references: HashiCorp [`terraform plan`](https://developer.hashicorp.com/terraform/cli/commands/plan), [state handling](https://developer.hashicorp.com/terraform/language/state), and the official [`hashicorp/local` file resource](https://registry.terraform.io/providers/hashicorp/local/latest/docs/resources/file).

## Challenge

Predict a plan before running it; change one variable; inspect state; destroy all local objects; test how
drift appears.

## Build outcome

Provision a local Docker resource first, then optionally reproduce one Azure network resource
after reviewing cost.

## Environment
Use a new temporary directory and the official `hashicorp/local` provider to manage one harmless file inside that directory. This models Terraform's plan/state/drift workflow without Docker or cloud credentials; it does not provision or verify a cloud resource. Keep the state and any saved plan out of Git and public logs because they can contain sensitive values. Never point the configuration at an existing project, home directory, or application data file.

## Lab steps
1. **Create a disposable workspace outside your source repository.** Make an `output` directory and a Terraform file containing a single `local_file` resource:

   ```hcl
   terraform {
     required_providers {
       local = {
         source  = "hashicorp/local"
         version = "~> 2.0"
       }
     }
   }

   variable "message" {
     type    = string
     default = "planned state"
   }

   resource "local_file" "lab_marker" {
     filename        = "${path.module}/output/lab.txt"
     content         = var.message
     file_permission = "0600"
   }
   ```

   Create `output/` before planning. Keep any Terraform state and plan file in this disposable directory.
2. **Format and inspect before applying.** Run `terraform fmt -check`, `terraform init`, `terraform validate`, then `terraform plan`. Predict the resource action. Continue only if the plan proposes the one expected local file and no unrelated or destructive action.
3. **Apply and record state.** Run `terraform apply`, approve only the reviewed plan, inspect `terraform state list`, and read the exact synthetic file. Do not print or attach the state file.
4. **Change desired configuration.** Run `terraform plan -var='message=reviewed state'`; compare the planned change with your prediction. Apply only if it still targets the lab file. Confirm its contents and inspect state again.
5. **Simulate external drift.** Change only `output/lab.txt` by hand to `manual drift`, then run `terraform plan` without changing configuration. Record whether the local provider detects a correction and what value it plans to restore. Apply the reviewed correction and verify the file matches configuration.
6. **Plan cleanup.** Run `terraform plan -destroy`, confirm the plan targets only `local_file.lab_marker`, then destroy it. Check that the lab output file is gone before deleting the temporary workspace. Do not run cloud provisioning or a broad cleanup command.

## Hints
```bash
terraform fmt -check
terraform init
terraform validate
terraform plan
terraform state list
terraform plan -destroy
```

`terraform plan` previews proposed changes and does not apply them. A saved plan can contain configuration and sensitive values; do not attach it to evidence. If the plan targets another path or resource, stop and check the working directory, resource filename, and state before proceeding.

## Verification

- The first plan matches the intended one-resource change and no unrelated resource is present.
- The state lists only the activity resource; the drift plan identifies the out-of-band change.
- The final plan is reviewed before apply or destroy, and the local resource is removed.
- State, provider context, and cleanup steps are described without exposing secret values.

## Troubleshooting

- **Provider cannot connect:** check the Docker context and daemon before editing Terraform configuration.
- **Plan wants unrelated deletion:** stop; verify the working directory, state path, provider, and resource names.
- **State lock or provider error:** read the error and resolve it in this isolated workspace; do not delete state blindly.
- **Drift does not appear:** confirm the change was made outside Terraform to the resource tracked in this state.

## Cleanup

Review `terraform plan -destroy` before running `terraform destroy`. Remove only the activity's test resource and state directory after confirming no work needs to be retained.

## Evidence to record

Include the provider and working directory checked, plan prediction and reviewed plan summary, state resource names, controlled drift observation, final cleanup plan/result, and any interrupted operation. Never attach a Terraform state file or secret values.

## Self-check

Explain state and drift; review the plan for unintended deletion; reproduce and clean up resources
confidently.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
