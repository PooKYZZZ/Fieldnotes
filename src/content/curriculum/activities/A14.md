# Terraform and Infrastructure as Code

## Scenario

Terraform proposes changes from configuration and state, but a small variable edit can replace a resource or expose that the real resource has drifted.

## Learning objectives

- Use a disposable workspace and local-only provider for one test resource.
- Predict plan changes before each apply and inspect the resulting state.
- Compare configuration, state and the resource after one controlled out-of-band change.

## Expected observations

The first plan contains only the intended lab resource. Changing the selected variable yields a plan whose additions, updates or replacements can be compared with the prediction. A controlled drift appears as a difference between the actual local object and recorded configuration/state. Stop if a plan includes unrelated or destructive changes.

## Prerequisites

Complete or study Module 14 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Predict a plan before running it; change one variable; inspect state; destroy all local objects; test how
drift appears.

## Build outcome

Provision a local Docker resource first, then optionally reproduce one Azure network resource
after reviewing cost.

## Environment

Use a new directory and a local Docker provider resource only. Confirm the Terraform working directory and Docker
context before any apply; do not configure cloud credentials for this exercise.

## Lab steps

1. Create a minimal Terraform configuration for one named local test resource. Keep state in the disposable
   workspace and exclude it from Git.
2. Run `terraform fmt -check`, `terraform init`, `terraform validate`, and review `terraform plan`.
3. Predict the resource change, then apply only after confirming the plan matches that prediction.
4. Inspect state and the running local resource. Change one harmless variable, predict the second plan, then apply
   and observe what changed.
5. Simulate drift by changing the test resource outside Terraform. Run plan again, explain the difference, and
   restore state through a reviewed apply or destroy.

## Hints

```bash
terraform fmt -check
terraform validate
terraform plan
terraform state list
```

A plan is a proposal, not permission to ignore its deletion or replacement actions. Never paste state files into
public logs; they can contain sensitive values.

## Verification

- The first plan matches the intended one-resource change and no unrelated resource is present.
- The state lists only the activity resource; the drift plan identifies the out-of-band change.
- The final plan is reviewed before apply or destroy, and the local resource is removed.
- State, provider context, and cleanup steps are described without exposing secret values.

## Troubleshooting

- **Provider cannot connect:** check the Docker context and daemon before editing Terraform configuration.
- **Plan wants unrelated deletion:** stop; verify the working directory, state path, provider, and resource names.
- **State lock or provider error:** read the error and resolve it in this isolated workspace; do not delete state blindly.
- **Drift does not appear:** confirm the change was made outside Terraform to the resource tracked in this state.

## Cleanup

Review `terraform plan -destroy` before running `terraform destroy`. Remove only the activity's test resource and state directory after confirming no work needs to be retained.

## Evidence to record

Include the provider and working directory checked, plan prediction and reviewed plan summary, state resource names, controlled drift observation, final cleanup plan/result, and any interrupted operation. Never attach a Terraform state file or secret values.

## Self-check

Explain state and drift; review the plan for unintended deletion; reproduce and clean up resources
confidently.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
