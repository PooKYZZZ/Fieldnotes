# Ansible and configuration management

## Scenario

Configuration management should converge a host to a desired state, rather than report changes on every run or silently make broad changes across a fleet.

## Learning objectives

- Limit an inventory to one snapshot-backed disposable VM.
- Apply a small playbook twice and compare the task recap.
- Introduce a harmless drift and confirm only relevant tasks correct it.

## Expected observations

The first run reports the intended change; a second unchanged run should report no unnecessary changes for supported idempotent modules. After a controlled configuration drift, the corresponding task changes and any notified handler runs only when appropriate. Check mode is a preview, so verify the host after an actual lab apply.

## Prerequisites

Complete or study Module 15 in 02_Infrastructure_and_Cloud.pdf.

## Challenge

Run the same playbook twice; introduce a package or config drift; rerun; observe exactly which tasks
changed.

## Build outcome

Configure a clean Ubuntu VM with a service account, runtime packages, NGINX and the status
service.

## Environment

Use a disposable Ubuntu VM and an inventory that names only that VM. Take a restorable snapshot first. Never run the
playbook against `all`, a shared fleet, or a production host.

## Lab steps

1. Write a small playbook that ensures one package and one test configuration are present, then starts a test
   service. Make privileged tasks explicit.
2. Run syntax checks and a check-mode/diff preview against the disposable VM; read every proposed change.
3. Apply the playbook to the named VM, then run it a second time without changing inputs.
4. Introduce a harmless configuration drift in the VM and run the playbook again. Inspect which task changed and
   whether its handler ran.
5. Record how to restore the original configuration or revert the VM snapshot.

## Hints

```bash
ansible-playbook --syntax-check -i inventory.ini site.yml
ansible-playbook --check --diff -i inventory.ini site.yml
ansible-playbook -i inventory.ini site.yml
```

Check mode is a useful preview but not a perfect simulation: some modules do not support it fully. Verify the actual
result on the lab host.

## Verification

- The inventory resolves only to the intended disposable VM.
- The first run reaches the target state; the second run reports no unnecessary changes.
- After drift, the playbook restores the intended state and only relevant tasks change.
- The evidence lists privileged changes and a working rollback or snapshot procedure.

## Troubleshooting

- **Host limit includes unexpected machines:** do not run the playbook; correct the inventory and confirm the target.
- **Check mode differs from apply:** check module support and verify the actual changed state afterward.
- **A handler does not run:** confirm the notifying task changed and the handler name matches.
- **SSH fails:** validate the lab key and VM address without copying private key material into the repository.

## Cleanup

Restore the VM snapshot or remove the dedicated test VM. Do not run cleanup against a shared inventory; retain only the playbook and sanitized recap.

## Evidence to record

Include the inventory target boundary, syntax/check-mode preview, first and second run recaps, the controlled drift and handler behavior, the actual verification and the available snapshot or rollback path.

## Self-check

Reproduce configuration on a fresh VM and describe every privileged change with a rollback option.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
