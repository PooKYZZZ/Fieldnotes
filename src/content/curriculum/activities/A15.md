# Ansible and configuration management

## Scenario

Configuration management should converge a host to a desired state, rather than report changes on every run or silently make broad changes across a fleet.

## Learning objectives

- Limit an inventory to one snapshot-backed disposable VM.
- Apply a small playbook twice and compare the task recap.
- Introduce a harmless drift and confirm only relevant tasks correct it.

## Expected observations
The first run creates the directory and managed file and notifies the demonstration handler. The unchanged second run reports no changes and does not notify it. After you edit the managed file by hand, the third run restores its declared content and notifies the handler once. `--check --diff` previews likely changes, but it is not a substitute for verifying the actual lab host after apply.

## Prerequisites
Study Module 15 in 02_Infrastructure_and_Cloud.pdf. Review the official [Ansible playbook guide](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_intro.html), especially desired state, idempotence, and handlers.

## Challenge

Run the same playbook twice, introduce harmless drift in its managed text file, and rerun it. Explain why the file task and notification handler changed while the unchanged run did not.

## Build outcome

Manage one harmless file on a single disposable VM and demonstrate repeatable desired-state convergence without restarting a service.

## Environment

Use a disposable Ubuntu VM and an inventory that names only that VM. Take a restorable snapshot first. Never run the
playbook against `all`, a shared fleet, or a production host.

## Lab steps
1. **Bound the target first.** Create an inventory with exactly one alias for your disposable VM. Use a dedicated SSH identity outside the repository, verify the VM fingerprint, and inspect the resolved target before running a play.
2. **Preview a small desired state.** Create `site.yml` that manages a directory and a text file in the remote lab user's home using `ansible.builtin.file` and `ansible.builtin.copy`. Give the file a fixed mode and a known sentence. Do not use `become` for this home-directory exercise.
3. Add a handler using `ansible.builtin.debug` that says the managed file changed; have the copy task notify it. This safe demonstration makes handler timing visible without restarting a real service.
4. Run `--syntax-check`, then `--check --diff`. Read the inventory target and every proposed path before applying. Apply once, capture the task recap and handler output, then apply again without changes.
5. Append a harmless line to the managed file on the lab VM and run the playbook again. Compare the recaps and explain why the file task and handler ran. Inspect the final file content and remove only the lab directory after recording evidence.

## Hints

The following playbook gives the directory and file fixed desired states. The handler is deliberately a `debug` action, so the exercise demonstrates notification without restarting a service:

```yaml
- name: Manage an A15 text fixture
  hosts: lab
  vars:
    lab_dir: "{{ ansible_env.HOME }}/fieldnotes-a15"
  tasks:
    - name: Ensure the lab directory exists
      ansible.builtin.file:
        path: "{{ lab_dir }}"
        state: directory
        mode: "0700"
    - name: Ensure the managed file has the declared content
      ansible.builtin.copy:
        dest: "{{ lab_dir }}/status.txt"
        content: "A15 configuration is present\n"
        mode: "0600"
      notify: Report the configuration change
  handlers:
    - name: Report the configuration change
      ansible.builtin.debug:
        msg: "The managed file changed; no service was restarted."
```

A minimal inventory should contain one `[lab]` host. Verify it with `ansible-inventory -i inventory.ini --list` before using `ansible-playbook`. Typical sequence:

```bash
ansible-playbook --syntax-check -i inventory.ini site.yml
ansible-playbook --check --diff -i inventory.ini site.yml
ansible-playbook -i inventory.ini site.yml
ansible-playbook -i inventory.ini site.yml
```

Use fully qualified module names such as `ansible.builtin.copy`. A handler runs only after a notifying task reports a change; check mode can approximate this but does not guarantee every module's real apply behavior.

## Verification
- The resolved inventory contains only the named disposable VM, and all managed paths are beneath that lab user's home directory.
- The preview identifies the expected file change; the first apply creates it and the immediate second apply reports no unnecessary changes.
- After controlled drift, only the copy task changes and the demonstration handler runs; the restored file matches the declared content.
- Evidence distinguishes a preview from an actual post-apply check and includes a safe rollback/cleanup path.

## Troubleshooting
- **Unexpected host or path appears:** do not apply; inspect inventory aliases, groups, variables, and the rendered play target.
- **Second run still changes:** inspect file content, mode, owner, templating, and any timestamps or generated values that make the desired state unstable.
- **Handler does not run:** confirm the notifying task changed and that the handler name matches exactly.
- **SSH fails:** check the lab address, user, key permissions, and host fingerprint without copying a private key into the repository.

## Cleanup

Restore the VM snapshot or remove the dedicated test VM. Do not run cleanup against a shared inventory; retain only the playbook and sanitized recap.

## Evidence to record
Include the one-host inventory boundary, syntax and preview result, first and second run recaps, the exact harmless drift, the third-run correction and handler output, final file verification, and cleanup/rollback path. Exclude private key material and real host details.

## Self-check

Reproduce the declared file state on a fresh VM. Explain why this playbook needs no privilege and which changes would require explicit elevation and a rollback plan.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
