# Software supply chain and secure CI/CD

## Scenario

A clean build can still contain a risky dependency or base image, while a scanner finding can be a false positive or outside the reachable application path.

## Learning objectives

- Add non-publishing dependency and image checks to a disposable branch.
- Use a safe documented policy fixture to verify a failing gate without adding vulnerable code.
- Trace a sample finding to its input, scope, owner and evidence-based disposition.

## Expected observations

The controlled policy fixture causes the designated check to fail, and removing or correcting it restores a passing run. A finding should name its scanned package or image and affected range; the result is limited by scanner coverage and database freshness and does not certify application security.

## Prerequisites
Review the [Module 21 learning path](/modules/21) before starting; the activity reference PDF is optional. Use the official [Trivy filesystem scanning guide](https://trivy.dev/docs/latest/guide/target/filesystem/), [Trivy misconfiguration scanning guide](https://trivy.dev/docs/latest/guide/scanner/misconfiguration/), and [GitHub dependency review guidance](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review).

## Challenge
Scan a local source tree and one locally built image, then demonstrate that a safe misconfiguration policy fixture can block a check and pass after correction. Report scanner coverage and database freshness; do not add a vulnerable dependency or publish an artifact.

## Build outcome

Create a secure pipeline that tests, scans, versions and records a deployable container artifact.

## Environment

Use a disposable CI branch and local scanner tools or repository-provided checks. Do not publish an image or deploy
to an environment. Do not add a known vulnerable dependency or base image just to trigger a scanner.

## Lab steps
1. In a disposable branch, identify the lockfiles, configuration files, and Dockerfile/build context that belong to the app. Make a sanitized working copy with no `.env` files or credentials in the scan directory; record scanner/tool versions.
2. If the project builds a container, build its actual app image locally as `fieldnotes-a21:lab` from the reviewed Dockerfile/context (for example, `docker build -t fieldnotes-a21:lab .` from that context) and record its image ID. If it has no container artifact, mark the image scan not applicable rather than scanning an unrelated image. Run `trivy fs --scanners vuln,misconfig,secret .` on the sanitized source tree and, when applicable, `trivy image fieldnotes-a21:lab`. Record which scanners ran, inputs, database timestamp, and whether each result was clean, had findings, or could not complete. A finding is not automatically exploitable; inspect package/version, affected range, fix, and application reachability.
3. Validate a gate without adding a vulnerable package or running an unsafe image. In a throwaway directory named `trivy-policy-fixture`, create a Dockerfile containing `FROM scratch` and `USER root`; run `trivy config --exit-code 1 --severity HIGH,CRITICAL ./trivy-policy-fixture`. It should report the root-user policy finding and return a failing gate. Change the fixture to `USER 10001` and rerun. This checks one image-configuration policy only; it does not prove CVE detection or that the full pipeline is secure. Do not build or run either fixture.
4. In the test workflow, keep scanning read-only and non-publishing. If GitHub Dependency Review is unavailable for the repository plan/type, record the limitation and run the local scanner checks instead; the feature is available for public repositories and eligible private repositories with Code Security/Advanced Security.
5. Re-run the corrected fixture and the normal project gates. Document who owns a finding, the evidence for disposition, and an expiry/review date for any accepted exception. Keep only sanitized reports.

## Hints

- Pin scanner versions and preserve machine-readable reports as CI artifacts with appropriate retention.
- Keep CI permissions read-only unless a specific job needs more.
- A clean scan is not proof that the application is secure; document coverage gaps.

## Verification

- Tests, scans, and build run on the intended pull request without publishing or deploying.
- The controlled policy failure blocks the check and the corrected branch passes.
- Findings can be traced to a dependency/image and have an owner and evidence-based disposition.
- The README states scanner scope, limits, and exception review rules.

## Troubleshooting

- **Scanner cannot access the registry:** use the intended local image or a permitted public base image; do not add
  broad credentials.
- **Finding appears unrelated:** verify the lockfile/image digest and scanner database timestamp before disposition.
- **A suppression hides new findings:** scope it narrowly, document why, and give it an expiry or review date.

## Cleanup

Revert the deliberate test-only failing rule and remove generated reports if they contain unnecessary metadata. Keep only the reviewed workflow and sanitized findings summary.

## Evidence to record

Include scanner and version, scanned inputs, sanitized finding metadata, policy fixture and failing/pass results, disposition and owner, and documented coverage or database-freshness limitations. Do not add vulnerable artifacts or publish images.

## Self-check

Show that an intentionally failing security gate blocks release and explain what the gate does not detect.

## Independent reflection

Make two paper promotion decisions. In the first case the reviewed revision and builder match policy and the provenance subject matches the built image digest. In the second the release label is the same but the digest differs. Compare the associated software inventory and scan result, then explain what each piece of evidence can establish. This classification does not require publishing an artifact or running a deliberately vulnerable service.

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
