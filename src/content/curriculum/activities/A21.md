# Software supply chain and secure CI/CD

## Scenario

A clean build can still contain a risky dependency or base image, while a scanner finding can be a false positive or outside the reachable application path.

## Learning objectives

- Add non-publishing dependency and image checks to a disposable branch.
- Use a safe documented policy fixture to verify a failing gate without adding vulnerable code.
- Trace a sample finding to its input, scope, owner and evidence-based disposition.

## Expected observations

The controlled policy fixture causes the designated check to fail, and removing or correcting it restores a passing run. A finding should name its scanned package or image and affected range; the result is limited by scanner coverage and database freshness and does not certify application security.

## Prerequisites

Complete or study Module 21 in 03_Operations_and_Security.pdf.

## Challenge

Add dependency and image scanning to a test pipeline; document a false-positive handling process and
an intentionally blocked risky change.

## Build outcome

Create a secure pipeline that tests, scans, versions and records a deployable container artifact.

## Environment

Use a disposable CI branch and local scanner tools or repository-provided checks. Do not publish an image or deploy
to an environment. Do not add a known vulnerable dependency or base image just to trigger a scanner.

## Lab steps

1. Add dependency and container-image scanning to the test pipeline alongside tests and a reproducible build.
2. Record tool versions, scanned inputs, and what each scanner can detect.
3. Verify the scanner with a safe documented fixture or a controlled policy failure that contains no exploitable
   code or vulnerable runtime artifact.
4. Inspect a sample finding; confirm its package/image, severity, affected version range, fix availability, and
   whether it is reachable in this application.
5. Correct the controlled failure, rerun the gates, and document a review path for false positives, exceptions,
   expiry, and ownership.

## Hints

- Pin scanner versions and preserve machine-readable reports as CI artifacts with appropriate retention.
- Keep CI permissions read-only unless a specific job needs more.
- A clean scan is not proof that the application is secure; document coverage gaps.

## Verification

- Tests, scans, and build run on the intended pull request without publishing or deploying.
- The controlled policy failure blocks the check and the corrected branch passes.
- Findings can be traced to a dependency/image and have an owner and evidence-based disposition.
- The README states scanner scope, limits, and exception review rules.

## Troubleshooting

- **Scanner cannot access the registry:** use the intended local image or a permitted public base image; do not add
  broad credentials.
- **Finding appears unrelated:** verify the lockfile/image digest and scanner database timestamp before disposition.
- **A suppression hides new findings:** scope it narrowly, document why, and give it an expiry or review date.

## Cleanup

Revert the deliberate test-only failing rule and remove generated reports if they contain unnecessary metadata. Keep only the reviewed workflow and sanitized findings summary.

## Evidence to record

Include scanner and version, scanned inputs, sanitized finding metadata, policy fixture and failing/pass results, disposition and owner, and documented coverage or database-freshness limitations. Do not add vulnerable artifacts or publish images.

## Self-check

Show that an intentionally failing security gate blocks release and explain what the gate does not detect.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
