# Incidents, backups, recovery and disaster scenarios

## Prerequisites

Complete or study Module 23 in 03_Operations_and_Security.pdf.


## Challenge

Stop the API, corrupt a noncritical config in a copied lab, restore a test database snapshot and record the
timeline.

## Build outcome

Complete a controlled incident drill with detection, mitigation, data restoration and short
postmortem.

## Environment

Use a disposable local database or a copy of a lab database with synthetic records. Confirm the backup path and
snapshot before changing data. Never stop or modify a production service or database for this activity.

## Lab steps

1. Record the test service's baseline health and create a few synthetic database rows with known identifiers.
2. Create a backup using the documented tool. Record its time, size, and checksum; keep it outside the database
   container or volume being tested.
3. Stop only the lab API and simulate an incident using a copied configuration or disposable test data.
4. Restore the database into the isolated lab target, start the API, and verify the known rows and health endpoint.
5. Write a timeline covering detection, mitigation, restore, verification, and communication. Compare actual recovery
   time and data loss with your stated RTO and RPO assumptions.

## Hints

- Verify that the backup is readable before relying on it.
- Keep the source backup unchanged; restore into a separate test target where practical.
- A successful restore command is not enough: query known records and exercise the application path.
- Use sanitized output and synthetic identifiers in the postmortem.

## Verification

- The backup checksum matches before and after the drill and the restore target is the disposable lab.
- Known records are present after restore and the API's read path succeeds.
- The timeline measures observed recovery and data-loss window rather than guessed values.
- The postmortem records cause, impact, detection gap, follow-up owner, and one prevention or detection improvement.

## Troubleshooting

- **Backup will not restore:** inspect version compatibility, permissions, format, and restore logs without replacing
  the source backup.
- **API remains unhealthy:** inspect application configuration and database connectivity separately.
- **Data is missing:** check which backup was used and compare the synthetic identifiers to the pre-drill record.

## Cleanup

After verifying the drill, stop the test service and remove only the copied databases, backup, and config created for this activity. Preserve the original disposable fixture if you need to repeat it.

## Evidence to record

One short readme/note containing expected result, actual result, commands or test case
evidence, and a failure case; avoid full solution copy-pastes.

## Self-check

Prove a working restore and explain what data or service availability would be at risk in a real outage.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
