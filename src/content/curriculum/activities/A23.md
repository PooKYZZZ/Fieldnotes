# Recovery drill: restore and verify synthetic data

## Scenario

A recovery plan should be tested with isolated data so the operator can distinguish a valid backup copy from a successful application recovery.

## Learning objectives

- Create and back up only the synthetic SQLite fixture in a new temporary directory.
- Restore into a separate file and verify its checksum, integrity and expected record IDs.
- Measure database-only recovery and state clearly which service-recovery steps remain untested.

## Expected observations

The backup checksum stays unchanged and SQLite integrity_check reports ok for the synthetic copy. The separate restored file contains the IDs present at backup time and excludes the later synthetic row. The measured interval covers only the operations timed in this drill, not application startup, dependencies or user access.

## Prerequisites

Study the three Module 23 lessons. Use a disposable Ubuntu or other Linux shell with Python 3 and its standard library.

## Environment

This exercise creates a new temporary directory and a synthetic SQLite database. Run every command in the same Bash session and keep `LAB_DIR` pointed at the `fieldnotes-recovery.*` directory created in Step 1. Never point it at a real database, repository, Docker volume, or backup. Do not stop or modify Fieldnotes, Docker Compose, or any live service.

## Challenge

Restore known synthetic records into a separate SQLite target after simulated data loss. Verify the backup bytes, database integrity, and expected records, then report the measured data-loss interval and database restore time.

## Build outcome

Produce a short recovery note with the backup checksum, restored record IDs, integrity result, chosen RPO/RTO targets, observed timings, and the limits of this database-only drill.

## Lab steps

1. **Create an isolated fixture.** Set restrictive permissions, create a new temporary folder, and seed two recognizable synthetic records. Keep this terminal open for the whole exercise.

   ```bash
   umask 077
   LAB_DIR="$(mktemp -d "${TMPDIR:-/tmp}/fieldnotes-recovery.XXXXXX")"
   export LAB_DIR
   printf 'Disposable lab: %s\n' "$LAB_DIR"

   python3 - <<'PY'
   import os
   import sqlite3
   from datetime import datetime, timezone
   from pathlib import Path

   database = Path(os.environ["LAB_DIR"]) / "service.sqlite"
   now = datetime.now(timezone.utc).isoformat(timespec="seconds")
   with sqlite3.connect(database) as connection:
       connection.execute(
           "CREATE TABLE records (record_id TEXT PRIMARY KEY, value TEXT NOT NULL, created_at TEXT NOT NULL)"
       )
       connection.executemany(
           "INSERT INTO records VALUES (?, ?, ?)",
           [("synthetic-001", "alpha", now), ("synthetic-002", "beta", now)],
       )
   print(f"Created synthetic fixture: {database}")
   PY
   ```

2. **Create and verify a backup.** Set recovery targets before the simulated incident. The sample values below are for this small drill only. Record the backup cutoff and checksum; use SQLite's backup API so the copy is made through SQLite rather than copying a potentially open database file.

   ```bash
   RPO_TARGET_SECONDS=86400
   RTO_TARGET_SECONDS=300

   python3 - <<'PY'
   import os
   import sqlite3
   from pathlib import Path

   lab = Path(os.environ["LAB_DIR"])
   with sqlite3.connect(lab / "service.sqlite") as source, sqlite3.connect(lab / "backup.sqlite") as backup:
       source.backup(backup)
   PY

   BACKUP_CUTOFF="$(date -u +%s)"

   python3 - <<'PY'
   import os
   import sqlite3
   from pathlib import Path

   lab = Path(os.environ["LAB_DIR"])
   with sqlite3.connect(lab / "backup.sqlite") as backup:
       result = backup.execute("PRAGMA integrity_check").fetchone()[0]
       if result != "ok":
           raise SystemExit(f"Backup integrity check failed: {result}")
       print(f"Backup integrity: {result}")
   PY

   BACKUP_HASH="$(sha256sum "$LAB_DIR/backup.sqlite" | awk '{print $1}')"
   printf 'Backup SHA-256: %s\nBackup cutoff (UTC epoch): %s\n' "$BACKUP_HASH" "$BACKUP_CUTOFF"
   ```

3. **Simulate a bounded data-loss incident.** Add one known record after the backup, record when the incident is observed, and delete only the two named synthetic rows from the fixture. The backup and all real data remain untouched.

   ```bash
   python3 - <<'PY'
   import os
   import sqlite3
   from datetime import datetime, timezone
   from pathlib import Path

   database = Path(os.environ["LAB_DIR"]) / "service.sqlite"
   now = datetime.now(timezone.utc).isoformat(timespec="seconds")
   with sqlite3.connect(database) as connection:
       connection.execute("INSERT INTO records VALUES (?, ?, ?)", ("synthetic-003", "after-backup", now))
   PY

   INCIDENT_OBSERVED="$(date -u +%s)"
   python3 - <<'PY'
   import os
   import sqlite3
   from pathlib import Path

   database = Path(os.environ["LAB_DIR"]) / "service.sqlite"
   with sqlite3.connect(database) as connection:
       connection.executemany("DELETE FROM records WHERE record_id = ?", [("synthetic-002",), ("synthetic-003",)])
       print("Simulated loss of two synthetic rows; source file remains in the temporary lab.")
   PY
   ```

4. **Restore into a separate target.** Do not overwrite `service.sqlite` or `backup.sqlite`. Start timing the restore and verification path, then restore the saved backup into a new file and check integrity plus the expected IDs.

   ```bash
   RESTORE_START="$(date -u +%s)"
   python3 - <<'PY'
   import os
   import sqlite3
   from pathlib import Path

   lab = Path(os.environ["LAB_DIR"])
   with sqlite3.connect(lab / "backup.sqlite") as backup, sqlite3.connect(lab / "restored.sqlite") as restored:
       backup.backup(restored)
   with sqlite3.connect(lab / "restored.sqlite") as restored:
       integrity = restored.execute("PRAGMA integrity_check").fetchone()[0]
       ids = [row[0] for row in restored.execute("SELECT record_id FROM records ORDER BY record_id")]
   expected = ["synthetic-001", "synthetic-002"]
   print(f"Restore integrity: {integrity}")
   print(f"Restored IDs: {ids}")
   if integrity != "ok" or ids != expected:
       raise SystemExit("Restore verification failed; preserve the lab files and investigate.")
   PY

   printf '%s  %s\n' "$BACKUP_HASH" "$LAB_DIR/backup.sqlite" | sha256sum --check
   RESTORE_END="$(date -u +%s)"
   printf 'Observed data-loss interval: %s seconds\n' "$((INCIDENT_OBSERVED - BACKUP_CUTOFF))"
   printf 'Database restore and verification time: %s seconds\n' "$((RESTORE_END - RESTORE_START))"
   printf 'Targets chosen before the drill: RPO %s seconds; RTO %s seconds\n' "$RPO_TARGET_SECONDS" "$RTO_TARGET_SECONDS"
   ```

5. **Compare evidence with targets.** State whether the observed data-loss interval and database restore/verification time were within your chosen targets. Explain that this timing does not include service startup, dependency recovery, access restoration, communication, or operational approval.

## Hints

- `sqlite3.Connection.backup()` creates a consistent copy through SQLite's API.
- `PRAGMA integrity_check` checks database structure; it does not test an application's queries or configuration.
- The checksum proves whether the backup bytes stayed the same. It does not prove that the application can use the backup.
- A recent backup may still be unsuitable if its credentials, encryption key, storage, or runbook are unavailable during recovery.
- This fixture uses one local temporary directory, so it does not test off-host, immutable, or independently controlled backup storage.

## Verification

- The backup checksum is unchanged after the drill and the backup passed `PRAGMA integrity_check`.
- The separate restored target contains `synthetic-001` and `synthetic-002`; `synthetic-003` is absent because it was written after the backup cutoff.
- The note records UTC cutoff and incident times, observed data-loss interval, and database restore/verification duration.
- The conclusion distinguishes a database-file drill from a full service recovery test and does not claim an RTO for an untested application.

## Troubleshooting

- **Python reports that the lab path is missing:** stay in the same Bash session and re-run Step 1; do not substitute a real path.
- **The backup integrity check fails:** keep the source and backup files for inspection; do not overwrite either one with the failed restore.
- **The restored IDs differ:** compare the fixture IDs, backup cutoff, and restore source. Preserve the temporary files until you understand the mismatch.
- **`sha256sum` is unavailable:** record that limitation and use an approved local SHA-256 utility; do not install software during the drill.
