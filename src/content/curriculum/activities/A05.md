# HTTP, TLS, APIs and reverse proxies

## Scenario

A reverse proxy can accept a client request while its upstream application is unavailable, misrouted or speaking an unexpected protocol.

## Learning objectives

- Trace one local request from client through NGINX to a test API.
- Compare direct and proxied responses, including headers and status codes.
- Use a controlled upstream failure and confirm the diagnosis in proxy logs.

## Expected observations
The direct and proxied `/health` requests should both return HTTP `200` with `{"status":"ok"}`. The `Server`/`Date` headers may differ because the proxy and API can add or alter headers; compare the status and body first. With the proxy pointed to an unused upstream port, the client should receive `502 Bad Gateway`, and the NGINX error log should identify the failed upstream connection. Restoring the known port and reloading should return the original result. A `502` is a symptom at the proxy/upstream boundary, not proof that the API code itself is broken.

## Prerequisites

Complete or study Module 05 in 01_DevOps_Foundations.pdf.

Technical references: [FastAPI first steps](https://fastapi.tiangolo.com/tutorial/first-steps/), [NGINX proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), and [HTTP status semantics (RFC 9110)](https://www.rfc-editor.org/rfc/rfc9110.html).

## Challenge

Inspect headers with curl -i/-v; compare 200, 404 and 502 behavior; draw browser -> DNS -> TLS ->
NGINX -> API.

## Build outcome

Put a tiny /health FastAPI endpoint behind NGINX in a local VM; document exactly how requests
reach it.

## Environment

Use a disposable Linux VM or local containers with a tiny test API and NGINX. Bind the test services to loopback or
an isolated Compose network; do not expose them to the internet.

## Lab steps
1. **Prepare a loopback-only lab.** Use a disposable Linux VM with Python 3, FastAPI/Uvicorn, and NGINX. Keep the API on `127.0.0.1:8000` and the proxy on `127.0.0.1:8080`; do not publish either service to the internet.
2. **Create the minimal health endpoint.** In a virtual environment, make `app.py`:

   ```python
   from fastapi import FastAPI

   app = FastAPI()

   @app.get("/health")
   def health():
       return {"status": "ok"}
   ```

   Run it with `uvicorn app:app --host 127.0.0.1 --port 8000`. `127.0.0.1` limits this practice server to the VM itself. Confirm `curl -i http://127.0.0.1:8000/health` returns HTTP `200` and a JSON body before adding the proxy.
3. **Add one NGINX server block** to the disposable VM's NGINX configuration:

   ```nginx
   server {
       listen 127.0.0.1:8080;
       server_name localhost;

       location / {
           proxy_set_header Host $host;
           proxy_pass http://127.0.0.1:8000;
       }
   }
   ```

   The URI-less `proxy_pass` preserves the incoming request path in this simple location. Validate with `sudo nginx -t` before reloading NGINX.
4. **Compare the same request.** Run `curl -i` against the direct endpoint and `http://127.0.0.1:8080/health`. Compare status, response body, and selected headers. In this local exercise, TLS and public DNS are not involved; include them as separate conceptual hops only if your diagram labels them as not tested.
5. **Predict and create an upstream failure.** Change only the NGINX upstream port to an unused local port, run `nginx -t`, reload the disposable NGINX service, and request the same proxied URL. Inspect the error log for the upstream address and connection failure. The proxy's `502` reports an upstream communication problem, not which root cause you should assume.
6. **Restore and verify.** Restore port `8000`, validate and reload NGINX, then repeat the direct and proxied requests. Save the sanitized config excerpt and results, not full logs that may contain unrelated data.

## Hints
```bash
curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8080/health
sudo nginx -t
sudo journalctl -u nginx --since "5 minutes ago" --no-pager
```

NGINX's `proxy_pass` address and optional URI affect how the request path is forwarded. In this simple `location /` example, leaving off the URI avoids a prefix-rewrite exercise. Validate configuration before reload; do not edit the system's default site or a non-lab proxy.

## Verification

- The direct and proxied health checks succeed with the correct mapping.
- The lab-only broken mapping produces a reproducible proxy error and a matching log entry.
- After rollback, `nginx -t` succeeds and the proxied health endpoint works again.
- The diagram accurately distinguishes DNS, TLS termination, proxy routing, and API handling for this lab.

## Troubleshooting

- **The API cannot bind:** confirm the chosen port is free and the service binds to loopback.
- **NGINX rejects the configuration:** run `nginx -t` and inspect the reported file and line.
- **The proxy returns 502:** check the upstream address, protocol, listener, and API logs in that order.
- **Only direct access works:** verify the proxy path and trailing-slash behavior.

## Cleanup

Stop only the lab API and proxy, remove the temporary configuration/project, and retain sanitized response headers and logs.
