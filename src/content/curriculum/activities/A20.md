# Secrets, identities and secure configuration

## Scenario

Applications need credentials to be present without exposing their values in terminal output, logs, repositories or CI reports.

## Learning objectives

- Use only a clearly fake token value in a local test or disposable repository.
- Check missing-configuration behavior, log redaction and least-privilege workflow permissions.
- Document ownership, storage and rotation without recording any real secret.

## Expected observations
A missing `APP_TOKEN` produces a clear nonzero failure without displaying any value. The fake-value run reports only that configuration is present; captured output contains neither the variable name's value nor environment dumps. The workflow's `contents: read` permission matches checkout/test-only behavior. The credential inventory describes ownership and rotation without containing secrets.

## Prerequisites
Review the [Module 20 learning path](/modules/20) before starting; the activity reference PDF is optional. Review GitHub's official [Actions secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) for least privilege, secret handling, and why redaction is not a security boundary.

## Challenge

Compare missing configuration with present dummy configuration, then classify synthetic identity and authorization cases without using a real token. Review the minimum permissions needed to check out and test code.

## Build outcome

Prepare a nonsecret configuration template, credential inventory and GitHub Actions security
review.

## Environment

Use a local test app or a disposable CI repository and a clearly fake token such as
`FIELDNOTES_DUMMY_TOKEN_DO_NOT_USE`. Never copy a real credential into the lab, terminal transcript, or evidence.

## Lab steps
1. In a disposable folder, create a tiny app that reads `APP_TOKEN` and prints only “configured” or “not configured”; it must exit nonzero when unset and must never include the value in an exception or log. Test it with the clearly fake value `FIELDNOTES_DUMMY_TOKEN_DO_NOT_USE`, then with the variable unset.
2. Capture the process output and search it for the fake value. Keep the terminal transcript private until that check passes; do not paste the fake value into notes or screenshots. Never test logging with a real credential.
3. Review this minimal GitHub Actions permission example for a workflow that only checks out and tests code:

   ```yaml
   permissions:
     contents: read
   ```

   Identify any additional API operation before granting a permission, and scope it to the job that needs it. Do not add a secret to this test workflow.
4. Write a credential inventory with name/purpose, owner, authorized readers, protected storage, rotation trigger, and response if exposed. Record the process and locations, never values. Explain why a masked log is not proof that transformed or encoded secret data cannot leak. Then use a paper policy that permits a specific issuer, audience and release subject to read one artifact. Compare a matching read request, a claim with the wrong audience, and a matching identity requesting a write. Label each outcome as allowed, identity rejected, or action denied and explain the deciding field. No token needs to be minted or sent.

## Hints
In Python, use `os.environ.get("APP_TOKEN")`; test whether the returned string is present, then print only a fixed status sentence. Do not use `print(os.environ)` or include the value in an f-string. The dummy value is for the local process test only; never store it in the activity evidence.

GitHub advises least-privilege token permissions and warns automatic secret redaction is not guaranteed for transformed values. Do not use `pull_request_target` to check out or execute untrusted pull-request code with secrets or a privileged token.

## Verification
- Unset and fake-value runs have the expected status, and neither stdout nor stderr includes the fake value.
- The example fails closed when required configuration is absent and does not print environment contents. The paper policy test separately shows why presence, accepted identity, and permission to perform an action are different.
- Workflow token permissions are no broader than the operations performed; any write permission has an identified API call and scope.
- The inventory has owners, authorized access, storage, rotation, and incident steps, but contains no secret values.

## Troubleshooting

- **Token appears in a log:** stop sharing the artifact, remove the dummy value, and verify the logger and exception
  path do not include environment values.
- **Scanner misses the fixture:** check supported file types and patterns; never validate detection with a real key.
- **Workflow needs write permission:** identify the exact API call and scope the permission to that job.

## Cleanup

Remove the dummy value from the test environment and logs. Keep only sanitized configuration examples and the response checklist.

## Evidence to record
Include the sanitized app logic, process exit status and fixed output for set/unset tests, proof that captured output did not contain the test value (without repeating it), the permission review, and nonsecret ownership/rotation procedure. Never record a real or dummy credential.

## Self-check

Explain where each credential lives, its permissions, its rotation path and how you would respond to
accidental publication.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
