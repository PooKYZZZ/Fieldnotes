# Secrets, identities and secure configuration

## Scenario

Applications need credentials to be present without exposing their values in terminal output, logs, repositories or CI reports.

## Learning objectives

- Use only a clearly fake token value in a local test or disposable repository.
- Check missing-configuration behavior, log redaction and least-privilege workflow permissions.
- Document ownership, storage and rotation without recording any real secret.

## Expected observations

The app reports whether required configuration is missing without echoing the dummy value. A deliberate fake pattern can be detected by the chosen scanner, while captured output and evidence remain free of that value. Permissions are justified by job operations; masking alone is not proof that a secret stayed private.

## Prerequisites

Complete or study Module 20 in 03_Operations_and_Security.pdf.

## Challenge

Create a deliberately invalid dummy token and confirm the app fails without printing it; review a sample
least-privilege Actions permissions block.

## Build outcome

Prepare a nonsecret configuration template, credential inventory and GitHub Actions security
review.

## Environment

Use a local test app or a disposable CI repository and a clearly fake token such as
`FIELDNOTES_DUMMY_TOKEN_DO_NOT_USE`. Never copy a real credential into the lab, terminal transcript, or evidence.

## Lab steps

1. Add a small configuration example that reads a token from an environment variable and fails closed when it is
   missing.
2. Run a test with the dummy value and a test with the value unset. Confirm logs do not print the value.
3. Add or review a GitHub Actions permissions block with read-only access by default; identify any step that needs
   additional access and justify it.
4. Use a local secret scanner or a safe dummy fixture to verify that a deliberate dummy-token pattern is detected.
5. Write where a real credential would be stored, who could access it, how it would be rotated, and the response
   steps after accidental publication—without recording the credential itself.

## Hints

- Print only whether a variable is configured, never its value.
- Keep real local environment files ignored and out of screenshots.
- Treat masking as a safety net; do not intentionally send actual secrets to test log redaction.

## Verification

- Missing configuration produces a clear error and the process does not start in an unsafe mode.
- The dummy value is not present in captured output or generated reports.
- Workflow permissions are the minimum needed for each job.
- The credential inventory contains purpose, owner, permission, storage, and rotation method, but no secret values.

## Troubleshooting

- **Token appears in a log:** stop sharing the artifact, remove the dummy value, and verify the logger and exception
  path do not include environment values.
- **Scanner misses the fixture:** check supported file types and patterns; never validate detection with a real key.
- **Workflow needs write permission:** identify the exact API call and scope the permission to that job.

## Cleanup

Remove the dummy value from the test environment and logs. Keep only sanitized configuration examples and the response checklist.

## Evidence to record

Include the nonsecret configuration example, missing/dummy configuration behavior, redacted output and scanner result, permission review, and credential ownership/rotation plan. Never save a real token or the dummy token value itself.

## Self-check

Explain where each credential lives, its permissions, its rotation path and how you would respond to
accidental publication.

## Independent reflection

What would you inspect first if this stopped working tomorrow? What can you verify without asking anyone
else?
